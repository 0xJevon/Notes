# 12 · 工具辅助审计（SAST · CodeQL · MCP · IAST）

> **一句话**：工具负责"铺满候选"，人负责"收敛成结论"。工具报的每一条，都要能指回 `文件:行号`、能出复现包，否则不进报告。
> 源：小迪代码审计笔记「技巧·工具挖掘」一节（2026-11-20 补入，原文只有配置截图，判据是我按审计动作补的）。
> 与 [[01-审计流程与技巧]] 第 3 步（Analyze）配合用：那篇讲跟数据流，这篇讲用什么铺面前提。

---

## 一、三类工具的分工（不能互相替代）

| 类型 | 全称 | 什么时候介入 | 能出什么 | 出不了什么 |
|---|---|---|---|---|
| **SAST** | Static Application Security Testing | 有源码，进场第一步 | **全量候选**（行号级，覆盖所有入口） | 判不了可达性、判不了前置条件 |
| **DAST** | Dynamic Application Security Testing | 有可运行环境 | 真实请求的命中结果 | 覆盖率低，深层业务逻辑漏 |
| **IAST** | Interactive Application Security Testing | 能部署 + 能操作页面 | 操作路径上的**真实数据流** | 没点到的功能全漏 |

**判据**：SAST 管覆盖，IAST 管确认，DAST 管验证。三者是三种问题，不是三种精度。

---

## 二、SAST 的三条路

### 1. IDEA 插件——最快，适合单点精读

- 内置 Inspector + Find Usages，跟 sink 时随手看污点来源
- **产出**：辅助判断，不产出报告。它的价值是省掉"这个参数谁传的"这一类翻找

### 2. CodeQL——最重，适合整套系统铺面

思路是先把源码编译成可查询的数据库，再用 QL 语句问结构性问题。

**建库**（以 Maven 项目为例）：

```bash
codeql database create tmall --language="java" \
  --command "mvn clean install --file pom.xml -Dmaven.test.skip=true" \
  --source-root=/path/to/Tmall_demo-master --overwrite
```

**分析**（用官方规则集）：

```bash
codeql database analyze tmall /path/to/codeql/java/ql/src/codeql-suites/java-code-scanning.qls \
  --format=csv --output=result.csv
```

**原笔记的实测结论（重要）**：官方规则集对**业务逻辑漏洞的检测能力弱**，报出来的偏模式化（硬编码、弱随机、不安全随机数）。要覆盖业务洞，得自己按项目写 QL，或用别人拓展的规则集（原笔记提到 CodeQLpy）。

**据此得出的判断**：CodeQL 的价值不在"跑官方规则出报告"，在**能对整个代码库问结构性问题**——"这个方法被谁调用""这个参数能不能流到那个 sink""这个注解在哪些类上缺失"。把它当查询引擎用，不是当扫描器用。

### 3. MCP 辅助——把代码结构能力接给模型

原笔记的操作流程：

| 步 | 动作 |
|---|---|
| 1 | 运行 `enrir-CodeAuditTool.exe`，在 `resources` 的 yaml 里配置 maven 仓库 |
| 2 | `enrir-CodeAuditTool.exe -i "源码地址"` 生成分析结果 |
| 3 | Cherry Studio 里选模型、建话题、配 MCP 服务器，之后用对话方式问代码 |

**判据（红线）**：模型能读结构、能回答"这个参数流到哪"，但**它会把"存在拼接"说成"存在注入"**。每条结论都要自己回代码确认。
**在库里的位置**：这是 [[Security/工具链/00-索引|工具链]]「AI 接重复劳动、不接判断」的具体一例——模型铺候选，人定结论。

## 三、IAST：只报真的

把源码部署到带插桩的测试平台，正常操作网站，插桩层记录实际流过的数据，生成报告。

| 优势 | 短板 |
|---|---|
| **误报低**——只报真实流过的路径 | 覆盖率完全取决于你点了多少功能 |
| 能看到 SAST 跟不动的反射/动态拼接 | 需要能起环境，且要熟悉业务操作路径 |

**用法**：SAST 出了候选、环境也能起时，用 IAST 快速确认哪几条是真的，省掉逐条手工验证。

---

## 四、什么时候用哪个

| 情况 | 用什么 |
|---|---|
| 刚拿到源码，不知从哪看起 | CodeQL 建库 + 人工过依赖版本 → 先出一张入口清单 |
| 已知可疑点，要确认 | IDEA 跟一遍 + 本地起服务发请求 |
| 要覆盖全部入口，判断可达性 | CodeQL 自写 QL 查"入口 → sink"路径 |
| 能部署、时间紧、要真实命中 | IAST 边操作边看 |
| 代码量极大、只要候选 | MCP 接模型批量问，人工收敛 |

---

## 五、本线的红线

1. 工具出的每条候选必须能指到 `文件:行号`，指不到的直接丢——这是 A2「五列齐全」的入口门槛
2. 工具判"可利用"不算，要自己发出请求拿到响应
3. **报告里不许直接引用工具给出的风险等级**，定级按三轴自己算（见 [[Security/F-验证定级交付/00-索引|F 域]]）
4. 官方规则集的漏报率未知，不许拿"工具没报"当"没有洞"的依据
