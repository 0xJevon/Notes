## Web漏洞原理

### sql注入原理，从代码层面了解sql注入的成因

原理：攻击者将可控变量构造为恶意的sql语句导致输入的数据被拼接为sql代码执行，根本原因是没有区分数据和代码，也就是没有对用户可控数据做严格过滤

代码层面：若原sql语句是select * from users where username='' and password=''，攻击在构造语句为admin'--+，则构造的恶意sql语句为select * from users where username='admin'--+' and password=''，正常sql语句逻辑变为select * from users where username='admin'，篡改了本来的sql查询语句

不安全开发：

1. 手动拼接sql语句而非参数化查询
2. 对用户输入未进行严格过滤
3. 使用ORM框架如Mybatis时有意或无意将安全写法${}改为#{}

修复：

1. 预编译使用?占位符使用户输入始终未数据而非代码
2. 对用户输入进行白名单过滤，如过滤'、"或#等
3. 限制数据库权限



### 不同数据库的SQL注入

主流数据库包括mysql、sqlserver、oracel、PostgreSQL等，漏洞原理相同都是攻击者通过可控变量构造恶意sql语句使原sql语句拼接闭合造成恶意攻击

不同点在于不同数据库中的关键字不同

1. 执行命令函数MySQL使用LOAD_FILE()、INTO OUTFILE写入shell，SQLServer中使用xp_cmdshell
2. 延时函数MySQL使用sleep()、oracle使用DBMS_PIPE.RECEIVE_MESSAGE、PostgreSQL使用pg_sleep()
3. 文件读取MySQL使用LOAD_FILE()，PostgreSQL使用pg_read_file()

在实战中我会先利用端口扫描或报错信息等确定数据库类型，再用SQLMap的--dbms参数指定数据库类型进行攻击，最好根据数据库特性选择高阶利用方式如MySQL使用/\*!*/内联注释绕过WAF，或SQLServer中若xp_cmdshell被禁用我则会选择sp_oacreate执行命令

### mysql的报错注入

报错注入函数报告extractvalue()、updatexml()、floor()、exp()等，报错信息中带出非法内容

- extranctvalue()、updatexml()使用concat和~拼接造成XPath路径报错，比如updatexml(1,concat(0x7e,(select database()),0x7e)查询数据库名，但报错信息最多为32字符所以可以使用substring()或mid()截断查询，或是limit分页查询，具体语句updatexml(1,concat(0x7e,substring((select database()),1,30)),1)，还可以通过load_file读取文件内容extractvalue(1,concat(0x7e,substring(load_file('etc/passwd'),1,30)),1)，也可用into outfile写入shell

- `floor` 报错注入利用 `GROUP BY` 创建临时表，并以 `floor(rand(0)*2)` 作为主键。由于 `rand(0)` 在计算过程中被多次调用，序列为0、1、0导致临时表的主键冲突，而 `concat()` 中的子查询结果会被 MySQL 在报错信息中泄露，`count(*)` 是 **聚合函数**，它强制 MySQL 使用 `GROUP BY` 的临时表机制。

  ```sql
  select count(*),concat(version(),floor(rand(0)*2))x from information_schema.tables group by x
  ```

  - 仅适用于MySQL数据库(5.0及以上版本)

- exp()会计算e的x次方，当传入的x参数非常大时会导致指数函数溢出，exp上限为709，exp(710)触发溢出

  ```sql
  AND EXP(~(SELECT*FROM(SELECT CONCAT(table_name,':',column_name) FROM information_schema.columns WHERE table_schema=database() LIMIT 0,1)x))
  ```

### sql二次注入

数据库对用户输入的数据有严格过滤，如对数据进行转义，插入数据admin'--+ sql语句为insert into users values('admin\\'--+')，其中--+被转义，但是存储在数据库后可能因为存储或读取机制的差异导致存储的就是未过滤的的数据也就是'admin'--+'，所以可以通过update或delete触发数据库中存储的恶意代码，sql语句为update users set password='123456' where username='admin'--+' 

防御：

1. 输入时使用预编译，占位符作为数据载体只会被作为数据处理，而不会当作SQL语法的一部分执行
2. 存储时限制字段类型，如使用正则匹配将用户名、密码等字段设置为字符串类型
3. 关键操作前再次过滤或检验数据，可再次对特殊字符转义或使用白名单检验

### ssrf漏洞原理

- 原理

  当服务端有向内网请求资源或功能的操作时，若服务端对用户可控的URL为作出严格过滤，如未校验HOST头或未限制302跳转，攻击者便可利用该服务端向内网发出恶意请求，常见于业务功能需要请求外部资源的情况如远程文件/图片下载、远程URL访问等

- 利用

  使用http://协议探测内网服务、使用file://协议读取内网文件

  还可以利用SSRF攻击云服务器，去探测内网服务，造成云元数据泄露，若获得了云服务凭证还可临时接管云服务器

  更严重还可以使用gopher://协议配合Java反序列化造成RCE，以及对Redis写入SSH密钥造成未授权

  - 绕过

    对于有过滤的SSRF可使用DNS重绑定、IP编码绕过IP黑名单

- 防御
  1. 限制可被利用的攻击协议如gopher://、file://以及dict://等
  2. 设置白名单限制服务器可访问的内网ip



### dict和gopher协议有什么区别

dict主要用于探测内网端口或服务指纹，可单次执行命令，但受限于**单次交互**无法完成复杂攻击

gopher协议可构造**多行协议包**攻击无认证服务如Redis、fastcgi、mysql等(Redis的set写webshell)，以及写入配合Java的URLClassLoader造成RCE

防御上可限制服务器访问非业务端口(Redis的6379端口)，或代码层禁用URLClassLoader

### CSRF的原理以及如何防御

CSRF是攻击者利用浏览器保存用户凭证即cookie的机制，攻击者可以构造恶意请求链接或恶意页面（如转账、修改密码等），诱使用户在已登陆目标网站且cookie未过期的情况下恶意链接，浏览器会携带cookie向目标服务器发送请求，由于服务端仅根据cookie验证用户身份未检验请求来源，造成服务器将恶意请求识别为用户的合法操作，进而执行攻击者预设的指令，从而造成漏洞。

防御

- 检测cookie来源
  - 检测referer头是否来自白域名，不是则拒绝请求

- 使用token识别用户
  - 用户登录网站时，在服务端生成随机且唯一的token。并存储在用户会话中，用户发送请求时会同时携带cookie和token，服务端会额外验证请求包中的token与用户登录时存储的token是否一致，不同则拒绝请求

- 采取同源策略
  - 要求页面发起的HTTP请求与当前页面的协议、域名和端口相同，限制了跨域请求
- 二次验证
  - 对于涉及金融、账号安全等敏感操作时作出二次验证，如密码/短信验证

## Java安全

### 说一下Java反射

Java反射是动态操作类元数据的机制，允许在运行时获取类的Constructor、Field以及Method，如Class.getDeclaredFields，并且还能动态修改私有成员，也能通过setAccessible(true)去创建新的实例或调用方法，如Method.invoke，使攻击者可以更灵活的操控类，是Java反序列化漏洞最基本的方法，如CC1链中通过Transformer数组反射调用Runtime.getRuntime.exec()实现命令执行，防御可以应用白名单限制可反射调用的类、限制类加载器以及及时更新补丁



面试可能追问：

1. 如何检测应用中的危险反射调用？
   - 答：静态分析查找Method.invoke调用链，动态Hook关键反射API
2. 除了Runtime.exec，反射还能触发哪些危险操作？
   - 答：ClassLoader.defineClass(字节码注入)、JNDI lookup(反序列化)、特权上下文切换等
3. 如何绕过反射防御机制？
   - 答：通过Unsafe类内存操作、JNI调用、或利用保留的合法反射接口



### CC链基本原理

CC链的核心是通过反序列化将一系列实现了Serializable接口的可序列化类作为入口，调用它们的readObject()方法触发链式调用，这些类在反序列化的过程中，因为人为利用反射修改参数值导致在不同的类中自动调用某些方法最终触发命令执行等危险操作

**CC1**

初代的CC1链是基于Apache Commons-Collections 3.2.1这个组件，使用Runtime.getRuntime.exec为执行命令的sink，这个链继承了Transformer接口的相关类如ConstantTransformer、InvokerTransformer以及ChainedTransformer，使用ConstantTransformer获取Runtime.class，然后利用InvokerTransformer通过反射获取getRumtime，并通过invoke执行exec。然后利用jdk8u65自带的AnnotationInvocationHandler为source入口，调用其中的readObject为链的起点，然后利用TransformedMap.checkSetValue()方法连接整条链，这是CC1的一种写法，还有一种更换了gadget通过AnnotationInvocationHandler中的动态代理触发到LazyMap.get()然后连接后面的命令执行类。

CC1是后续 CC 链发展的基础，但是对JDK和 Commons - Collections 组件版本有严格的要求，适用范围相对较窄。

**CC6**

接着是更为通用的CC6，可以不受Commons-Collections以及jdk的版本限制，使用更稳定的HashMap为source，然后通过TiedMapEntry.hashcode()连上与CC1同样的sink，即执行 `Runtime.getRuntime().exec()` 命令。

CC6 链的优势在于版本兼容性强，能在更多环境中使用。

**CC3**

CC3更换了利用部分，不再依赖反射调用Runtime.class而是利用类加载机制执行命令，类加载会经过loadClass()->findClass()->defineClass()路径，攻击者将恶意代码写入攻击类的静态代码块，当类被加载并通过newInstance()初始化后会自动调用类的静态方法，这时写入的恶意代码就会执行，CC3入口部分与CC6一致，然后类加载部分调用了TemplatesImpl.defineClass()，恶意类写入_bytecodes字段，执行部分使用的是TemplatesImpl.getTransletInstance()下的newInstance()。

**CC4**

CC4沿用CC3的执行部分，将入口部分更换为PriorityQueue.readObject()，通过TransformingComparator.compare()连接，该类在Common Collections 4.0可序列化而在3.2.1版本不行，所以CC4可针对特定版本

**CC2**

CC2不再使用Transformer[]数组，因为在shiro中重写了动态加载数组的方法导致无法通过Transformer数组实现危险方法。

CC2 链的出现是为了绕过 Shiro 框架的限制。

**CC5和CC7**

CC5和CC7的还是和CC1一样通过Transformer数组调用Runtime.getRuntime().exec()执行命令，只不过更换了一下入口类。CC5是BadAttributeValueExpException.readObject()为source，通过TiedMapEntry.toString()连接到LazyMap，CC7将HashTable.readObject()作为入口类，特别的是用了Java hash碰撞的一个特性，就是yy的hash值与zZ的hash值相同。

**防御**

升级jdk版本、禁用不必要的反序列化或定期更新依赖库，使用JDK 17+的过滤机制



### 反序列化的危险函数

Java反序列化入口方法ObjectInputStream.readObject()、readExternal()、JSON.parse、JSON.parseObject，通过反射修改私有变量参数构造gadget链触发sink如Runtime.getRuntime().exec("calc")；

php反序列化入口方法unserialize()，反序列化时自动触发魔术方法wakeup()，销毁触发魔术方法desturct()，然后控制对象属性调用不同的魔术方法构造POP链执行命令。

python还有个pickle反序列化

防御：Java更新依赖库，启用ObjectInputFilter；PHP禁用unserialize()，对魔术方法做参数校验。



### Shiro550原理

Shiro550通过RememberMe Cookie保存用户凭证，加密过程是序列化->AES-CBC加密->Base64加密，漏洞利用点是，攻击者构造恶意序列化链，然后使用默认的AES密钥和Base64加密算法构造恶意Cookie发送，服务器收到恶意Cookie并进行解密操作时会触发ObjectInputStream.readObject()反序列化造成命令执行；



反序列化链可以使用CC11，该链针对Commons-Collections 3.1-3.2.1版本，因为Shiro重写了resolveClass()，添加了ClassUtils.forName()，其中使用loadClass()加载类，但loadClass()无法加载数组类所以。所以CC11结合CC6的入口部分(HashMap)+CC2的执行部分(TemplatesImpl)进行动态类加载造成恶意代码执行；

CB链针对CommonsBeanUtils依赖，以PriorityQueue.readObject()为source，TemplatesImpl.getOutputProperties()配合类加载作为命令执行部分



防御：升级Shiro版本或更换默认密钥，禁用RememberMe或使用JWT替代，部署反序列化过滤器SerialKiller。



### RMI的漏洞原理

远程方法调用(RMI)是Java提供的一种机制，允许一个JVM上的对象调用另一个JVM上对象的方法。

**具体流程**

**RMI Server**创建实例化对象Stub（含远程对象引用），然后使用LocateRegistry.createRegistry创建注册中心Registry，管理和存储远程对象的引用，最后将Stub绑定到注册中心以便Client能够发现和调用这些远程对象；

**Client**需要调用远程方法时会从Reigstry获取Stub，使用UnicastRef发起远程调用(底层上TCPEndpoint处理具体网络请求)，从而与服务端通信

RMI数据传输依赖Java序列化机制，所以攻击者可以构造序列化链造成攻击，当Registry或Server接收恶意序列化数据并进行反序列化操作时时就可能触发命令执行

**攻击方式**

JRMP注入：伪造UnicastRef指向攻击者控制的RMI服务，诱导Server反序列化恶意响应，进而执行恶意代码，这种攻击方式利用了 RMI 在处理远程引用和反序列化过程中的漏洞。

DGC攻击：分布式垃圾回收（DGC，Distributed Garbage Collection）是 RMI 用于管理分布式对象生命周期的机制。攻击者利用DGCImpl.dirty()在反序列化过程中的漏洞，通过构造恶意序列化数据在服务端反序列化时触发RCE。

**防御**

可限制RMI访问权限限制1099端口，禁止远程类加载，升级JDK版本



### JNDI注入漏洞原理

Java 命名与目录接口（JNDI）是 Java 提供的一种标准服务，它能将服务地址和服务名进行绑定，应用程序可以通过 `lookup()` 方法来访问命名服务，从而获取所需的资源，比如RMI、LDAP等服务。然而，当应用程序在处理用户输入时，没有对传入 `lookup()` 方法的参数进行严格的验证和过滤，攻击者就可以构造恶意的 JNDI 引用，使得应用程序在执行 `lookup()` 操作时加载并执行恶意代码，进而引发 JNDI 注入漏洞。

**攻击方式**

RMI原生反序列化漏洞，绑定恶意对象到Registry，当应用程序使用lookup()方法查找恶意对象时，会触发Java反序列化机制，调用readObject()方法，如果存在可利用的反序列化链就能构造恶意反序列化数据

JNDI特有的引用漏洞，JNDI的Reference类可以指定远程工厂类factory，攻击者可以构造恶意的Reference对象，并将factory指向一个包含恶意代码的远程类。当应用程序使用lookup()加载并实例化该引用时，会从指定的远程地址下载并执行恶意类从而造成攻击。该方法针对**jdk8u121之前版本**，

LDAP+引用漏洞，为增强安全性，JDK8u121引入了trustURLCodebase限制，默认禁止从远程地址加载类。但攻击者可以利用LDAP服务器，让LDAP响应返回javaSerializeDate或JavaReferenceAddress等特殊类型的数据，从而绕过trustURLCodebase限制，当应用程序通过lookup()查询LDAP服务时，会加载并执行恶意代码。**针对JDK版本8u121-8u191**，

**针对jdk8u191之后版本**对JNDI远程类加载做了更严格的限制，但是若目标引入了javax.el依赖，攻击者可利用ELProcessor.eval()执行任意表达式。攻击者构造恶意的JNDI引用，当应用程序执行lookup()时触发ELProcessor.eval()执行恶意表达式造成代码执行

**防御方案**

升级JDK版本并禁用远程类加载（设置trustURLCodebase=false）

对lookup()做白名单过滤

对用户输入进行严格的验证和过滤

### Fastjson反序列化流程

FastJson反序列化漏洞最初的版本是1.2.24，通过paser或parserObject解析Json字符串时在DefaultJSONParser类中检测到@type后会通过TypeUtils.loadClass加载其指定的类，随后会在JavaBeanInfo.build中通过反射获取类结构比如setter或getter方法，最后由JavaBeanDeserailizer反序列化恶意类时触发恶意方法。

**利用链**

基于**JdbcRowSetImpl**类的利用主要是利用其`setDataSourceName`和`setAutoCommit`等方法。攻击者可以通过构造包含`@type`为`com.sun.rowset.JdbcRowSetImpl`的 JSON 数据，设置`dataSourceName`为恶意的 JNDI 地址，当 Fastjson 反序列化该 JSON 数据时，会触发 JNDI 注入，从而加载并执行恶意代码。

结合 **BCEL**（Byte Code Engineering Library）ClassLoader 实现 RCE 的方式，是通过构造包含恶意字节码的 JSON 数据。Fastjson 在反序列化过程中会加载并执行这些字节码，从而实现远程代码执行。这种方式不需要与外部网络进行交互，适用于目标系统无法访问外网的情况。

利用 **TemplatesImpl** 链是通过构造包含`@type`为`com.sun.org.apache.xalan.internal.xsltc.trax.TemplatesImpl`的 JSON 数据。攻击者可以在 JSON 数据中设置恶意的字节码，当 Fastjson 反序列化该 JSON 数据时，会触发字节码的加载和执行，从而实现代码执行。

**高版本绕过**

然后在后续1.2.25版本后为了修复漏洞将原本的TypeUtils.loadClass替换为了checkAutoType过滤类，这个类会加载白名单中的类，以及检测是否有黑名单中的类被指定加载，其中的autoTypeSupport默认关闭，会影响后面的绕过，第一种绕过方式是autoTypeSupport开启时，可以用**L和;闭合**恶意类绕过过滤，因为TypeUtils.loadClass会去除L和;，导致恶意类被加载进入后续的解析流程；

第二种更为通用的方式是**Class缓存污染**在解析第一段Json时将恶意类作为val传入Class类，然后Fastjson解析这个类时会调用MiscCodec解析器里面若满足解析的类是Class类时会调用TypeUtils.loadClass并将恶意类传入mapping，然后第二部分仍旧是恶意的利用类比如JdbcRowSetImpl，在第二次解析时checkAutoType会从缓存中加载出恶意类并代入后续的利用流程。1.2.25-1.2.32版本：未开启AutoTypeSupport时能成功利用，开启AutoTypeSupport不能成功触发，因为加载第二部分恶意类时会进入第一个过滤判断导致抛出异常；1.2.33-1.2.47版本：无论是否开启AutoTypeSupport，都能成功利用；因为除了判断类是否在黑名单中还判断类是否在缓存中，都不满足才抛出异常。1.2.48后mapping缓存改为局部变量后阻断了污染。

**防御**

升级 Fastjson 版本，例如，1.2.48 及以后的版本对缓存机制进行了改进，阻断了 Class 缓存污染的绕过方式。

尽量避免开启`autoTypeSupport`，因为开启该选项会增加反序列化漏洞的风险。如果确实需要使用，应严格配置白名单，只允许反序列化安全的类。

## 代码审计

### JAVA代码审计流程

拿到Java源码后首先应该先查看开发文档、README文件或注释信息快速了解项目的功能、业务逻辑以及关键技术，这样对源码使用的框架和结构做一个简单的了解后便可以根据环境要求使用maven建构项目，配置数据库搭建实验环境。

然后判断是用什么项目，若是servlet项目，一般会存在WEB-INF目录，然后其下的web.xml文件中记录了所有的路径映射，找到漏洞点后可根据这个文件逐步跟踪获得路由，以及lib目录了解引入的第三方库；若是Springboot项目则一般存在application.properties或application.yml配置文件以及controller目录，对应的路由可在该目录下的控制器中找到。Springboot的数据流一般是Controller层接收用户输入->Service层处理->Dao层拼接SQL->执行。

然后是具体的漏洞挖掘，可以使用一些自动审计工具如Fortify先整体审计后再人工对审计结果做出筛选和确认，也可以手动搜索漏洞点并跟踪挖掘。

对应sql注入漏洞首先要区分该项目是用什么方法连接的数据库，如JDBC原生连接，Mybatis以及Hibernate框架连接，具体的可以从开发文档、pom引用库或是框架特征进行判别，如Mybatis一般存在mapper目录其下的xml文件写入具体的sql语句；然后搜索不同方法的不安全写法，如原生JDBC搜索append、order by和+直接拼接等不能预编译的点逐步跟踪到Controller文件下找到漏洞路由进行验证；Mybatis搜索${，在order by排序、like模糊查询等情况不能使用#{}的安全写法，通过漏洞点找到路由，再在实验环境下手动或使用sqlmap验证漏洞是否存在。

对于文件操作漏洞可先找到功能点再通过路由找到功能代码进行审计判断是否操作漏洞，或是搜索new File{、FileInputStream、new FileInputStream{等关键字进行审计判断漏洞是否存在。

接着是鉴权漏洞，同样先确定使用的框架，若是Intercreptor拦截器一般会存在intercreptor目录，鉴权逻辑主要查看代码中的preHandler，审计代码并找到对应路由进行验证；若是Filter过滤器一般会存在filter目录，鉴权逻辑在代码中的init或doFilter中；使用Shiro鉴权可在开发文档或pom引用中确定，查看shiro的配置信息，anon一般表示不需要鉴权的配置，可搜索这些不需要鉴权的路径进行拼接绕过；然后JWT鉴权一般就是默认密钥未修改，可以自主构造JWT进行权限访问。

然后是一些第三方组件的漏洞，可以搜索是否存在有历史漏洞的组件，如Log4j、XStream、Jackson、Fastjson 1.2.48之前版本，Common Collections 3.1-3.2.1或Common Collection 4等版本可能存在反序列化漏洞，找到路由使用ysoserial生成payload验证漏洞

## 提权

### mysql提权

UDF提权

- UDF（USER DEFINE FUNCTION）是MYSQL的拓展接口，允许用户添加自定义函数实现特定功能，MYSQL允许通过动态链接库(Linux中的.so或Windows中的.dll)加载自定义函数，这些函数能调用系统API，从而实现与操作系统的交互功能。
- 当MYSQL配置文件中的secure_file_priv为空或指向可写目录、有CREATE和FILE权限且MYSQL以root权限运行时，攻击者可通过UDF执行系统命令实现提权
- 具体步骤
  - 上传恶意so/dll文件
  - 上传UDF函数`CREATE FUNCTION sys_exec RETURNS INTEGER SONAME 'udf.dll'`
  - 执行系统命令`SELECT sys_exec('command')`

MOF提权

- MOF（Managed Object Format）是一种用于描述 WMI（Windows Management Instrumentation，Windows 管理规范）数据的语言。
- 攻击者利用MySQL的写权限写入MOF恶意文件到`C:\WINDOWS\System32\wbem\MOF`，系统会定期编译执行该目录下的.mof文件，利用该特性便可通过MOF文件执行系统命令从而实现提权

启动项提权

- MySQL启动时会读取配置文件（如my.ini或my.cnf），攻击者获得写权限后可修改配置文件，然后重启MySQL服务，利用修改后的配置执行恶意操作，如使用LOAD DATA INFILE读取或写入文件获取敏感信息或上传恶意文件实现提权

  

## 内网渗透

### 解释一下代理隧道技术

为解决与内网的通信问题以便后续的信息收集以及深入攻击可以使用代理隧道技术，首先通过webshell到提权再到内网或直接获得内网vpn后，可使用cs或msf上传shell然后建立socks隧道，接着使用proxifier建立socks代理，若无法直接通过cs或msf上传payload建立Socks代理时，可以上传frp、nps或chise等工具作为替代方案建立Socks代理，此外若内网对出网流量有严格限制时还可以针对特定的服务建立对应隧道，如仅允许80/443出网时可使用reGeorg建立HTTP隧道将流量伪装成正常HTTP请求，若仅允许DNS查询可以使用dnscat2建立DNS隧道利用TXT记录传输数据，限制TCP/UDP但允许ping时可以使用ptunnel建立ICMP隧道将数据封装在ICMP包中，若存在SSH服务且可登录时可以使用动态端口转发(-D)或本地转发(-L)

### 正反向代理的区别

正向代理是客户端明确要访问的目标服务器，由代理服务器代替客户端向目标服务器发起请求，并将响应返回给客户端，起到了隐私保护和突破访问限制的作用。在内网渗透中，当防火墙对入站流量限制不严格且能允许客户端访问外部IP时可使用cs的bind_tcp或msf的exploit/multi/handler生成正向木马，上传shell后使用connect建立正向连接。但目标防火墙会记录连接的IP和端口，易被溯源；

反向代理则是服务于服务端，反向代理服务器接收客户端的请求，再将请求转发给服务端，并将响应返回给客户端，客户端并不知道请求服务端真实服务器。在内网渗透中由于防火墙对出战流量限制较少，大部分会利用反向代理绕过入站限制，使用cs的reverse_http或msf的reverse_tcp生成反向木马，客户端开启对应端口监听流量，上传shell后建立反向连接；

可配合正反向代理建立混合代理，攻击者与公网VPS建立反向连接，然后VPS与内网跳板机建立正向连接，接着进行内网渗透，这样可以更好的隐藏攻击者的流量，难以被溯源。
