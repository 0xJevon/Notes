# M3 提权与身份切换：UAC 与 sudo

> 归属：[[Tech/操作系统/00-学习地图]] ｜ 答题：[[M3-问答]] ｜ 上一单元：[[M2-导读-特权与能力]]

## 1. 这个单元要回答什么

**"我是管理员，为什么还是被拒？"**

这个问题有两个完全不同的答案，**混在一起是你现在最容易犯的错**：

| 答案 | 机制 | 什么时候是它 |
|---|---|---|
| A. 你的令牌里管理员组被标成了 **deny-only** | UAC 的过滤令牌 + DACL | **绝大多数情况** |
| B. 对象的完整性级别比你高 | MIC，`no-write-up` | 沙箱场景（低权限进程写高权限位置） |

多数人（包括很多写工具的）会把 A 说成 B，说"UAC 拦住了"。**UAC 没有"拦"，它只是给了你一枚权限更少的令牌。** 拦你的是 DACL——只不过因为令牌变了，DACL 的结论跟着变了。

这个区分不是文字游戏：A 的解法是"换完整令牌"，B 的解法是"换更高完整性的进程"，两条路完全不同。

## 2. 核心机制

### 2.1 完整性级别是什么

每个令牌有一个完整性级别（IL），每个对象也可以有一个。规则只有一条，而且**只管写**：

```text
写操作：主体 IL ≥ 对象 IL   才能通过
读操作：不检查 IL
```

这条叫 `no-write-up`。四个级别：

| 级别 | 值 | 谁在这个级别 |
|---|---|---|
| Low | 0x1000 | 沙箱化进程（部分浏览器渲染进程、PDF 阅读器） |
| Medium | 0x2000 | **普通用户，以及 UAC 过滤后的管理员** |
| High | 0x3000 | 提权后的管理员 |
| System | 0x4000 | SYSTEM 进程 |

默认情况下，文件系统对象的 IL 都是 Medium。所以 **Medium 进程写普通文件不会被 IL 挡**——这一点很关键，它意味着：平时遇到的 `Access is denied`，八成不是 IL 造成的。

IL 真正起作用的地方是沙箱：Low 进程想写 Medium 的文件，被 `no-write-up` 挡住，只能通过 broker 进程代写。这是浏览器"另存为"要弹框的原因。

### 2.2 UAC 的真实动作：分裂令牌，不是拦截

管理员登录时（M1 讲过），系统发两枚令牌。过滤令牌里：

- 完整性级别降到 **Medium**
- **`Administrators` 组被标记为 `Use for deny only`**

第二行才是关键。它意味着：在 DACL 求值时，这个组**只能用来拒绝，不能用来允许**。所以哪怕 ACL 里写着 `BUILTIN\Administrators:(F)`，过滤令牌也拿不到这个允许。

用 `whoami /groups` 能直接看到这个标记：

```text
BUILTIN\Administrators   Alias   S-1-5-32-544
    Mandatory group, Enabled by default, Enabled group, Group owner
```

提权前会看到 `Use for deny only` 字样，提权后这行消失。**这是你判断"我现在是哪个令牌"最快的一眼。**

### 2.3 怎么区分 A 和 B

按这个顺序查，30 秒能定：

| 步骤 | 看什么 | 结论 |
|---|---|---|
| 1 | `whoami /groups` 里 Administrators 有没有 `Use for deny only` | 有 → 是 A，换完整令牌即可 |
| 2 | `whoami /all` 里的 `Mandatory Label` | 比对象低 → 可能是 B |
| 3 | `icacls 目标` 里有没有 `(DENY)` | 有 → DACL 显式拒绝，与 IL 无关 |
| 4 | 文件是不是只读属性、你是不是所有者 | 只读属性会挡写；所有者能改 DACL |

### 2.4 UAC 弹不弹，由程序决定

程序的 manifest 里写着 `requestedExecutionLevel`：

| 值 | 行为 |
|---|---|
| `asInvoker` | 继承父进程令牌，**不弹** |
| `highestAvailable` | 管理员身份运行时弹 |
| `requireAdministrator` | **一定弹** |

所以"为什么这个 exe 双击没弹 UAC"的答案通常在它的 manifest 里，不在系统设置里。反过来，**如果程序没写 manifest，Windows 会用启发式判断**（名字里带 setup/install 之类），这也是有时期望外的程序会弹的原因。

### 2.5 Linux 侧：sudo、su 与 setuid

Linux 没有 UAC，也没有"两枚令牌"。它用另一套思路：**把提权做成一次显式的委托**。

| 路径 | 机制 | 需要什么 |
|---|---|---|
| `su` / `su -` | 切换到目标账户 | **目标账户的密码**（通常是 root 密码） |
| `sudo` | 按 `/etc/sudoers` 授权，以目标身份执行**一条命令** | 自己的密码（或 `NOPASSWD`） |
| SUID 程序 | 文件属主是 root + SUID 位 | 无，任何人可运行 |
| capabilities | 文件带 `cap_*` | 无 |
| polkit | 桌面环境下的特权请求（D-Bus） | 会话有效 + 规则允许 |

**和 UAC 的根本差别**：

| | Windows（UAC） | Linux（sudo） |
|---|---|---|
| 授权单位 | **账户**（你在管理员组就行） | **命令**（逐条列出你能跑什么） |
| 凭证 | 不重新验证密码（点确认即可） | 默认要输自己的密码 |
| 结果 | 换一枚令牌，同一用户 | 换 euid，变成另一个身份 |
| 配置位置 | 组关系 + manifest | `/etc/sudoers`、`/etc/sudoers.d/` |

**这里有一个必须记住的判据**：`sudo` 的"只能跑某几条命令"**不是安全边界**。因为大量程序本身能执行 shell、读写文件、加载插件——只要能跑其中之一，就等于能跑任意命令。

```bash
sudo -l
# 例如： (root) NOPASSWD: /usr/bin/vim
# 这条等于 root：vim 里 :!sh 就出来了
```

所以看到 `sudo -l` 的输出，判的不是"他能不能提权"，而是"**这些命令里哪一个能逃逸**"。这条判断在 Linux 侧的地位，相当于 Windows 侧的"服务路径可写"。

另一个容易漏的点：`sudo` 之后**没有新登录**（M1 讲过），所以 `last` 看不到，但 `auth.log` 会记一条 `sudo:` 行。找"谁提的权"，Windows 看 4672 与登录类型，Linux 看 `auth.log` 的 sudo 行。

## 4. 动手验证（两边各 15 分钟）

```cmd
:: ① 看自己当前的完整性级别与组标记
whoami /groups | findstr /i "Mandatory Label"
whoami /groups | findstr /i "Administrators"

:: ② 同一个操作，分别在普通 cmd 和管理员 cmd 里试
type C:\Windows\System32\drivers\etc\hosts >nul && echo READ_OK
echo test >> C:\Windows\System32\drivers\etc\hosts

:: ③ 看目标对象的 ACL 与所有者
icacls C:\Windows\System32\drivers\etc\hosts
```

**要亲眼看到的**：普通 cmd 里写 `hosts` 失败，管理员 cmd 里成功；而 `icacls` 显示 `BUILTIN\Administrators:(F)`。

然后回答自己一个问题：**失败的原因是 IL，还是 deny-only？**（提示：看 `icacls` 里 `Users` 给了什么，再看自己过滤令牌里 Administrators 的状态）

Linux 侧（**不要真的去试 `su`**，看配置就够）：

```bash
# ① 我能以 root 身份跑哪些命令
sudo -l

# ② 逐条问：这个程序能不能起 shell / 读写任意文件？
#    vim、less、find、awk、python、tar…… 几乎都能
#    对照 GTFOBins 的清单确认

# ③ 为什么 su 需要 root 密码：看 shadow 的权限
ls -l /etc/shadow

# ④ 有没有 SUID 与 capability 文件（M2 已看过，这里当"提权面"复核）
find / -perm -4000 -type f 2>/dev/null | head -10
```

**要亲眼看到的**：`sudo -l` 里那些"限定命令"，没有一条是真的受限——只要程序能起 shell，就是 root。

## 5. 为什么这样设计

**为什么不干脆让管理员一直以高权限运行？**

因为那等于所有程序（包括你随手点开的陌生 exe）都拿到管理员权限。UAC 的思路是：**默认低权限，需要时再升**，把"提权"变成一个需要显式动作的事件。

**代价：**

- 大量老程序假设自己有管理员权限，在 Medium 下静默失败，用户只看到"没反应"
- 两枚令牌造成判断混乱——`whoami /priv`、`icacls`、`net session` 在不同令牌下答案不同
- IL 与 DACL 两套检查叠在一起，出错时难以归因（这个单元就是为解决它写的）
