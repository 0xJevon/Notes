## 1. 这个单元要回答什么

**系统在判断"你能不能做这件事"的时候，认的是什么？**

直觉答案是"用户名"。错。两边都不认名字，只认数字：

|         | 认什么                          | 名字是什么                              |
| ------- | ---------------------------- | ---------------------------------- |
| Windows | **SID**（`S-1-5-21-...-1001`） | 显示层的翻译                             |
| Linux   | **uid / gid**（`1000`、`0`）    | 由 NSS（`/etc/passwd`、LDAP、SSSD）翻译出来 |

这一条不通，后面全部悬空：ACL 里写的是 SID 或 uid、令牌或 cred 里装的是它们、日志里记的也是它们。你看到 `icacls` 输出一串 `S-1-5-21-...`、看到 `/etc/passwd` 里两个数字，不是显示有问题，是它本来就只有这个。

## 2. 核心机制

### 2.1 SID 的构成

```text
S-1-5-21-3623811015-3361044348-30300820-1013
│ │ │  └────────── 机器/域标识（96 位）──────────┘ └RID┘
│ │ └ 5 = SECURITY_NT_AUTHORITY
│ └ 1 = 版本号，永远是 1
└ S = 字符串形式前缀
```

最后一段是 **RID**（Relative ID）。前 96 位标识"这是哪台机器/哪个域发的身份"，RID 标识"这个域里的第几个账户"。

由此直接推出三个能用来判断的事实：

| 事实                            | 推论                                          |
| ----------------------------- | ------------------------------------------- |
| 本地账户的 SID 前缀来自**这台机器**的机器 SID | 两台机器上同名的 `test`，SID 不同 → A 机的授权搬到 B 机**无效** |
| 域账户的 SID 前缀来自**域**            | 同一个域里，一个域账户在任何成员机上 SID 都一样 → 授权可以跨机器生效      |
| RID 是分配顺序，不是名字                | 改名不影响 SID → 权限照旧                            |

### 2.2 内置账户的 RID 是写死的

| 账户              | RID     | 说明                                    |
| --------------- | ------- | ------------------------------------- |
| `Administrator` | **500** | 不管改成什么名字，RID 都是 500。识别内置管理员看 RID，不看名字 |
| `Guest`         | 501     | 默认禁用                                  |
| 第一个普通用户         | 1000 起  | 之后依次递增                                |

这就是"改名藏管理员"这类手法为什么没用：**防守方看 RID 500，不看名字。**

### 2.3 知名 SID：不依赖任何账户存在

有些 SID 不对应具体账户，是系统预定义的"身份类别"。它们在每台机器上都一样，这是你判断"这个东西谁能碰"的常用依据：

| SID                | 名字                                  | 什么时候出现                   |
| ------------------ | ----------------------------------- | ------------------------ |
| `S-1-5-18`         | `NT AUTHORITY\SYSTEM`               | 系统自身。不是"一个账户"，是操作系统的身份   |
| `S-1-5-19` / `-20` | `LOCAL SERVICE` / `NETWORK SERVICE` | 内置服务账户                   |
| `S-1-5-32-544`     | `BUILTIN\Administrators`            | 本地管理员组                   |
| `S-1-5-32-545`     | `BUILTIN\Users`                     | 普通用户组                    |
| `S-1-5-11`         | `Authenticated Users`               | **任何通过认证的身份**，包括域用户、服务账户 |
| `S-1-5-7`          | `ANONYMOUS LOGON`                   | 匿名                       |

`Authenticated Users` 是最常被误读的一个：它包含的远不止"这台机器的用户"，**域里任何一个通过认证的账户都算**。看到某个目录写着 `Authenticated Users:(F)`，意味着域内任何一台机器上的任何域用户都能写——这是提权面，不是"配置略松"。

### 2.4 组是授权用的批量手段

组本身也是一个安全主体（有 SID），加进组等于一次性获得一批授权。所以"这个人为什么有这个权限"经常要往上追两层：他在哪个组，那个组又在哪个组里。

### 2.5 Linux 侧：uid、gid 与附加组

Linux 用同一套思路，但存储和来源完全不同。

**uid 是一个 32 位整数，`0` 就是 root。** 用户名不在内核里，是用户态查出来的：

```text
/etc/passwd 一行七个字段：
  alice : x : 1000 : 1000 : Alice : /home/alice : /bin/bash
  用户名 密码 uid   gid   注释    家目录       登录 shell
```

内核只认 `1000`。`ls` 显示 `alice` 是它替你查了 NSS（`/etc/passwd`、LDAP、SSSD）。所以 `ls -n` 能直接看到数字——**和 `icacls` 显示 SID 是同一件事**。

| 概念   | Windows                     | Linux                        |
| ---- | --------------------------- | ---------------------------- |
| 主体标识 | SID                         | uid                          |
| 主组   | 令牌里的组 SID 列表                | gid（`/etc/passwd` 第 4 列）     |
| 附加组  | 同上，全部装进令牌                   | `/etc/group` 里把你列进去，`id` 能看到 |
| 最高身份 | `SYSTEM`（S-1-5-18），**不是账户** | `root`（uid 0），**就是一个账户**     |
| 名字来源 | 安全账户管理器 / 域控                | NSS（文件、LDAP、SSSD 都可）         |

最后一行那个差异比看起来重要：**Windows 的 SYSTEM 是"系统的身份"，没有密码、不能登录；Linux 的 root 是一个正常账户，有密码、能登录、能被 `su` 切换。** 这决定了"拿到最高权限"在两边意味着不同的东西。

另一个差异：**Linux 没有"机器标识"**。所以不存在"拷到另一台机器权限失效"这回事——但也因此，**跨机共享靠 uid 数字对齐**，两台机器上同名不同 uid 会直接导致文件归属错乱（NFS 场景常见）。这是 Windows SID 机制想解决、而 Linux 留给运维解决的那类问题。

## 4. 动手验证（**第 1 步：先跑这个**，Windows 10 分钟）

```cmd
:: 看自己的 SID，注意最后一段 RID
whoami /user

:: 看自己所在的组，每个组都是一个 SID
whoami /groups

:: 列出所有本地账户及其 SID，认出 RID 500
wmic useraccount get name,sid
```

然后在 3 组权限的目录上做一次改名实验：

```cmd
:: 新建账号、给它一个目录的权限、再改名，看 ACL 变不变
net user test P@ssw0rd /add
mkdir C:\sidtest
icacls C:\sidtest /grant test:(OI)(CI)M
icacls C:\sidtest
ren C:\sidtest sidtest2
icacls C:\sidtest2
```

**要亲眼看到的**：改名之后 `icacls` 里显示的**名字跟着变了，但 SID 一点没动**。这就是"权限绑 SID，不绑名字"的直接证据。

Linux 侧（10 分钟）：

```bash
# ① 看自己的数字身份
id
# 输出里有 uid=、gid=、groups= —— 最后那个是附加组

# ② 让 ls 显示数字而不是名字，对应 icacls 显示 SID
ls -n /etc/shadow
touch /tmp/idtest && ls -n /tmp/idtest

# ③ 反查：数字到名字的转换发生在用户态
getent passwd 1000
getent group 0

# ④ 改用户名，看文件归属变不变（需要 root）
sudo usermod -l newname oldname
ls -n /home/
```

**要亲眼看到的**：`ls -n` 显示的是数字；改用户名之后，文件的 uid **没变**、显示的名字变了。和 Windows 那一侧是同一个结论。

如果不想改真实账号，用 `stat -c '%u %U' 文件名` 看 uid 与名字的对应即可，不冒险。

## 5. 为什么这样设计

**为什么不直接用用户名？**

因为名字会变、会重名、会跨机器重复。用 SID 换来三条：改名不影响授权、同名不等于同一主体、权限可以精确到"哪个域里的第几个账户"。

**代价是什么？**

- 读起来不直观——所以工具要帮你把 SID 翻译成名字，翻译不了就显示成 `S-1-5-21-...`
- 授权不能跨机器照搬，运维上很麻烦（这就是为什么域环境存在）
- **机器克隆会出问题**：复制一台机器时如果机器 SID 没重写，两台机器的同名本地账户 SID 相同——权限体系会认错人
