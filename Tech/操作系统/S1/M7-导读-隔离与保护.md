# M7 隔离与保护

> 归属：[[Tech/操作系统/00-学习地图]] ｜ 答题：[[M7-问答]] ｜ 上一单元：M6 服务与守护进程 ｜ 下一单元：[[M8-导读-日志与审计]]

## 1. 这个单元要回答什么

**权限都对，为什么还是被拒？**

M4 讲的 DACL/mode 是"第一层门"。这一单元讲第二、第三层——它们在权限检查**之后**生效，所以现场表现为"我明明有权限"。

| 层 | 它管什么 | 你看到的 |
|---|---|---|
| 访问控制（M4） | 你能不能碰这个对象 | `Access is denied` / `Permission denied` |
| **完整性 / MAC** | 你的"可信度"够不够 | 同样的拒绝，但 ACL 看着没问题 |
| **隔离边界** | 你根本不在同一个"世界"里 | 看不到进程、连不上端口、文件不存在 |

## 2. 核心机制

### 2.1 Windows：三样东西

| 机制 | 管什么 | 怎么确认 |
|---|---|---|
| **完整性级别（IL）** | 写操作要求主体 IL ≥ 对象 IL（`no-write-up`） | `whoami /all` 的 Mandatory Label；Process Explorer 的 Integrity 列 |
| **PPL（保护级别）** | 特定进程不允许被非保护进程打开，即使有 `SeDebug` | lsass 属性里的 Protection 项；`RunAsPPL` 注册表值 |
| **Credential Guard / VBS** | 把凭据放进虚拟化隔离区，SYSTEM 也读不到真实内容 | `msinfo32` 的"基于虚拟化的安全性"；`Get-CimInstance Win32_DeviceGuard` |
| AppContainer | 应用沙箱，只有显式授予的能力 | 进程的 AppContainer SID |

关键判断：**PPL 挡住的是"打开"这个动作**，所以报错和"没有权限"完全一样；Credential Guard 不挡打开，**挡的是内容**（读到的是空壳）。这两种失败在日志里几乎无法区分，只能看配置。

### 2.2 Linux：四样东西

| 机制 | 管什么 | 怎么确认 |
|---|---|---|
| **namespace** | 进程能看到哪些资源（pid/net/mnt/user/uts/ipc） | `ls -l /proc/$$/ns`；容器内 `ps` 只看到自己的进程 |
| **cgroup** | 能用多少资源 | `cat /proc/self/cgroup` |
| **seccomp** | 能调哪些系统调用 | `grep Seccomp /proc/self/status` |
| **SELinux / AppArmor** | 强制访问控制（MAC），在 mode bits **之后**再判一次 | `getenforce`、`ls -Z`、`dmesg | grep -i avc` |

两条判据：

1. **SELinux 的拒绝看起来像权限问题，但 `ls -l` 完全正常。** 唯一的确证是 `dmesg` 或 `audit.log` 里的 `AVC denied` 行，以及 `ls -Z` 里的 context
2. **namespace 造成的不是"拒绝"，是"看不见"**。进程不存在、端口没监听、文件不存在——这三件事在容器里经常是 namespace 而不是故障

### 2.3 两边的对应关系

| 要防的事 | Windows | Linux |
|---|---|---|
| 低可信进程改高可信对象 | IL（`no-write-up`） | SELinux/AppArmor 的类型强制 |
| 高权限也读不到敏感进程 | PPL、Credential Guard | `ptrace_scope` + MAC、独立 namespace |
| 应用沙箱 | AppContainer、Job Object | namespace + seccomp + cgroup |
| "看不见"而非"被拒绝" | 会话/窗口站隔离 | **namespace**（Linux 特有，Windows 没有等价物） |

**最后一行是不能迁移的地方**：Linux 的 namespace 让"看不见"成为一等机制，Windows 没有完全对应的东西（最接近的是会话隔离与 AppContainer）。所以容器里的"进程不见了"，用 Windows 经验完全推不出来。

### 2.4 归因顺序（本单元出口）

遇到"有权限却被拒"，按这个顺序查，别跳步：

```text
1. 身份对不对        → whoami /all ｜ id
2. ACL 放不放行      → icacls ｜ getfacl、ls -l
3. 完整性/保护层      → Mandatory Label、PPL ｜ getenforce、ls -Z、dmesg AVC
4. 隔离边界          → 是不是根本没在同一个 namespace / 会话里
5. 属性与挂载        → 只读挂载、chattr +i、文件被占用
```

第 4 步是最容易被跳过的一步，也是容器环境下最常见的真正原因。

## 4. 动手验证（两边各 15 分钟）

Windows：

```powershell
whoami /all | findstr /i "Mandatory"
# 看 lsass 的保护级别（需要管理员）
Get-Process lsass | Select-Object Name, Id
# VBS / Credential Guard 状态
Get-CimInstance -ClassName Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard |
  Select-Object SecurityServicesRunning, VirtualizationBasedSecurityStatus
```

Linux：

```bash
# ① 我在不在容器里、有哪些 namespace
ls -l /proc/$$/ns
cat /proc/1/cgroup
grep Seccomp /proc/self/status

# ② MAC 状态
getenforce 2>/dev/null || aa-status 2>/dev/null | head

# ③ 一个"看不见"的实验：新建 pid namespace
sudo unshare --pid --fork --mount-proc ps aux | head
# 对比：普通 ps aux 能看到一堆进程

# ④ SELinux 拒绝长什么样（如果有）
sudo dmesg | grep -i avc | tail -5
```

**要亲眼看到的**：③ 里在 namespace 内 `ps` 只能看到自己——**这不是权限拒绝，是世界变小了**。这个体验用 Windows 经验得不到。

## 5. 为什么这样设计

**为什么 ACL 之后还要再加一层？**

因为 ACL 是"对象所有者自己决定"的，而所有者可能是错的、可能被社工、可能是配置疏忽。MAC 与保护机制是**系统级的、所有者改不了的**兜底。

代价很实在：多一层就多一个排查环节，而且这一层的报错和权限问题几乎无法区分。这也是为什么"照着手册排查"经常卡住——手册默认你在第一层。
