# M8 日志与审计

> 归属：[[Tech/操作系统/00-学习地图]] ｜ 答题：[[M8-问答]] ｜ 上一单元：[[M7-导读-隔离与保护]]

## 1. 这个单元要回答什么

前五个单元讲的是"**能做什么**"。这个单元讲"**做了会留下什么**"。

两者是同一件事的两面：同一批主体（SID/令牌）、同一批对象（进程、服务、文件）、同一套检查。区别只在于——一次动作是被允许了，还是被记下来了。

你每天看告警，但可能从没问过：**这条告警是由哪一句系统行为产生的？** 答不出这一句，就只能在告警表面打转。

## 2. 核心机制

### 2.1 先分清三种"日志"

它们产生机制完全不同，混在一起会判错：

| 层          | 谁产生          | 例子                                 | 回答什么问题        |
| ---------- | ------------ | ---------------------------------- | ------------- |
| **系统安全日志** | 操作系统内核与安全子系统 | Windows Security EVTX、Linux auditd | 谁在什么时候做了什么    |
| **应用日志**   | 服务/中间件自己     | IIS、Nginx、Tomcat、MySQL 日志          | 这个请求长什么样      |
| **安全设备日志** | 防火墙、EDR、WAF  | NGFW 会话日志、EDR 告警                   | 有没有被拦、命中了哪条规则 |

**你现在看的最多的是第三层，最缺的是第一层。** 第三层告诉你"有人被拦了"，第一层才能告诉你"他到底做了什么、有没有成功"。

### 2.2 有没有日志，取决于三件事

不要假设"系统会记下来"。三件事任何一件不成立，你什么都看不到：

| 条件         | 说明                    | 现场怎么确认                      |
| ---------- | --------------------- | --------------------------- |
| **审计策略开着** | 很多类别默认不审计（对象访问、命令行记录） | `auditpol /get /category:*` |
| **日志没被覆盖** | 默认日志大小有限，滚动很快         | 事件查看器的日志属性                  |
| **有人集中采集** | 本机日志，管理员随时能清          | 问运维有没有转发到 SIEM              |

第三条是判断攻击痕迹时的前提：**没有集中采集，本机日志的可信度只到"最后一次被清空"为止。**

### 2.3 Windows 上真正要看的事件

按"它回答了什么问题"分组，不按编号背：

| 问题 | 事件 | 在哪 | 关键字段 |
|---|---|---|---|
| 谁登录了、怎么登的 | **4624** | Security | **LogonType**（2 本地/3 网络/10 RDP）、TargetUserName、IpAddress |
| 登录失败 | 4625 | Security | 失败原因、来源 IP |
| 谁拿到了高权限 | **4672** | Security | 分配的特殊特权列表——管理员登录就会出现 |
| 谁运行了什么 | **4688** | Security | NewProcessName、**CommandLine**、ParentProcessId |
| 谁装了服务 | **7045** | **System**（不是 Security） | ServiceName、ImagePath、ServiceType |
| 谁动了账号 | 4720 建号 / 4728、4732 加组 | Security | 目标账号、操作者 |
| 域内认证 | 4768/4769 | 域控 Security | TGT/TGS 请求，Kerberoast 会在这里露头 |
| 日志被清 | **1102** | Security | 谁清的 |

两个最常被忽略的点：

1. **4688 的 `CommandLine` 默认是空的**——要在"审核进程创建"之外，另开"在进程创建事件中包含命令行"这一项。看到 4688 有记录但命令行空白，说明这项没开，等于少了一半信息。
2. **7045 在 System 日志**。很多人只查 Security，漏掉服务安装这条最直接的持久化证据。

### 2.4 Sysmon：补上系统日志不记的东西

系统日志不记"进程连了哪个 IP"、"创建了哪个远程线程"。Sysmon 补这些，四个事件够用：

| 事件  | 记什么                     | 用来判什么                                |
| --- | ----------------------- | ------------------------------------ |
| 1   | 进程创建（含**父进程**、hash、命令行） | 异常父子链：`winword.exe → powershell.exe` |
| 3   | 网络连接                    | 进程外联到哪、哪个进程在扫内网                      |
| 11  | 文件创建                    | 落地文件、释放的 payload                     |
| 13  | 注册表写入                   | 持久化（Run 键、服务、COM 劫持）                 |

外加事件 8（CreateRemoteThread）——注入的最直接痕迹。

### 2.5 Linux 侧：auditd 与 syslog

| 要判什么      | 看哪                                                          |
| --------- | ----------------------------------------------------------- |
| 谁执行了什么命令  | `auditd` 的 `execve` 审计；没配 auditd 就只剩 `~/.bash_history`（可被清） |
| 谁登录成功/失败  | `/var/log/auth.log`（Debian 系）或 `/var/log/secure`（RHEL 系）    |
| 谁登录过、从哪来  | `last`（wtmp）、`lastb`（失败）、`who`                              |
| 提权动作      | `auth.log` 里的 `sudo:` 行                                     |
| 服务/定时任务变更 | `journalctl -u`、cron 日志                                     |

```bash
# 有没有审计规则？空的就等于"谁执行了什么"根本查不到
auditctl -l
# 加一条：记录对 /etc/passwd 的写与属性变更
auditctl -w /etc/passwd -p wa -k passwd_change

# journald 是不是易失的（只存内存，重启就没了）
grep -E '^Storage' /etc/systemd/journald.conf
```

**三条与 Windows 的实质差异**：

1. **Linux 默认几乎没有审计**。`auditctl -l` 是空的，就说明只有 syslog 的登录记录，进程执行完全查不到；Windows 至少有 4688（哪怕命令行为空）
2. **root 改日志不留专门事件**。Windows 清日志有 1102，Linux 删 `auth.log` 没有任何内置告警——只能靠远程 syslog 发现"这个时间点之后没数据了"
3. **journald 可能只在内存里**（`Storage=volatile` 或 `/run` 下），重启即丢。这是容器与云主机上最常见的"日志消失"原因，不是被人删了

所以判断 Linux 主机的痕迹，第一个问题永远是：**有没有远程 syslog / 集中采集？** 没有的话，本机日志的可信度只到"最后一次被人动过"为止。

### 2.6 这条判断的边界

攻击者拿到管理员/SYSTEM 之后，本机日志就不可信了——他能清（1102 只是"被记录下来的清空"，还有不记录的清法）、能改、能停服务。

所以完整的判断链是：

```text
本机日志（可被污染）
  + 集中采集（攻击者通常碰不到）
  + 网络侧日志（防火墙/流量，另一台设备）
  = 才谈得上"痕迹"
```

只有本机日志时，你能说的是"**在这个时间点之后没有记录**"，不能说"**没有发生过**"。

## 4. 动手验证（20 分钟）

```powershell
# ① 看审计策略开了什么
auditpol /get /category:*

# ② 看最近的成功登录，注意 LogonType
Get-WinEvent -FilterHashtable @{LogName='Security';Id=4624} -MaxEvents 20 |
  Select-Object TimeCreated, @{n='Type';e={$_.Properties[8].Value}}, @{n='User';e={$_.Properties[5].Value}}

# ③ 看进程创建事件里有没有命令行
Get-WinEvent -FilterHashtable @{LogName='Security';Id=4688} -MaxEvents 5 |
  Select-Object TimeCreated, @{n='Cmd';e={$_.Properties[8].Value}}

# ④ 服务安装事件（注意是 System 日志）
Get-WinEvent -FilterHashtable @{LogName='System';Id=7045} -MaxEvents 5
```

**要亲眼看到的**：4624 的 LogonType 分布（你日常远程管理是不是全是 3 和 10），以及 4688 的命令行字段是空的还是有的。

Linux 侧（如果有）：

```bash
id; cat /proc/self/status | grep Cap
sudo -l
last -n 5; lastb -n 5
auditctl -l 2>/dev/null | head
```

## 5. 为什么这样设计

**为什么不全记下来？**

因为记日志很贵：磁盘、IO、还有"记下来的东西本身是敏感数据"。所以设计上是"按类别选择性审计"，默认只记最关键的（登录、账号变更），细节（对象访问、命令行）要手动开。

**代价：**

- 默认配置下，很多有用的东西根本没记——你查不到不等于没发生
- 日志要轮转，高频事件（4688 在服务器上每天几万条）会迅速冲掉历史
- 日志本身是攻击目标：清日志是最常见的反取证动作之一

## 6. 伏笔

- 一条 4688 只有进程名、没有命令行，你能推出什么？（答完这题，你就知道为什么"日志不全"比"没日志"更容易误判）
- 攻击者用 `wevtutil cl Security` 清了日志，你会看到什么？如果他不用这个命令呢？
- 你现在手上的防火墙告警，对应到本单元哪一类日志？能不能反推出主机侧的行为？
