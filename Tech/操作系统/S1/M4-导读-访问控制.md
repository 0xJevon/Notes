# M4 访问控制：DACL 与 mode/ACL

> 归属：[[../00-学习地图]] ｜ 答题：[[M4-问答]] ｜ 上一单元：[[M3-导读-提权与身份切换]]

## 1. 这个单元要回答什么

一条 `Access is denied`，**到底是谁挡的？**

这是本线唯一的验收主轴。答"权限不够"等于没答——那只是把现象换了个说法。要能指到：哪个 SID、哪条 ACE、还是根本不是 DACL 的事。

## 2. 核心机制

### 2.1 求值过程

```text
① 你要一个访问权（比如 FILE_WRITE_DATA）
② 系统取你令牌里的 SID 列表（用户 + 所有组）
③ 按顺序遍历对象的 DACL，逐条 ACE 比对
④ 遇到 Deny 命中 → 立即拒绝，后面的不看
⑤ 遇到 Allow 命中 → 把这一位记成"已授予"，继续看后面的
⑥ 全部看完，请求的每一位都授予了才算通过
⑦ 一条都没命中 → 拒绝（默认拒）
```

第 ⑦ 步是最容易漏的一条：**没有允许就是拒绝**，不需要有人显式拒绝你。所以排查时"ACL 里没写你"和"ACL 里明确写了拒绝你"是两种不同的结论，但现象一样。

### 2.2 顺序不是随意的

Windows 在写入 ACE 时自己维护顺序：

```text
显式 Deny  →  显式 Allow  →  继承的 Deny  →  继承的 Allow
```

这就是"拒绝优先"的实现方式——不是求值时特殊照顾 Deny，是**把 Deny 排到了前面**。

理解这一点能解释一个常见困惑：为什么在父目录加了一条 Allow，子文件的拒绝还在？因为父目录的 Allow 属于"继承的 Allow"，排在子文件自己的显式 Deny 后面。

### 2.3 NULL DACL 与空 DACL（必须分清）

| 情况 | 含义 | 谁能访问 |
|---|---|---|
| **没有 DACL**（NULL DACL） | 不做任何检查 | **所有人，全权** |
| **有 DACL 但没有 ACE**（空 DACL） | 检查了，但一条规则都没有 | **所有人，拒绝** |

一个字符的差别，结论完全相反。这是真实配置错误的高发点：某些工具"清空权限"的操作实际写入的是 NULL DACL，本意是"收紧"，结果变成了"对所有人开放"。

判断方法：`icacls` 对一个 NULL DACL 的对象会显示非常干净、没有任何条目，但谁都能写——**看到"没有任何权限条目但能写"，就要警觉。**

### 2.4 所有者为什么总能进来

对象的所有者隐含两项权利：`READ_CONTROL`（读 ACL）和 `WRITE_DAC`（改 ACL）。

所以所有者的路径不是"绕过 ACL"，而是：**先改 ACL 给自己授权，再正常访问。** 这条在提权里很常见——拿到所有权（`takeown`）剩下的就好办了。

### 2.5 Linux 侧：mode bits 是"命中即停"

Linux 的基础权限只有 9 位，分三组：

```text
-rwxr-x---   alice  staff   file
 │└┬┘└┬┘└┬┘
 │ │  │  └ other
 │ │  └ group
 │ └ owner
 └ 类型（- 文件 / d 目录 / l 链接）
```

**求值规则和 Windows 完全不同，这是本单元最重要的一条**：

```text
if 我的 euid == 文件属主        → 只用 owner 那三位，**不再看 group / other**
else if 我的任一 gid == 文件组  → 只用 group 那三位，不再看 other
else                            → 用 other 那三位
命中即停，不累加
```

对比一下：

| | Windows | Linux |
|---|---|---|
| 匹配范围 | 令牌里**所有** SID 的 ACE 累加 | **只命中一次**，命中即停 |
| 谁优先 | 拒绝优先（Deny 排在前面） | 身份优先（owner > group > other） |
| 结论 | 多个组的权限会叠加 | 只有一个组的那三位生效 |

后果很实际：**文件属主如果是 root、属主位是 `---`，那么即使你在拥有权限的组里，你也会被拒**——因为你是"非属主"，才轮到 group 位；但如果你是属主且属主位没权限，就到此为止，没有 fallback。

由此产生几个高频误判：

| 现象 | 真正原因 |
|---|---|
| "我明明在组里，还是读不了" | 你是文件属主，走的是 owner 位 |
| "目录有 r 却进不去" | 目录需要 **x** 才能进入/遍历，r 只让你列名字 |
| "权限看着够，还是写不进" | 挂载点只读、`chattr +i`（不可变属性）、或 SELinux/AppArmor 拦了 |
| "文件删不掉，但我对文件有 w" | 删除看的是**目录**的 w 位，不是文件的 |

另外三样要认识：

- **umask**：新建文件默认 `0666 & ~umask`，目录 `0777 & ~umask`。umask 022 → 文件 644、目录 755
- **POSIX ACL**：`getfacl` / `setfacl`，能给单个用户/组授权，这一步才接近 Windows 的细粒度 ACE
- **特殊位**：SUID（M2 讲过）、SGID（目录上=新建文件继承组）、sticky（`/tmp` 的 `t`，限制只能删自己的）

### 2.6 归因表（两边合并）

| 类别 | Windows 怎么确认 | Linux 怎么确认 |
|---|---|---|
| ACL 拒绝 | `icacls` 里的 `(DENY)` 或无匹配 | `getfacl` / `ls -l` 三位都不够 |
| 身份上下文不完整 | Administrators 带 `deny-only` | euid 不是你以的身份（`id` 看） |
| 完整性/保护层 | Mandatory Label、PPL | SELinux `ls -Z`、AppArmor、`dmesg` 里的 AVC |
| 属性/所有权 | 只读属性、所有者 | `chattr +i`、挂载只读、你是属主但 owner 位为 0 |

## 4. 动手验证（两边各 15 分钟）

```cmd
:: ① 造一个目录，配一条 Deny，看它排在谁前面
mkdir C:\acltest
icacls C:\acltest /grant %USERNAME%:(OI)(CI)F
icacls C:\acltest /deny  %USERNAME%:(CI)(W)
icacls C:\acltest
:: 试着在里面建文件，看是不是被拒

:: ② 看有效权限（不是 ACL，而是算完之后你能干什么）
accesschk -l -d C:\acltest

:: ③ 看所有者
icacls C:\acltest | findstr /i "owner"
```

**要亲眼看到的**：`icacls` 输出里 `(DENY)` 那条排在 Allow 前面；以及你自己的显式 Deny 覆盖了同一条 Allow。

做完把目录删掉（`icacls C:\acltest /reset` 再删），别留在机器上。

Linux 侧（这一段是本单元的重点实验）：

```bash
# ① 证明"命中即停"：属主位是 ---，但组位有读权限，你仍然是属主
sudo touch /tmp/m4test
sudo chown "$USER:$(id -gn)" /tmp/m4test
sudo chmod 040 /tmp/m4test          # owner --- , group r-- , other ---
cat /tmp/m4test                      # 被拒！因为你是属主，走属主位，不 fallback 到组

# ② 目录的 r 与 x 不是一回事
mkdir /tmp/m4dir && chmod 600 /tmp/m4dir
ls /tmp/m4dir                        # 有 r：能列名字
cd /tmp/m4dir                        # 无 x：进不去

# ③ 特殊位与不可变属性
ls -ld /tmp                          # 最后的 t 是 sticky
sudo chattr +i /tmp/m4test
rm -f /tmp/m4test                    # 连 root 都删不掉
sudo chattr -i /tmp/m4test && sudo rm -f /tmp/m4test

# ④ 用 ACL 做一次"细粒度授权"（这一步才接近 Windows 的 ACE）
setfacl -m u:nobody:r /tmp/m4test 2>/dev/null; getfacl /tmp/m4test 2>/dev/null
```

**要亲眼看到的**：① 里明明是"组员有读权限"却读不了——这就是"命中即停、不累加"。这一条和 Windows 的"所有组累加"正好相反，也是两边最容易互相套错的地方。

## 5. 为什么这样设计

**为什么拒绝优先，而不是允许优先？**

因为安全策略的默认姿态应该是"关"。允许优先意味着：任何一条漏配或少配，都会变成开放。拒绝优先保证"只要有人说不行，就是不行"——代价是配错一条 Deny 会让整个目录锁死，而且很难查（因为你看不到"谁给的允许"，只能看到"谁给的拒绝"）。

**代价：**

- 继承关系复杂，改父目录影响面大，运维上容易出事
- 同一个结果可能由四种原因造成，归因成本高（这就是本单元存在的理由）
- 权限是静态的，而业务是动态的——权限漂移几乎不可避免
