# M1 认证与凭证上下文：令牌与 cred

> 归属：[[Tech/操作系统/00-学习地图]] ｜ 答题：[[M1-问答]] ｜ 上一单元：[[M0-导读-主体标识]]

## 1. 这个单元要回答什么

你输入密码按下回车，系统内部发生了什么？为什么同一个账号，会有**两个不同的令牌**？

先给结论，再看它怎么来的：

> **令牌是这个账号"这一次登录"的一次性凭证，不是账号的属性。**

同一账号不同时间、不同方式登录，拿到的令牌可以不一样。这一条是后面所有判断的地基。

## 2. 核心机制

### 2.1 登录的三步

```text
① 凭据交给 LSA（本地安全认证子系统）
        ↓
② LSA 验证：本地账户查 SAM，域账户问域控
        ↓
③ 验证通过 → 建一个「登录会话」→ 签发一枚「访问令牌」
```

令牌里装的是一份快照：

| 装什么 | 用途 |
|---|---|
| 用户 SID | 我是谁 |
| **组 SID 列表** | 我还在哪些组里（决定批量授权） |
| **特权列表** | 我能绕过哪些检查（M2） |
| **完整性级别** | 我的"可信度"有多高（M3） |
| 登录会话 ID | 这一批令牌属于同一次登录 |

**关键点**：令牌是快照。登录之后你被加进一个组，**当前令牌不会更新**，要重新登录才生效。反过来，你被踢出一个组，旧令牌里的组还在，直到重新登录——这条在应急响应里经常被忽略。

### 2.2 登录类型：为什么"登进去了"可能是假的

| 类型 | 名称 | 典型场景 | 有没有本地会话 |
|---|---|---|---|
| 2 | 交互式 | 在键盘前登录 | **有** |
| 3 | 网络 | 访问共享、SMB、大多数横向 | **没有** |
| 10 | 远程交互 | RDP | **有** |
| 5 | 服务 | 服务启动 | 有（服务专用） |
| 4 | 批处理 | 计划任务 | 有 |

`type 3` 是最容易误判的一格：**目标机上没有你的桌面会话，只有一次"认证通过"的记录。** 这就是为什么"我明明登上去了，为什么 `query user` 看不到我"——你根本没登录，你只是被验证了一次。

**这一格还是 Pass-the-Hash 成立的根源**：网络登录时，你的密码不会离开本机，目标机收到的是**用密码哈希算出的认证数据**。既然认证只依赖哈希，那么手里有哈希就等于有密码——不需要破解。

### 2.3 主令牌与模拟令牌

- **主令牌**：进程的身份。一个进程启动时绑定一枚主令牌，进程里所有线程默认用它。
- **模拟令牌**：线程级的"临时借用别人身份"。服务端处理客户端请求时，可以临时"变成"客户端去访问资源——这就是模拟。

为什么要有它：一个以 SYSTEM 运行的服务，需要**以访问者本人的身份**去读文件，否则所有人都能通过这个服务读到本无权读的东西。模拟是让服务"按来访者的权限办事"的机制。

**它也是提权的入口**：如果你能让一个持有 `SeImpersonatePrivilege` 的服务去模拟一个你控制的"客户端"，你就借到了它的身份。这条在 M2、M5 回收。

### 2.4 UAC 做的事：一次登录，两枚令牌

管理员组的成员登录时，LSA 会签发**两枚**令牌：

| 令牌 | 完整性级别 | 组成员状态 | 什么时候用 |
|---|---|---|---|
| 过滤令牌（filtered） | Medium | `Administrators` 被标成 **deny-only** | 默认，双击运行的程序 |
| 完整令牌（full） | High | 正常 | 你点了"以管理员身份运行"，并确认了 UAC |

所以"我是管理员"和"我现在有管理员权限"是两件事——**中间隔着一次令牌切换**。

这也解释了一个常见现象：程序启动时会弹 UAC，有些又不弹。弹不弹由程序的 manifest 决定（`requestedExecutionLevel`），不是由你的组身份决定。

### 2.5 Linux 侧：PAM 与 cred

Linux 没有和"令牌"完全对应的对象，对应的是进程的 `cred` 结构：

| 字段 | 含义 | 谁用它 |
|---|---|---|
| `uid` / `gid` | 真实身份（你到底是谁） | 记账、信号权限 |
| `euid` / `egid` | **有效身份**，绝大多数权限检查用它 | 访问检查 |
| `suid` / `sgid` | 保存的身份，用来切回去 | setuid 程序 |
| `fsuid` / `fsgid` | 文件访问专用 | 文件系统检查 |

```bash
cat /proc/self/status | grep -E '^Uid|^Gid'
# Uid:  1000  1000  1000  1000     ← real  effective  saved  fs
```

**最大的差异在这里**：Windows 的令牌是"签发后基本不变"的快照；Linux 的 cred 是**进程可以主动改的**——一次 `setuid()` 系统调用就能换，只要有权限。所以 Linux 的提权脚本常常"改完自己的 euid 继续跑"，Windows 的通常是"起一个新进程"。这个差异会贯穿到 M3、M5。

认证由 **PAM** 负责（`/etc/pam.d/`）。它是一条模块链：`pam_unix` 验密码、`pam_env` 设环境、`pam_limits` 设资源限制。

反直觉的一点：`su` / `sudo` 之后，**进程换了 euid，但没有"重新登录"**。`last` 里还是原来的登录记录，`whoami` 却变了。Windows 的 RDP 是"新登录"，Linux 的 `su` 不是——找"谁提的权"时，两边要查的地方不一样（M8 回收）。

## 4. 动手验证（两边各 15 分钟）

```powershell
# ① 看当前令牌里装了什么（普通 PowerShell 与终端(管理员)各跑一次，两次输出留着对比）
whoami /all

# ② 快照实验：加组之后不重新登录，看令牌变不变
net localgroup "Remote Desktop Users" $env:USERNAME /add
whoami /groups | Select-String 'Remote Desktop'   # 无输出 → 令牌没变
# 注销重登后再跑同一句 → 出现

# ③ 制造一次网络登录，然后看记录（可选，管理共享关了就跳过）
net use \\127.0.0.1\IPC$ /user:%COMPUTERNAME%\%USERNAME%
query user
# 之后去事件查看器找 4624，看登录类型是几
```

**要亲眼看到的**：`whoami /all` 里那三块——组列表、特权列表、完整性级别，是同一枚令牌的三个部分；普通窗口与管理员窗口的 `Mandatory Label`、`Administrators` 两栏不同；加组之后 `whoami /groups` **立刻**不反映，重登才反映。以及 `net use` 之后 4624 记的是 **type 3**，不是 type 2。

> 完整命令与粘贴位置见 [[M1-问答]] 的验证区，这里只列要点。

Linux 侧：

```bash
# ① 四个 uid 分别是什么
cat /proc/self/status | grep -E '^Uid|^Gid'

# ② 提权前后对比：sudo 之后 euid 变 0，但登录记录没变
whoami; last -n 3
sudo -i -u root whoami
cat /proc/self/status | grep '^Uid'   # 在 sudo 会话里跑，四个都是 0

# ③ 看一次认证是怎么走的
sudo tail -n 20 /var/log/auth.log 2>/dev/null || sudo journalctl -u ssh -n 20
```

**要亲眼看到的**：`sudo` 之后 `whoami` 变了，但 `last` 里**没有新增一条登录记录**——它不是"新登录"，只是换了 euid。这正是 2.5 说的那个差异。

## 5. 为什么这样设计

**为什么不干脆每次操作都重新验证密码？**

因为那会把认证成本摊到每一次文件读取上。令牌是"一次认证、多次使用"的缓存——用一次登录换来一段时间的免验证。

**代价有三条，都能在现场看到：**

1. **令牌是快照**：组变更不实时生效，权限回收有延迟窗口
2. **网络登录不落地可再用凭据**：这是安全设计，但它让"凭据在哪"变成一个必须想清楚的问题
3. **两枚令牌**：UAC 换来了"默认低权限运行"，代价是大量程序在 Medium 下静默失败，用户以为"权限不够"
