### Q1｜判定：这份 ACL 拷过去还能用吗

机器 A：

```text
> whoami /user
User Name        SID
================ ==============================================
machine-a\test   S-1-5-21-1111111111-2222222222-3333333333-1001

> icacls D:\share
D:\share machine-a\test:(OI)(CI)(M)
```

机器 B：

```text
> whoami /user
machine-b\test   S-1-5-21-4444444444-5555555555-6666666666-1001
```

把 `D:\share` 连 ACL 一起拷到 B 机。B 机上的 `test` 打开这个目录，能不能写？为什么？

1. 能不能？说明卡在哪。
2. 你的结论依据的是 SID 的**哪一段**？把两边的 SID 对齐着指出来。

**追问**：如果两台机器都加入了 `CORP` 域，改用域账号 `CORP\test` 做同样的拷贝，结果会变吗？为什么？

**我的回答**：不能，目录的权限是绑定在machine-a\test账户上的，账户的权限由SID决定，SID又与本地机器域绑定，所以拷到B机的test用户没有打开目录的权限。A机的SID依据是1111111111-2222222222-3333333333，B机是4444444444-5555555555-6666666666。CORP域是什么我不知道，但我猜应该会改变，如果这是个共享账号的话则权限应该不与本机绑定，那拷贝到不同机器上的权限应该就一致，也就可以打开目录。

**反馈**：

**判定 △。结论对，追问方向也准，但依据缺一段精度、一个词用错。**

对的三处：不能写 ✔；抓到"SID 决定授权" ✔；追问猜"域场景会变" ✔——三个判断里方向最准的一个。

**1. "SID 与本地机器域绑定"——本地账户绑的是这台机器的机器 SID，不是域。**
SID 结构是 `S-1-5-21-<颁发者标识>-<RID>`。本地账号时前三段来自**机器**（你这台是 `907884189-1424754844-4139161484`），域账号时才来自**域**。一句话记：**前缀回答"谁颁发的身份"，RID 回答"这个颁发者下的第几个"。**

**2. 你只指了前缀，漏了 RID 相同这件事——而这正是最容易骗人的地方。**
两边 RID 都是 1001，看起来"对上了"，但完整 SID 不同。判主体永远看**整串**，不能只看尾号。你结论没被误导，但依据缺这一句。

**3. 更准确的说法不是"test 没权限"，是"这条规则找不到人"。**
ACL 里那条 ACE 指向的 SID 在 B 机上不存在，成了**孤儿 ACE**（orphan ACE）。不是主体被拒绝，是没有任何主体匹配上它。

**4. 追问用词要换：不是"共享账号"，是同一个安全主体。**
域账号 `CORP\test` 在域内有唯一 SID（前缀是域 SID），两台机器都向域控查同一个对象 → 拷到哪台都生效。差别不在"共享"，在**谁颁发、是否唯一**。

> **再深一层**：B 机上删掉 `test` 再重建同名 `test`，A 机拷来的那条 ACE 会对新 `test` 生效吗？提示：你这次新建的 `test` 拿到的是 `-1002` 而不是 `-1001`，这已经说明了一件事。

### Q2｜为什么：为什么不直接用用户名

系统用一串数字（SID / uid）标识主体，而不是直接用用户名。

1. 不用数字会退化成什么？说出**两种**会出的乱子，各举一个具体场景。
2. 这么做的**代价**是什么？挑最麻烦的那一条说清它麻烦在哪。

**追问**：什么情况下 `icacls` 会显示成一串 `S-1-5-21-...` 而不是 `machine-a\test`？列举至少两种原因，并指出**哪一种在安全上是有意义的信号**。

**我的回答**：不用数字用账号名吗，可能创建相同的账号会导致权限冲突。不太清楚代价。有重名吗，不太清楚。

**反馈**：

**判定 ✘。一种乱子 + 代价空白 + 追问空白，只到四分之一。**

**1. 第一种你说对了：重名 → 权限冲突。**
具体场景：两台机器都有 `test`，如果授权按名字走，同名就是同主体，事后没人分得清这条规则指的是哪一个。

**2. 缺的第二种：改名。** 这正是你刚做过的实验。用名字授权，改一次名等于把该主体在全局的所有授权作废，还得逐台去改 ACL；用 SID，改名对授权零影响。

**3. 代价（你没答，最麻烦的是第一条）：**

| 代价          | 麻烦在哪                                                   |
| ----------- | ------------------------------------------------------ |
| **不可读**     | SID 对人没有意义，必须有翻译层（工具查 SAM / 域控）。翻译不到就露出 `S-1-5-21-...` |
| **不能跨机器照搬** | 本地账号的授权换机即失效——域存在的直接动因就是这个                             |
| **机器克隆**    | 克隆时没重写机器 SID，两台机器的本地账号 SID 相同，权限体系会认错人                 |

**4. 追问答案**：`icacls` 显示成 SID 的三种情况——

| 情况                 | 说明                      | 有无安全意义                      |
| ------------------ | ----------------------- | --------------------------- |
| 该 SID 在本机解析不到      | 账户已删、域不可达、信任断裂 → 孤儿 ACE | **有**：留着一条没人对得上的授权，是提权排查的入口 |
| 外部/跨域 SID 未展开      | 信任没建立                   | 弱                           |
| 工具直接打 SDDL 或语言环境缺失 | 显示层问题                   | 无                           |

有意义的只有第一种。

> **再深一层**：孤儿 ACE 上如果后来重建了同名账号，新账号能"继承"这条授权吗？为什么？（这一问和 Q1 的追问是同一件事）

### Q3｜对照：两个 1000

机器 A 上 `alice` 的 uid 是 1000，机器 B 上 `alice` 的 uid 是 1001。两台挂载同一个 NFS 目录。

1. A 在共享里新建的文件，B 上 `ls -n` 看到的属主数字是几？B 上的 `alice` 能不能改这个文件？
2. 一句话说清：**为什么 Windows 侧不存在这个问题**？这个差异的代价各是什么？

**我的回答**：应该看到的还是自己的uid，也就是1001。应该可以改吧，都是普通用户权限。Windows侧用户权限还与本地机器相关联，Linux方便管理了但不能做到权限的细粒度划分，Windows权限划分细了但权限控制更复杂不能跨机器运维。

**反馈**：

**判定 ✘。第 1 问两个小问都反了，第 2 问因果颠倒。**

**1. B 上看到的是 1000，不是 1001。**
文件的属主是**创建它的人**（A 的 alice，uid 1000），不是你查看时用的身份。`ls -n` 读的是 inode 里记的 uid，跟着文件走，不跟着看的人走。

**2. B 的 alice 改不了。**
她 uid 1001，既不是属主（1000），也不在属组（1000）→ 落到 other 位；普通 0644 只有读。

**3. 真正的坑不是"改不了"，是"可能恰好改得了"。**
如果 B 上 1000 号是另一个人（比如 bob），bob 就能读写 alice 的文件，**系统认为完全合法**——不报错，日志里也没有异常。这才是"uid 是裸数字"的代价：它在每台机器上被独立解释，两台机器的 1000 未必是同一个人。"都是普通用户所以能改"这个直觉，正是这个陷阱的现实版。

**4. 第 2 问你说反了。**
Windows 之所以没这个问题，恰恰因为 SID **不是**裸数字——它自带颁发者。两台机器第 1001 号 RID，前缀不同，整串撞不上；域账号则全局唯一。
你说的"Windows 权限与本地机器关联"在本地账号场景成立，但那正是**问题**（换机失效），不是解法。

**5. 顺带纠一个印象："Linux 做不到细粒度"不成立。**
POSIX ACL、SELinux 的粒度不比 Windows 粗。Linux 缺的不是粒度，是**身份的全局命名空间**——没有"域"这种东西保证"这个 1000 在哪儿都是同一个人"。（LDAP + SSSD 可以补，底层仍是数字。）

> **再深一层**：容器里 uid 会被重映射（`/proc/self/uid_map`，容器内 0 号可能对应宿主 100000）。这时"uid 1000 是谁"还能靠数字判吗？Windows 侧有对应物吗？

## 沉淀（唯一入库物，填三处）

> 名义上仍是五格（G07），实际填三处：矛盾与代价各一句话，并入①。

|        | 填什么                                                            |
| ------ | -------------------------------------------------------------- |
| ① 机制   | 主体用 ____ 标识，它由 ____ 和 ____ 组成，据此决定 ____。不用它，会退化成 ____；代价是 ____ |
| ② 失效条件 | 什么情况下"同一个 SID"或"同一个 uid"这个判断会出错                                |
| ③ 现场信号 | 这条机制在 __（whoami /user、icacls、id、ls -n）上表现为 __；判错的人会看到 __       |

**我的结论**（串成 2–3 句自己的话，不许分点照抄）：
Windows/Linux主体用SID/uid标识，SID由前缀包含机器或域标识+RID组成，uid是纯数字。如此设计SID是因为账户名会变、会重名、会跨机器重复，这样做能做到权限的细粒度控制但也会造成不能跨机器运维的困难。当SID指向的账户不存在了就会失效。whoami /user看到由颁发者+RID组成的SID。

**反馈**：

**判：补两处，暂不进 [[../_结论]]。**

① **机制**——立住了。只改一个词：`域标识` → `机器或域的标识`，本地账号用的是机器 SID（你输出里前三段就是）。

② **失效条件 —— 空。** 三个方向任选一个写：

- 孤儿 ACE：SID 指向的主体已经不存在了，"看 SID 判主体"还成立吗？
- 两台机器的第 1001 号 RID，"尾号相同"能不能当同一主体？
- NFS 上 uid 恰好对上一个不相干的人时，数字还准吗？

③ **现场信号 —— 空。** 你已经有三条现成的，任选一条写成一句：

- `whoami /user` 的末段 = RID，前三段 = 颁发者
- `icacls` 里 `JEVONBF00\test2` 与 `...-1002` 的翻译关系
- `ls -n` 的 `1000 1000`

补完 ②③ 我再判一次。**这两处必须你自己写**——我写了就等于你没学。

**反馈（第二轮）：② 成立（有一处层次要拧准）；③ 只写了半句，缺"判错的人看到什么"。**

**② 成立，但把话拧准一层。** 孤儿 ACE 的时候，`S-1-5-21-...-1002` 这个**标识本身没有失效**——它仍然唯一指向"这台机器颁发过的第 1002 号主体"。失效的是**这条授权**：ACL 里那条 ACE 永远命不中任何人，成了死规则。所以准确说法是：

> SID 仍然可读、仍唯一，但它指向的主体已不可登录，这条 ACE 从"允许某人"退化成"谁都不允许"；而且 RID 不复用，删号重建同名账号也接不回来。

这正好接上你自己输出里的 `-1002`：1001 被删掉的账户占着，新账号只能拿 1002，孤儿 ACE 永远没人命中。

顺带提醒一句：你抄的"代价"表里还躺着一条更狠的失效条件——**机器克隆**。两台机器的机器 SID 没重写时，`-1001` 在两边都是"同一个人"，此时"SID 相同 = 同一主体"直接崩掉。孤儿 ACE 是"没人能用"，机器克隆是"谁都能冒充"，后者才是要防的。

**③ 还差一句。** 你写的 `whoami /user 看到颁发者+RID` 是**机制复述**，不是**现场信号**。现场信号的标准是：判错的人看到什么会走错，你看到什么能判对、靠哪个字符判的。按这个句式补后半句：

```text
whoami /user 末段是 RID、前三段是颁发者；判错的人会看到 ____，就以为 ____。
```

两个可选的真实现场，挑一个写就行：

- 判错的人看到两台机器的 `...-1001` 尾号一样，就以为是同一个账号；
- 判错的人看到 `icacls` 里 `JEVONBF00\test2`，就以为权限是授给"test2 这个名字"的。

一句话，写完这单元就验收，三处并进 `_结论`。

---

**附：你这次补上的 `id` 输出里有两条 M1 要用的东西**

1. `groups=1000(parallels),4(adm),20(dialout),27(sudo),124(wireshark)…` ——**主体不是一个数字，是一个集合**。Linux 侧叫附加组，Windows 侧叫令牌里的组列表，M1 就讲这个集合怎么装进令牌。
2. `/etc/shadow` 属组是 **42（shadow）**，不是 0 —— 说明"能读密码哈希的"不止 root 一个主体。M1 的凭证那半段从这里起。
