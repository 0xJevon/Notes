# M6 服务与守护进程

> 归属：[[../00-学习地图]] ｜ 答题：[[M6-问答]] ｜ 上一单元：[[M5-导读-对象与句柄]] ｜ 下一单元：M7 隔离与保护

## 1. 这个单元要回答什么

**后台进程以谁的身份跑？它启动时读的东西，谁能改？**

这是提权里成功率最高的一类，两边都是。原因不是技术复杂，是**长期运行的程序必须从磁盘加载东西**，而那个"东西"的权限经常配错。

## 2. 核心机制

### 2.1 两边是同一个模型

```text
Windows：SCM（服务控制管理器）读注册表 → 以服务账户起进程
Linux  ：systemd（PID 1）读 unit 文件 → 按 User= 起进程
```

| | Windows | Linux |
|---|---|---|
| 管理器 | `services.exe`（SCM） | `systemd` |
| 配置位置 | 注册表 `HKLM\SYSTEM\CurrentControlSet\Services\` | `/etc/systemd/system/`、`/lib/systemd/system/` |
| 以谁运行 | 服务账户（`LocalSystem`/`NetworkService`/自定义） | `User=` / `Group=`（默认 root） |
| 启动什么 | `ImagePath` 指向的 exe | `ExecStart=` 指向的命令 |
| 配置谁可改 | 服务 ACL（`sc sdshow`） | unit 文件权限 + 目录权限 |

**两边的劫持点完全对称**：改配置、换二进制、改它加载的东西。

### 2.2 Windows 的三个可控点

| 可控点 | 怎么查 | 怎么被利用 |
|---|---|---|
| **可执行路径** | `sc qc` 的 `BINARY_PATH_NAME` | 路径未加引号 + 上级目录可写 |
| **路径所在目录** | `icacls "C:\Program Files\X"` | 目录可写 → 直接换掉 exe |
| **服务自身 ACL** | `sc sdshow 服务名` | 有 `SERVICE_CHANGE_CONFIG` → 改 `ImagePath` 再启动 |

**未加引号的路径不等于可利用。** 要四条同时成立：

1. 路径含空格且**没有引号**
2. 从根往下某一级目录对当前用户**可写**
3. 候选文件名（如 `C:\Program.exe`）**还不存在**
4. 服务账户权限**高于**当前用户

缺一条就不成立。报漏洞时逐条写，缺哪条说哪条——这是"可利用"与"不可利用"的分界。

### 2.3 Linux 的三个可控点

| 可控点 | 怎么查 | 怎么被利用 |
|---|---|---|
| **unit 文件可写** | `ls -l /etc/systemd/system/x.service` | 改 `ExecStart`，`daemon-reload` 后重启 |
| **ExecStart 指向的脚本可写** | `systemctl cat x` 看路径，再 `ls -l` | 直接改脚本内容 |
| **ExecStart 用了相对路径或未加引号** | `systemctl cat x` | PATH 劫持 / 参数注入 |

另外两个常见面：

- **cron**：`/etc/cron*`、`/var/spool/cron/` 里脚本可写；`crontab -e` 的编辑器若配错也是
- **旧式 init 脚本**：`/etc/init.d/` 里的脚本若可写，同样

Linux 侧最容易被忽略的是**目录**：`/etc/systemd/system` 如果对非 root 可写，等于给了持久化能力，不需要改任何现有文件。

### 2.4 先看账户，再判值不值

| Windows 账户 | 收益 | Linux 对应 |
|---|---|---|
| `LocalSystem` | 本机最高 | `root` |
| `NetworkService` / `LocalService` | 高于普通用户，带 `SeImpersonate` | 系统用户（`www-data` 等） |
| 自定义域账户 | 可能在域内有额外权限 | 自定义用户 |

**一个以普通用户运行的守护进程，劫持了也只是换一个普通用户。** 判断顺序永远是：账户 → 路径权限 → 配置权限。

## 3. 查这几节（两边）

| 位置 | 查什么 |
|---|---|
| Windows · Learn: *Services / service security and access rights* | 服务权限位（`SERVICE_CHANGE_CONFIG` 等） |
| Windows · `sc qc` / `sc sdshow` | 现场命令 |
| Linux · `man 5 systemd.service`、`man 5 systemd.unit` | unit 各字段含义 |

## 4. 动手验证（两边各 15 分钟）

Windows：

```cmd
sc qc Spooler
sc sdshow Spooler
:: 找路径带空格且没引号的服务
wmic service get name,displayname,pathname,startmode | findstr /i " "
```

Linux：

```bash
# ① 看一个 unit 的完整配置与文件权限
systemctl cat ssh 2>/dev/null || systemctl cat sshd
ls -l /etc/systemd/system/ /lib/systemd/system/ | head -20

# ② 有没有可写的 unit 或脚本（重点）
find /etc/systemd/system -writable -type f 2>/dev/null
systemctl list-units --type=service --state=running | head

# ③ cron
ls -l /etc/cron.d/ /etc/cron.daily/ 2>/dev/null
crontab -l 2>/dev/null
```

**要亲眼看到的**：unit 文件的属主与权限；以及 `ExecStart` 指向的那个脚本，它自己是什么权限。**劫持点往往在第二层，不在 unit 本身。**

## 5. 为什么这样设计

**为什么要一个专门的管理器，而不是自己 `nohup`？** 因为需要：开机自启、崩溃重启、依赖顺序、统一日志、身份隔离。这些能力都要"以特定身份、从固定路径、加载固定内容"——**固定就意味着可预测，可预测就意味着可劫持**。

代价是：配置的权限、路径的权限、被加载文件的权限，三者任何一个配错，整条链就被人接管。而这个错误在两边都极其常见。
