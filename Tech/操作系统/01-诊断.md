### Q1｜身份

本地账号 `Administrator` 被改名成 `admin`，之前配给它的目录权限还在吗？为什么？

再问一句：两台机器上都建了 `test` 账号，A 机上给 `test` 配的权限，能不能直接搬到 B 机用？

**我的回答**：还在吧，名称和目录权限不是像Linux一样绑在一起的吧。不能，两台不同机器的权限分配应该不一样。

**反馈**：

**判定 △。结论对，理由缺一层。**

第一问结论对（权限还在），但理由不成立：Windows 不是"名称和目录权限没绑在一起"，而是**权限只绑 SID，从不绑名字**。改名只改登录名/显示名，SID 一个字节都不动，ACL 里那条 `S-1-5-21-...-1001` 照样命中。

第二问结论对，但只对了一半：**本地账号**的 SID = 机器 SID + RID，机器不同则 SID 不同 → 不能搬；**域账号能搬**，SID 由域颁发，两台机器看到的是同一个 SID。差别不在"机器不同"，在**谁颁发这个 SID**。

这正好是 M0 的第一句：名字是显示层，SID 才是身份。

> **再深一层**：把 A 机的本地账号 `test` 删掉再重建同名 `test`，旧的权限还能用吗？为什么？

### Q2｜登录与令牌

你以普通用户 `alice` 登录，然后 `net use \\10.0.0.5\share /user:corp\bob` 访问了一台共享。之后在 `10.0.0.5` 上抓到了 `bob` 的 NTLM hash，但抓不到他的明文密码。

1. 为什么网络登录拿不到明文？（提示：凭据留在了哪台机器上）
2. 这件事和 Pass-the-Hash 能成立，是不是同一个原因？

**我的回答**：网络登录通常是加了密的，所以用NTLM hash，凭据留在了访问机上。应该是吧，pth也是在本机抓取其他登录用户的hash，并通过该凭证去访问用户hash可访问的服务。

**反馈**：

**判定 △。方向对，两个机制节点缺，一处把原理说成了手段。**

对的部分：凭据留在客户端（alice 那台机器上），服务端只有认证结果。

**缺的第一环：不是"加密了所以拿不到"，是"根本没发"。**
NTLM 是三方协议（客户端、服务端、域控）：服务端发一个随机挑战，客户端用**密码派生的密钥**对它算出一个响应，服务端把响应转给域控验证。密码本身从未离开客户端。所以服务端抓不到明文——它从来没收到过密码，只收到一个 24 字节响应。

**缺的第二环：PtH 与第一问是同一机制的两面。**
认证只验"响应算得对不对"，而响应能由 NT hash **直接算出** → 不需要还原明文。这就是 PtH 成立的**原理**。
你写"pth 也是在本机抓取其他登录用户的 hash"，这是**获取 hash 的手段**，不是原理。原理是"hash 本身就是可用的凭据形式"。
（补一句：`net use` 到远程共享，凭据其实是在 alice 的 LSASS 里以会话形式缓存的，所以"留在了访问机上"这句成立，但要能指到 LSASS + 登录会话这一层。）

> **再深一层**：Kerberos 场景下 Overpass-the-Hash 要的是 AES key 而不是 NT hash，为什么？

### Q3｜UAC

你是 `Administrators` 组成员，双击运行了一个程序。`whoami /groups` 里却显示：

```text
Mandatory Label\Medium Mandatory Level
BUILTIN\Administrators   Group   S-1-5-32-544   Group used for deny only
```

1. 为什么是 Medium？系统在哪一步做了这件事？
2. 此时你去写 `C:\Windows\System32\drivers\etc\hosts`，会成功吗？**卡在哪一道检查上**——DACL，还是别的？

> **题面修正（2026-11-09）**：原题此处写的是 `Enabled by default, Enabled group, Group owner`，与 `Medium Mandatory Level` 不可能同时出现——过滤令牌里 Administrators 的正确标记就是 `Group used for deny only`。原题把两段不一致的输出拼在了一起，是出题错误。

**我的回答**：不知道。不会吧，看不太懂.

**反馈**：

**判定 ✘。空白，但"看不太懂"有一半不怪你——上面那个题面 bug 已修。**

机制三段：

**1. 管理员登录时，LSA 发两个令牌。**
完整令牌（High IL，Administrators 正常可用）+ 过滤令牌（Medium IL，Administrators 标 `deny-only`）。这是 UAC 的"管理员批准模式"，默认对本地 Administrators 组成员生效。

**2. 双击运行程序 = 没走 UAC 提权 → 用的是过滤令牌。**
所以 `whoami /groups` 显示 Medium。不是"系统把你降权了"，是你此刻拿的是另一个令牌。

**3. 写 hosts 会失败，落点在 DACL——但根在令牌。**
hosts 的 ACL 只给 `Administrators:F`、`SYSTEM:F`、`Users:读/执行`。唯一能给你写权限的，就是 Administrators 那条 ACE；而它在你手上的令牌里被标成 **deny-only（只可用于拒绝，不可用于授权）** → 求值时跳过 → 拒绝。

所以"卡在哪一层"的完整答案是：**表在 DACL，根在令牌里组的可用属性**。
UAC 提权前后变的不是"权限"，是**令牌里组的可用性 + 完整性级别**。这个区分是 M1 的全部内容。

顺带把顺序记住：Windows 访问检查先看 **IL**（目标 IL 高于你 → 直接拒，根本不查 ACL），再看 **DACL**（Deny 先于 Allow，Allow 累加），特权是绕过检查的第三只手。

> **再深一层**：如果 hosts 被设成 High IL（自己手动改的），失败点会提前到 IL，还是仍然落在 DACL？两条路的报错文本一样吗？

### Q4｜特权

`whoami /priv` 里：

```text
SeImpersonatePrivilege        Impersonate a client after authentication   Disabled
SeDebugPrivilege              Debug programs                              Disabled
```

1. `Disabled` 是不是等于"没有这个特权"？如果不是，谁能把它打开？
2. 一个 IIS 应用池账户（`ApplicationPoolIdentity`）默认带上面哪个特权？这个特权能拿来干什么？

**我的回答**：不是吧

**反馈**：

**判定 △-。第一问答了半句，第二问空白。**

**1. `Disabled` = 特权在令牌里，但当前关闭。**
谁能打开：**进程自己**，一行 `AdjustTokenPrivileges`，不需要提权、不需要管理员。这是最反直觉的一点——**拥有特权**与**启用特权**是两件事，而启用只是代码里一次调用。
所以看到 `Disabled` 的正确反应不是"没有"，是"**有，但还没开**"。判断能不能用，要问的是"这个进程会不会去开它"。

**2. IIS 应用池账户默认带 `SeImpersonatePrivilege`（另有 `SeCreateGlobalPrivilege`）。**
它能干什么：允许进程**模拟**一个连上来的客户端身份。配合命名管道或 RPC 让高权进程主动连你，你就拿到它的令牌——Potato 全家（Rotten/Juicy/PrintSpoofer）都是这一条路。

M2 与 M3 的分界就在这：M2 讲"哪个特权能绕过哪一道检查"，M3 讲"绕过之后怎么变成另一个身份"。

> **再深一层**：SeImpersonate 为什么在 IIS 应用池、SQL Server 服务账户上是默认给的，在普通用户令牌上却不给？这条差异对应哪一类攻击面？

### Q5｜访问控制

```text
C:\app BUILTIN\Users:(OI)(CI)(M)
```

你以普通用户身份执行 `echo x > C:\app\a.txt`，返回 `Access is denied`。

列出**至少三个**可能原因，并说明怎么用一条命令区分它们。

**我的回答**：没有目录的执行权限，没有文件的写权限

**反馈**：

**判定 ✘。两处错，且方向是反的。**

**1. `(M)` 是 Modify，含读、写、执行、删除——题面给的就是"有"。**
你答"没有目录执行权限、没有文件写权限"，等于把 M 读成了空权限。这一条错，后面所有推理都悬空。

**2. 只列两条，且没有区分手段。** 而这两条本质是同一条（"权限不够"），不是不同层。

ACL 看着给够了却仍失败，现实里就这五种：

| 原因 | 一条命令区分 |
|---|---|
| 存在显式 **Deny ACE**（Deny 永远先于 Allow） | `icacls C:\app\a.txt` 找 `(DENY)` |
| a.txt 的**继承被断开**，只有它自己的 ACE 生效 | 同上，看条目有没有 `(I)` 标记 |
| 文件带**只读属性** | `attrib C:\app\a.txt` 有 `R` |
| 目标 **IL 高于进程 IL** | `whoami /groups` 看完整性级别 |
| AppLocker/SRP 拦了 cmd 或其子进程 | 事件日志 AppLocker 分支 |

一条能同时看前三项：`icacls C:\app C:\app\a.txt`

**关键认知（M4 的骨架）**：Windows 的 ACL 求值是 **Allow 累加 + Deny 优先**（不看顺序，看有没有 Deny）；Linux 的 mode bits 求值是 **命中即停**（owner → group → other，命中就结束，不回落、不累加）。两个模型方向相反，混用必错。

> **再深一层**：`(OI)(CI)` 只对**之后新建**的子对象生效。那么已存在的 a.txt 为什么可能继承不到这条 M？缺的是哪个标记？

### Q6｜句柄与保护

同一台机器上，`mimikatz` 读取 lsass 报错：

```text
ERROR kuhl_m_sekurlsa_acquireLSA ; Handle on memory (0x00000005)
```

但任务管理器右键 lsass → "创建转储文件"能成功。

1. 这两件事差在哪？谁在替任务管理器做那一步？
2. 如果这台机器开了 LSA Protection（RunAsPPL），上面哪个还能成？

**我的回答**：不知道

**反馈**：

**判定 ✘。正常，这题要见过 PPL 才答得出。**

**1. `0x5` = 拒绝访问：请求 lsass 的进程句柄被拒。差在两件事同时成立。**

- 任务管理器是**以 High IL 运行、令牌里 `SeDebugPrivilege` 可用**的进程；
- 而 mimikatz 在 Medium IL 的过滤令牌下——**根因和 Q3 完全同一个**：lsass 的 DACL 里唯一能给你 `PROCESS_VM_READ` 的 ACE 是 Administrators，而它在你的令牌里是 deny-only → 求值跳过 → 0x5。再加上 lsass 是 High IL，Medium 进程连读都被拦。

所以"谁在替任务管理器做那一步"的答案是：**没人替它，它自己就有那个特权和级别**。

**2. 开 RunAsPPL 后：两个都不成。**
PPL 把 lsass 变成受保护进程，检查点从 DACL 前移到**内核对象管理器**：只放行受保护/签名的调用者，SYSTEM 也不够。任务管理器的 dump 一样失败。

题眼不是"权限不够"，是"**保护级别高于权限**"。M7 存在的理由就是这一类。

> **再深一层**：PPL 之后为什么连 SYSTEM 都打不开？——拦住它的不再是 ACL，那是什么？还剩哪三条路能取到 lsass 里的东西？

### Q7｜服务

```text
SERVICE_NAME: MyAppSvc
        BINARY_PATH_NAME   : C:\Program Files\My App\svc.exe
        SERVICE_START_NAME : LocalSystem
```

路径没有引号。

1. 这条能不能利用？如果能，利用点具体是哪个文件？
2. 需要什么前提？请说出至少两个——只差一个条件这条就不成立。

**我的回答**：LocalSytem

**反馈**：

**判定 ✘。你答的是运行账户，问的是利用点与前提。**

**1. 未加引号的路径，系统按空格断词依次尝试：**

```text
C:\Program.exe
C:\Program Files\My.exe
C:\Program Files\My App\svc.exe
```

利用点是第一个候选：**`C:\Program.exe`**。

**2. 前提（按卡死概率排序）：**

| 前提 | 现实情况 |
|---|---|
| 对 `C:\` 有创建文件的权限 | **默认没有**——这条路多数死在这里 |
| 服务以高权账户运行 | 题面已给 LocalSystem ✔ |
| 服务被重启或系统重启（重新解析路径） | 需要时机 |
| `C:\Program.exe` 尚不存在 | 否则被覆盖/冲突 |

判别值不值得打，先跑 `icacls C:\`。

M6 的核心问题不是"路径有没有引号"，是"**服务解析路径的那一刻，谁有权往候选路径里放文件**"。

### Q8｜边界

`SYSTEM` 和 `Administrators` 组的成员，谁权限更大？说出**两处实质差别**（不要说"SYSTEM 是系统账户"这种同义反复）。

**我的回答**：SYSTEM权限更大，可以创建Administrators用户吧，记不到了。

**反馈**：

**判定 △。方向对（SYSTEM > Administrators），但举的例子不成立**——Administrators 自己就能建账号并加进 Administrators，这不是差别。

两处最硬的差别：

| | SYSTEM | Administrators |
|---|---|---|
| 特权 | 令牌含 `SeTcbPrivilege`（act as part of OS），能创建登录会话、绕过 ACL 做完全访问 | **默认没有** SeTcb，需显式授予 |
| UAC | 无过滤令牌，永远完整令牌 | 交互式会话拿的是过滤令牌（Q3） |
| 登录 | **不能**交互登录桌面，只能由 SCM / 计划任务拉起 | 可交互 |
| 网络 | 本地账户，**不能向远程资源认证** | 域内可认证 |

反直觉的那条最值钱：SYSTEM 权限更大，但**动不了网络**——不能访问共享、不能认证到域。所以横向移动里 SYSTEM 反而不如一个域管账号。

> **再深一层**：很多标着"只有 SYSTEM 能读"的对象，Administrators 把权限拿到 SYSTEM 后就能读——那"SYSTEM 更大"这句话的准确含义到底是什么？

### Q9｜痕迹

有人在目标机器上执行了 `sc create` 装了一个服务，并启动了它。你要在日志里找到这件事。

1. 去**哪个日志**、找**哪个事件 ID**？关键字段是哪几个？
2. 如果那台机器从没改过审计策略，这条记录还会有吗？
3. 攻击者事后想把痕迹抹掉，他做的动作**反而会留下一条新记录**，是哪个事件？

**我的回答**：AppEvent.evt吧，事件IP不太清楚。记不到

**反馈**：

**判定 ✘。`AppEvent.evt` 是旧式应用日志，方向就错了**（服务安装事件不在应用日志里）。

**1. 正确分层：**

| 事件 | 日志 | 依赖审计策略 |
|---|---|---|
| **7045** 服务已安装 | **System** | **不依赖**（SCM 自己写） |
| 7036 服务状态变更（启动/停止） | System | 不依赖 |
| **4697** 服务已安装 | Security | **依赖**（审核安全系统扩展，默认关） |
| 1149 / 4688 相关 | Security | 依赖 |

关键字段：`Service Name`、`ImagePath`（看可执行路径与引用）、`Service Type`、`Start Type`、`Account Name`、`Subject: Account Name`（谁装的）。

**2. 答案：会有。**
4697 不会有（默认不审），但 **7045 一定有**——它是服务控制管理器写的，跟审计策略无关。
这一问是整个 M8 的分水岭：**日志 ≠ 审计**。很多事件是组件自己写进日志的，不是审计子系统记的；反过来，没有审计策略就没有 4688（进程创建）。

**3. 1102**（Security 日志被清除）与 **104**（System 日志被清除）。
`wevtutil cl Security` 执行的那一瞬间就留了 1102——清空动作本身被记在即将被清的那本账上。

> **再深一层**：看到 1102，但之后既没有 4688 也没有 7045，你判"他没干过事"还是"他干完清干净了"？判据是什么？

### Q10｜Linux 权限

```text
-r--r----- 1 root staff /opt/app/conf.yml
```

你是 `staff` 组成员，**不是** root。

1. 你能读吗？
2. 把属主改成你自己，权限位不变，你还能读吗？为什么？
3. 如果读不了，除了 mode bits，还有哪**两种** Linux 特有的可能？

**我的回答**：
可以，staff组有读权限。
可以，属主有读权限，我是属主可以读。
SUID和SGID

**反馈**：

**判定 △。1、2 对，3 错。**

**1 ✔** 命中 group 位的 `r--`，能读。
**2 ✔** 答案"能读"，理由是属主位是 `r--`。

**但这题第 2 问没考出它想考的东西**：属主位恰好有 `r`，所以按"属主能读"推也对。真正考"命中即停"的题面应该是 `----r-----`——那时改成属主**反而读不了**：属主位命中（虽然是空权限）就停止求值，不会回落到 group 位。
这正是 Linux 与 Windows 最根本的差异：**Linux 命中即停，Windows 累加 + Deny 优先**。

**3 ✘：SUID/SGID 是"执行时换身份"，不是"读不了"的原因。** 正确候选：

| 可能 | 怎么验 |
|---|---|
| **POSIX ACL**（有 deny 条目，或 mode 位只是 mask 的投影） | `getfacl /opt/app/conf.yml` |
| **SELinux/AppArmor**（MAC 层） | `ls -Z`、`ausearch -m avc`、`dmesg` |
| `chattr +i`（immutable，root 也写不了） | `lsattr` |
| 挂载只读 | `mount` 里的 `ro` |

前两条才是"Linux 特有的第二道门"，和 Windows 的 IL / PPL 是同一个生态位——**有权限也拿不到**。

> **再深一层**：`getfacl` 里出现 `mask::r--`，而 `ls -l` 的 group 位也显示 `r--`——这两者是什么关系？`chmod g-w` 动的是哪一个？

### Q11｜Linux 痕迹

一台 Linux 服务器怀疑被入侵，你只有本机，没有集中日志。

1. 第一件事查什么？为什么是它？
2. `last` 和 `auth.log` 各能回答什么、**不能**回答什么？
3. 攻击者执行了 `history -c`，你还能从哪些地方找线索？（至少两个）

**我的回答**：
/var/log/secure，安全日志可以查看安全相关事件
上个用户的登录时间但不知道干了什么，系统用户的认证记录
记不太到

**反馈**：

**判定 △。方向对，取证顺序反了，第 3 问空白。**

**1 ✘-：把"读日志"当第一件事，顺序是反的。**
入侵响应第一步不是翻日志，是**固定易失现场**：当前进程树、网络连接、登录会话、计划任务/cron、最近改动文件、已加载模块。
理由三条：日志可能已被清；系统可能还在被控（你在它上面跑命令会被看见）；重启即全丢。日志是第二、三步的材料。
（`/var/log/secure` 是 RHEL 系的叫法，Debian 系是 `/var/log/auth.log`——这个区分你答对了。）

**2 ✔-**：基本对。`last` 读 wtmp，答"谁在何时从哪登录、待了多久"，答不了"干了什么"；`auth.log` 只覆盖认证（ssh 成败、sudo、su），答不了进程执行。
要补两句：wtmp 可被 `utmpdump` 改写或清空；两者都看不到非登录类动作（cron、服务、无登录的反弹 shell）。

**3 ✘：至少两个。**

| 来源 | 命令 | 前提 |
|---|---|---|
| **auditd**（execve 审计） | `ausearch -sc execve` | 规则存在；`auditctl -l` 为空就等于没有 |
| **进程记账** psacct/acct | `lastcomm`、`sa` | 装了并开着 |
| **journald** | `journalctl _COMM=bash` | 是持久化模式，不是 volatile |
| 其他用户 / root 的 history | `cat /root/.bash_history` | `history -c` 只清当前 shell |
| 活着的 shell | `/proc/<pid>/cmdline`、`environ` | 进程还没退 |

最值钱的是第一条：**`history -c` 抹的是 shell 的历史，抹不掉内核层的 execve 审计**——前提是审计开着。
这就是 M8 的落点：**可观测性不取决于攻击者删了什么，取决于你事先开了什么。**

> **再深一层**：如果 `auditctl -l` 为空、没装 psacct、journald 是 volatile，这台机器上还剩哪些痕迹能证明"有人执行过命令"？
