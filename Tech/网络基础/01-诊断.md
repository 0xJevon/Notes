## 逐题反馈

### Q1 全链路清单

**我的回答**：浏览器输入网址，通过DNS协议的解析器查询域名对应的IP，通过TCP/IP协议栈与目标服务器建立socket连接并发送请求数据包，数据包会通过路由、集线器等传输到服务器处，服务器处理完数据包后会按相反的方向把返回包反馈到客户端，这样用户就能在客户端看到对应的网页了

**反馈**：

主干四步抓对了（名字解析 → 建连 → 发送 → 原路返回），方向没问题。但有四个缺口：

**1. 从"网址"直接跳到了"DNS"，中间少了 HTTP 报文的构造。**
浏览器不是把网址发给服务器，而是先按固定格式拼出一段文本（请求行 + 消息头 + 空行 + 消息体），**这段文本才是真正被传输的对象**。少了这一步，容易误以为"网络层传的是网址"。

**2. "通过路由、集线器等传输"——这句话有两个问题。**
- 集线器（Hub）在现代网络里基本绝迹了，接终端的是**交换机**；
- 更要紧的是：**包不是每跳都经过路由器**。同网段通信只经过交换机（二层），跨网段才交给路由器（三层）。这个区分是后面所有内容的地基——你在 Q3 犯的错，根就在这里。

**3. 缺两个环节：ARP 和 NAT。**
ARP 是"怎么找到下一跳的 MAC 地址"，NAT 是"内网地址怎么变成公网地址出去"。你的链路图里这两个位置是空的，而企业网出问题最频繁的恰恰是这两处。

**4. 表述问题**：不是"与目标服务器建立 socket 连接"。socket 是你本机内核里的一个句柄，建立的是 **TCP 连接**，socket 只是你操作它的入口。

> **再深一层**：你说"返回包按相反方向回来"。那么回程路由一定是去程的逆序吗？如果是，互联网就不需要各自维护路由表了——想想为什么不是。

### Q2 两个 ping 结果不一样

**我的回答**：第一个证明了本机与8.8.8.8能通过ICMP协议连接，也就是网络互通。第二个排除了本机的DNS表中存在www.baidu.com这个域名，应该是DNS协议有问题，所以故障出在应用层

**反馈**：

结论方向对：网络是通的，问题在名称解析。但有四处需要收紧。

**1. 第一问可以再说透一层。** `ping 8.8.8.8` 通，同时证明了四件事：IP 层可达、**路由表有默认路由**、**NAT 工作正常**（否则私网地址出不去）、出口没有拦 ICMP。这四条里，NAT 那条尤其值钱——它排除了一大类故障。

**2. "排除了本机的 DNS 表中存在 www.baidu.com 这个域名"——这句话把两件事混住了。**
准确表述是：**8.8.8.8 通，排除了网络连通性问题，因此故障被定位在"名称解析"这一环。** 你的写法像是在说"本地没这条记录"，但 `cannot resolve` 涵盖的是整个解析链失败（本地缓存、hosts、DNS 服务器地址、DNS 服务器可达性），不只是"表里没有"。

**3. "DNS 表"这个词不准确。** 本地只有 hosts 文件（静态映射）和 DNS 缓存，没有"DNS 表"。

**4. "故障出在应用层"——定性太粗，对下一步没有指导意义。**
DNS 确实是应用层协议，但真实故障点一般是：DNS 服务器地址配错、DNS 服务器不可达（UDP 53 被拦）、或解析结果被污染。**说"名称解析失败"比说"应用层故障"有用，因为前者直接指向下一个动作。**

**5. 你漏了排障的第一刀**：`cannot resolve` 和 `Request timeout` 是两种完全不同的失败——前者是**解析没成**，后者是**解析成了但连不上**。这一刀不切开，后面全乱。

> **再深一层**：如果 8.8.8.8 通，但你的 DNS 服务器（比如 114.114.114.114）ping 不通，`ping www.baidu.com` 报的错和题目里那个一样吗？

### Q3 地址与网关不匹配

**我的回答**：都不能，首先网关是192.168.2.1和192.168.1.10/24不在一个网段上，所以不能与192.168.1.20进行通信。其次机器配置的是内网地址，并没有与外网通信的地址所以不能访问外网

**反馈**：

**这题错得最有价值，请重点看。**

**第一问就错了：`192.168.1.10/24` 访问 `192.168.1.20` 是通的。**

因为 192.168.1.20 和自己处在同一个 /24 网段内，**同网段通信根本不用网关**。主机会直接 ARP 问"谁是 192.168.1.20"（广播），拿到 MAC 后由交换机转发。网关配错完全不影响这条路径。

你的推理是"网关不在同网段 → 不能通信"——这一步把**同网段能力**和**跨网段能力**混成了一体。牢记一句：**网关只在"目的地址不在本网段"时才被使用。**

**第二问结论对，但理由错，而且错在一个更根本的地方。**

你写"机器配置的是内网地址，并没有与外网通信的地址"——**内网地址完全可以通过 NAT 访问外网**，这是全世界企业网的标准做法，不需要任何公网地址。这条误解如果不纠正，后面学 NAT（M9）会全盘歪掉。

真正的因果链比你的版本长一环：

```
目的地址在外网 → 判定为跨网段 → 必须交给网关
                                   ↓
                        网关 192.168.2.1 不在本网段
                                   ↓
                         ARP 不到它，拿不到 MAC
                                   ↓
                          包发不出去（只有 SYN 重发）
```

不是"网关地址错了所以不通"，而是"网关地址错了 → 找不到网关的 MAC → 无法交给下一跳"。**中间那一环是你缺的。**

配置错在哪：网关必须和本机地址同网段，即应为 `192.168.1.1` 这类地址。

> **再深一层**：如果把掩码从 /24 改成 /16（地址仍为 192.168.1.10/16），这台机器能上网吗？能访问 192.168.2.1 吗？为什么改一个掩码就把结论翻转了？

### Q4 只有 SYN

**我的回答**：1、SYN包没有正确的发送给其他机器。2、其他机器的确认的ACK包被拦截。如果端口没有程序监听应该不会一直重发SYN包

**反馈**：

**后半问的结论是对的**：端口没监听不会一直重发 SYN，服务端会立刻回 **RST**，客户端马上报 `Connection refused`。这个直觉说明你想清楚了"有回应"和"没回应"的区别。

**问题在前半问：只列了 2 条，而且两条本质是同一类。**
"SYN 没发出去"和"回包被拦"都是**包丢失**，属于同一个维度的两个方向。题目要的是**不同层**的原因：

| 层 | 可能原因 | 现象差异 |
|---|---|---|
| 二层 | ARP 失败（同网段但目标不存在） | 只有 SYN 重发，包根本没出网卡 |
| 三层 | 无路由 / 路由不可达 | 通常回 ICMP 不可达，但常被中间设备丢弃 |
| 防火墙 | 静默 DROP | 只有 SYN 重发，**与端口未监听完全不同** |
| 传输层 | 目标存活但端口无监听 | 立刻 RST，不是静默 |
| 主机 | 目标宕机 / 网线断开 | 静默或 ICMP 不可达 |

**表述修正**：第二次握手是 `SYN+ACK`，不是"确认的 ACK"。

> **再深一层**：RST 和静默丢弃，分别对应防火墙的哪两种动作（REJECT 和 DROP）？为什么生产环境更常用后者？它的代价是什么？

### Q5 子网划分

**我的回答**：网络地址总共是32位，192.168.1.0/24也就是32-24=8位有效地址，也就是2^8=256位主机地址，其中要去掉广播地址255和网络地址0所以可用地址是254，/26也就是64-2=62个可用地址。

**反馈**：

/24 完全正确，思路也对（要扣掉网络地址和广播地址）。

**问题在 /26：你只给了结果，没给过程。** 你写"64-2=62"，但 64 从哪来？正确算法是 `2^(32-26) = 2^6 = 64`。我需要确认你是真会算，还是记住了"62"这个数字。

**请补答**：`192.168.1.0/26` 的网络地址、广播地址、第一个和最后一个可用地址分别是多少？

**另一个隐患比结果更重要**：你写"去掉广播地址 255 和网络地址 0"——这个说法**只在 /24 下巧合成立**。
准确的定义是：网络地址 = **主机位全 0**，广播地址 = **主机位全 1**。在 /26 里它们不是 .0 和 .255（第一个子网例外）。**用 /24 的特例去套所有掩码，是这类计算最常见的错源。**

> **再深一层**：`192.168.1.100/25` 和 `192.168.1.100/24`，这台机器认为"谁是同网段"的答案一样吗？如果一条网线上的两台机器一个配 /24、一个配 /25，会发生什么？

### Q6 证书告警但能打开

**我的回答**：HTTPS是通过SSL/TLS进行加密的，证书无效以为着证书过期或证书颁发机构未受认证，所以身份没有进行验证，但还是进行的加密通信

**反馈**：

这题答得干净。两个结论都对：**加密建立了、身份未验证**。而且你能把"加密"和"认证"当两件事分开看，这个区分很多人做不到。

补三层，让它更结实：

**1. 加密之所以能建立，是因为客户端在验证失败后仍选择继续握手**——也就是你点了"继续访问"。不点，连接就断了。所以这不是 HTTPS 的默认行为，是用户主动降级。

**2. 更准确的说法：不是"没有验证"，而是"验证了，但结果不被信任"。**
证书链验不通、域名不匹配、签发者不在信任列表——身份信息其实拿到了，只是没有可信第三方为它背书。这个区别在排查时很有用。

**3. 告警的意义在于**：你正在和一个"自称是目标、但没人能证明它是目标"的对方通信。加密保证了"旁人看不懂"，**但没保证"对面不是中间人"**。这就是为什么证书错误要被当成事故而不是提示。

> **再深一层**：如果是攻击者做中间人，客户端看到"证书无效"；如果是公司部署了 SSL 解密审计设备，客户端往往**不报错**。两者都是"中间人在中间"，为什么现象不同？

### Q7 读一张拓扑

**我的回答**：

```
iptables -t filter -P FORWARD DROP

iptables -t filter -A FORWARD -s 10.10.1.10 -d 10.10.2.20 -p tcp --dport 3306 -j ACCEPT

iptables -t filter -A FORWARD -s 10.10.2.20 -d 10.10.1.10 -p tcp --sport 3306 -j ACCEPT
```

直接写DMZ访问内网会导致防火墙完全起不到数据审计和网络隔离的作用，若DMZ区被攻陷则会导致不单10.10.1.0/24网段会被攻击者全量攻击内网段10.10.2.0/24也会被攻击

**反馈**：

**这是 8 题里答得最好的一题**，说明你有真实操作经验：四要素齐全、默认拒绝的策略也对、回程也考虑到了、最小权限的解释方向正确。

三个要修正的点：

**1. 缺接口限定（实务上最关键）。**
只写 IP 不够。多接口防火墙上必须指定 `-i`（从 DMZ 侧接口进）和 `-o`（往内网侧接口出）。否则同一对 IP 在别的接口上也会被放通——**规则写对了 IP，方向却可能反了。**

**2. 回程规则不必手写。**
iptables 是有状态的（conntrack），标准做法是一条：

```
iptables -A FORWARD -m state --state ESTABLISHED,RELATED -j ACCEPT
```

你这样逐条配反向规则不错，但**规则数量会随业务线性增长**，几百条业务规则就是几百条回程规则，维护不起。这也是"有状态防火墙"相对"包过滤"的核心优势。

**3. 你的解释逻辑对，但范围说大了。**
你写的规则已经是**单 IP 到单 IP**，所以真正的风险不是"整个 10.10.1.0/24 被攻陷"，而是"这一台 Web 被攻陷后，攻击者获得了一条直连数据库的通路"。
**把范围说准，比说得严重更有说服力**——和你写漏洞报告时定的那个标准是同一个道理。

> **再深一层**：这条规则放通后，Web 服务器能不能反过来让数据库主动连它？（提示：注意方向，以及 conntrack 的 `RELATED` 会放过什么）

### Q8 一个现象的归属

**我的回答**：搞不懂SYN_RECV是什么意思，但感觉应该是服务端已经收到客户端发出的SYN请求但没有做出回应，下一步可以看服务端是否正常工作吧

**反馈**：

前半对：服务端确实收到了 SYN。**后半反了。**

`SYN_RECV` 是**半连接**状态，意思是：**服务端已经回了 SYN+ACK，正在等客户端的第三个 ACK。**

所以不是"没回应"，而是"**回应了，但没等到确认**"。这条连接在等的是**客户端**，不是服务端。

可能的原因：
- SYN+ACK 在回程被丢（防火墙、NAT 表项缺失）
- 客户端收到但没回 ACK（客户端已超时放弃、或客户端侧有问题）
- 大量 SYN_RECV 堆积 → 典型 SYN Flood，或**半连接队列被打满**

下一步该查什么（比"看服务端是否正常"精确得多）：

1. 客户端侧有没有收到 SYN+ACK（**在客户端抓包**，别在服务端抓）
2. `ss -s` 看队列是否溢出，关注 `SYNs to LISTEN sockets dropped`
3. 中间设备的会话表 / NAT 表是否满
4. **数量**：一条是偶发丢包，成千上万条就是攻击或队列配置问题

> **再深一层**：服务端为什么要为"还没确认"的连接提前保留资源？这个设计带来了什么攻击面？（这就是 SYN Flood 的原理）
