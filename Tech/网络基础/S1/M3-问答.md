### Q1｜概念：套接字到底是什么

1. 套接字是一个程序、一个文件，还是一块记账信息？
2. 它存在进程里，还是存在内核里？进程手里拿到的是什么？
3. 一条 TCP 连接靠什么唯一标识？写全。

**我的回答**：
套接字的实体是控制信息的集合包括TCP报头，源目端口、序号和确认号等；套接字在操作系统内核中，通过Socket库创建，操作程序创建套接字后会生成标识符给进程用于操作对应的套接字；TCP连接包含源目IP和源目端口。
**反馈**：

**1 ✔、2 ✔、3 ✔，只有一个概念要修。**

1. 方向对（一块记账信息）。但**TCP 报头不在套接字里**。套接字里存的是**状态量**：对端 IP/端口、本端 IP/端口、序号、窗口、状态。报头是每次发包时**照着账本现拼的单据**，拼完发出去就没了。账本（套接字）和单据（报头）要分开——排障时 `netstat` 看的是账本，抓包看的是单据，两样东西能对上才是会读证据。
2. 对：状态在内核，进程手里只有描述符。
3. 对：四元组，源目 IP + 源目端口。

### Q2｜过程：三次握手按顺序做了什么

按顺序写出三个包各自携带什么、对方据此确认了什么。然后回答：**为什么不能只握两次？**（说明两次会漏掉哪一种确认）

**我的回答**：
先请求连接发送SYN包，确认连接发送SYN和ACK，对确认连接的确认发送ACK包，双方由此确认要发送字节流的大小和可接收的窗口。
如果只握两次可能导致请求方的SYN包延迟发送给服务方，服务方确认连接但请求方此时并不需要连接，此时就会导致资源的浪费，所以还需要请求方的二次确认。
**反馈**：

**三个包的顺序 ✔，"为什么不能两次"答的是经典理由 ✔。但握手确认的对象写错了——这正是本题题眼。**

**确认的不是"字节流大小和窗口"，是双方的初始序号（ISN）。**

| 包         | 携带                       | 对方据此确认了什么                         |
| --------- | ------------------------ | --------------------------------- |
| ① SYN     | 我的初始序号 ISN_c             | （服务端记下：客户端从 ISN_c 起算）             |
| ② SYN+ACK | ACK=ISN_c+1 ＋ 服务端的 ISN_s | 客户端知道：服务端收到了我的起点，且服务端自己的起点是 ISN_s |
| ③ ACK     | ACK=ISN_s+1              | 服务端知道：客户端收到了**我的**起点              |

窗口大小是 SYN 包里**捎带的通告**，不是被"确认"的对象；字节流大小此刻是零——数据一个字节都还没发。你把"捎带的信息"当成了"被确认的东西"。

**为什么确认序号才是核心**：之后每一个字节的编号都从 ISN 起算。双方起点对不上，接收方就没法判"这是第几个字节、中间丢了没有"——重传机制整个建立在它上面。所以三次握手不是客套，是**对表**。

"为什么不能两次"你说对了历史 SYN 的幽灵连接问题，但题目括号里要的那句你没点出：**两次握手里，服务端永远无法确认"客户端收到了我的 ISN"**——它不知道自己的起点有没有被对方记住，只能单方面把连接立起来等。你答的"资源浪费"正是这个确认缺失的后果。

### Q3｜判定：一台机器怎么同时服务五万个客户端

一台 Web 服务器只监听 80 端口，此刻有 5 万个客户端保持着连接。

1. 内核靠什么把这 5 万个连接区分开？
2. 服务端只用了**一个**本地端口，为什么不会"端口不够用"？
3. 那瓶颈会在哪里？说出两个你认为最可能的资源。

**我的回答**：
连接会分为源目IP和源目端口，所以虽然服务器的源IP和端口都一样但客户端的IP和端口并不相同所以可以区分；为客户端提供服务可能会开临时临时进程占用临时端口吧，所以虽然连接的都是同端口但会存在临时端口不够用的情况；服务器本身的内存和硬盘资源吧，因为要提供服务。
**反馈**：

**1 ✔。2 方向装反了——这是本题唯一的硬错。3 对一半。**

**2. 服务端不为每个连接开新端口，也不占用任何临时端口。** accept 出来的每条新连接，服务端那侧**还是 80**。区分靠的是四元组里**客户端**那两个值：5 万个客户端就有 5 万个不同的"客户端 IP+端口"组合。你在 `netstat` 里会看到几千行都是 `本机.80 → 某客户端`，本地端口一个都没变。

"临时端口不够用"是**客户端的病**：主动发起连接的一方才要消耗临时端口，`TIME_WAIT` 堆积时占着不放，端口池耗尽后新连接发不出去。你把服务端和客户端的账记反了。

**你自己的验证输出里就有活证据**，这条你没发现：

```text
tcp4  0  0  192.168.68.195.61985  104.26.1.147.443  ESTABLISHED
tcp4  0  0  192.168.68.195.61982  104.26.1.147.443  ESTABLISHED
```

同一个远端 `104.26.1.147.443`，两条连接，全靠**本地端口 61985 / 61982** 区分——这就是"客户端消耗临时端口"的现场，也是四元组在工作。哪天你看到本机临时端口被 `TIME_WAIT` 占光，就是这条的失效现场。

**3.** 内存 ✔——每条连接的收发缓冲区加套接字结构，5 万条就是实打实的几百 MB 起步。更贴的第二个答案是**文件描述符上限**：每条连接占一个 fd，进程的 `ulimit -n` 一到，连接建不了，表现和"端口不够用"几乎一样。"硬盘"不贴——静态小站点的瓶颈轮不到磁盘。

## 沉淀（本单元唯一入库物）

> **先确认「这个机制」指哪一条**：不是整章主题，是导读第 2 节「核心机制」里那条判定/流程。
> M3 的那条是：**一条连接在系统里被什么唯一标识、建立时双方各确认了什么。**

| 格 | 填什么 |
|---|---|
| ① 过程 | ______ 先 ______，然后 ______，最后 ______ |
| ② 为什么这样设计 | 不这么做会 ______；代价是 ______ |
| ③ 什么时候不成立 | 如果 ______，这套就不适用 |

**我的结论**（三格串成 2–3 句自己的话，不许分点照抄）：
客户端与服务端通过四元组（源目IP和源目端口）确认唯一的连接，然后通过三次握手确认传输的字节流大小和一次可接收的窗口大小，三次握手成功最后建立连接。不建立完整的三次握手可能导致双方无法确认同时空闲和需要连接导致资源的浪费。

**反馈（沉淀 · 第一版，2026-11-03）**：

**判定：补一格。** ① 有一处硬错（和 Q2 是同一个错，说明不是笔误），② 没落到代价上，③ 空着。

| 格         | 这次盯什么                                                                                                  |
| --------- | ------------------------------------------------------------------------------------------------------ |
| ① 过程      | 四元组那句 ✔ 保留。握手改成：**SYN 交换双方初始序号（ISN）→ ACK 各自确认收到对方的起点**。删掉"字节流大小和窗口"——窗口是捎带的通告，字节流此刻还没发生                |
| ② 为什么这样设计 | "确认同时空闲"太含糊。写实质：起点对不上 → 接收方没法判第几个字节、丢了没有 → 重传无从谈起。代价也要写：多等一个 RTT 才能发数据；半开连接占着服务端队列（这就是 SYN flood 的攻击面） |
| ③ 什么时候不成立 | 至少写一条。现成的两个：**UDP 没有握手**（DNS 一问一答打包即走，牺牲的就是这套保障）；**NAT 之后服务端看到的四元组里源 IP 已是出口地址**（K05 的钩子）              |
客户端与服务端通过四元组（源目IP和源目端口）确认唯一的连接，然后通过SYN交换初始序号ISN用于确认字节流起点，ACK表示对ISN的确认。如果不缺认起点会让接收方不知道接收到第几个字节了，也就无法确认丢失从而导致重传机制失效，代价是需要双方都确认导致服务队列被占用。UDP没有三次握手机制换取效率但失去了可靠性。
补完这轮我再看一眼，过了直接进 K04 收尾。

**反馈（沉淀 · 第二版，2026-11-03）**：

**判定：过。** → 已入 [[_结论]] K04

| 格 | 判 |
|---|---|
| ① 过程 | 对。四元组定位连接 + SYN 交换 ISN + ACK 确认对方起点，"确认字节流起点"这个说法比 v1 的"字节流大小"准了一整级——起点是**约定的编号原点**，不是长度 |
| ② 为什么 | 链条对：起点没确认 → 不知道收到第几个字节 → 判不出丢没丢 → 重传无从谈起。这条链就是 TCP 全部的可靠性根基 |
| ③ 不成立 | 挑中 UDP ✔。一句"换效率丢可靠性"抓住了要害——DNS 一问一答打包即走，省的就是这一整套账 |

**②的因果再校一格（不影响过）**：

你写「代价是需要双方都确认导致服务队列被占用」——**占队列的原因不是"确认次数多"，是"服务端收到 SYN 就先建半开条目，第三个包不来就一直占着"**。

差别很实在：如果代价只是"多确认一次"，那这个代价是固定的、可控的。真实情况是**代价由攻击者控制**——他只发第一个包，你就得替他保管一个半开的条目，直到超时才清。这就是 SYN flood 的全部原理，不需要打穿任何东西，只要把队列塞满新连接就进不来。

所以那句更准的写法：**代价是服务端必须先替每条还没握完手的连接预占一个队列位，而这个位的存活时间由对端决定。**
