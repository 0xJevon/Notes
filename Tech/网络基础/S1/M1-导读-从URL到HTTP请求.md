# M1 从 URL 到 HTTP 请求

> 归属：[[00-学习地图]] ｜ 答题：[[M1-问答]]

## 1. 这个单元要回答什么

敲下回车之后、把第一个字节交给操作系统之前，**浏览器自己一个人做完了哪些事？**

看起来只是个开场白，但它是整条链路的参照系。如果这里理解偏了，后面讲 TCP 缓冲区、IP 分片、路由选路时，你会不知道那些机制到底在替谁干活——因为你不清楚它们服务的那个"对象"长什么样。

一句话版本：浏览器把**一个网址**翻译成**一段字节 + 一个目的地（IP:端口）**，然后才交给操作系统。

## 2. 核心机制

### 2.1 URL 被拆成三段，分别交给不同的人

以 `http://a.example.com:8080/x/y?z=1` 为例：

| 拆出来的部分 | 值 | 谁消费它 |
|---|---|---|
| 协议 | `http` | 浏览器自己（决定用哪个客户端模块） |
| 主机名 | `a.example.com` | 交给 DNS 换成 IP（M2） |
| 端口 | `8080`（缺省 80/443） | 交给 TCP 定位进程（M3） |
| 路径与参数 | `/x/y?z=1` | 写进请求行，交给服务端应用自己解释 |

这里有一个容易被忽略的分工：**浏览器从头到尾不关心 IP**，它只认主机名。IP 是下一层的事。

这个"上层只认名字、下层负责翻译"的分工，是后面所有讨论的地基——也是理解 NAT、代理、CDN 为什么能"插在中间"的前提。

### 2.2 请求和响应的报文长什么样

```text
请求报文                                响应报文
┌────────────────────────────────┐     ┌────────────────────────────────┐
│ GET /x/y?z=1 HTTP/1.1          │ ← 请求行（方法 + 路径 + 版本）
├────────────────────────────────┤     ├────────────────────────────────┤
│ Host: a.example.com            │     │ HTTP/1.1 200 OK                │ ← 状态行（版本 + 状态码 + 短语）
│ User-Agent: ...                │     ├────────────────────────────────┤
│ Accept: text/html              │ ← 消息头（一堆 key: value）
│ Cookie: ...                    │     │ Content-Type: text/html        │
├────────────────────────────────┤     │ Content-Length: 1024           │ ← 消息头
│ （空行，必须有）               │     │ Set-Cookie: ...                │
├────────────────────────────────┤     ├────────────────────────────────┤
│ 消息体（GET 一般为空）         │ ← 消息体
└────────────────────────────────┘     ├────────────────────────────────┤
                                       │ <html>...                      │ ← 消息体
                                       └────────────────────────────────┘
```

记忆锚点只有一句：**请求行/状态行 → 消息头 → 空行 → 消息体**。空行是生死线，它的作用是告诉解析器"头结束了"。

### 2.3 一个页面不是一次请求

打开一个新闻首页，HTML 只是第一个请求。HTML 里引用的 1 张图、2 个 CSS、5 个 JS、若干埋点脚本，每一个都是**独立的一次请求-响应**。

这一条决定了三件事，后面都会用到：
- 为什么"页面慢"通常不是服务器慢，而是请求数太多、串行排队
- 为什么 HTTP/1.1 会队头阻塞（同一域名并发有限、必须排队）
- 为什么 HTTP/2 要做多路复用（M16 回收）

## 4. 为什么这样设计（这一节决定你的理解深度）

**为什么是纯文本协议？**
为了让报文"人肉可读、可手写、可抓包直读"。代价是头部冗余、解析要逐字符扫描、数字还得转字符串。HTTP/2 改成二进制帧，本质就是把这个 trade-off 反过来了——牺牲可读性，换解析效率和压缩率。**没有哪个更好，取决于当时的主要矛盾。**

**为什么是无状态的？**
服务端不保存"你上次来过"的记忆，因此不需要为每个客户端预留内存，也就能扛住海量并发。代价是"我是谁"必须每次自己带上——于是有了 Cookie、Session、Token。
**关键认知：无状态不是设计缺陷，是刻意的交换。** 把状态从服务端搬到客户端，换的是扩展性。

**为什么必须有 Host 头？**
一台服务器（一个 IP）上可以跑很多个网站。没有 Host，服务端拿到请求后无法判断你要的是哪个站点。HTTP/1.0 没有它，所以那个年代基本是"一个 IP 一个站点"；HTTP/1.1 把它设为必填，虚拟主机才普及。
**这一点请记住，它是 M15 的伏笔**：Host 是明文，套上 TLS 之后服务端就看不到了，那 HTTPS 怎么区分同一 IP 上的多个站点？

**为什么用 URI 而不是直接用 IP？**
URI 描述"资源在哪台**逻辑主机**的什么路径"，IP 描述"物理上哪台机器"。两者解耦，才能做到换服务器不改网址、一台机器多个站点、以及后面所有"中间插一层"的操作（代理、CDN、负载均衡）。

## 5. 动手验证（10 分钟）

```bash
curl -v http://example.com/ 2>&1 | head -30
```

在输出里找齐三样东西：请求行的三个部分、Host 头的值、响应状态行。

然后打开浏览器 DevTools → Network，刷新任意一个内容站，看请求条数——用真实数字验证 2.3 那条"一个页面 N 个请求"。
