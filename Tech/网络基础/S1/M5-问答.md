### Q1｜概念：三种设备各在哪一层动手

包过滤防火墙、反向代理、CDN，都能让"打过去的请求不是源站在回"。

1. 三者分别在**哪一层**动手？各自**按什么**做决定？
2. 哪一个能看见 HTTP 请求里的 SQL 注入？为什么另外两个看不见？
3. 用户能不能察觉自己被导到了 CDN 节点上？从哪个信息能看出来？

**我的回答**：
包过滤防火墙在网络层和传输层动手，通过源目IP、源目端口和协议进行过滤；反向代理在客户端与服务端之间加了一层转发的代理服务器，应该是网络层，请求是代理在回；CDN是把请求导向了最近的缓存服务器，同样不是源站回。
反向代理可以看到SQL注入，因为它是识别明文传输的请求后再转发到Web服务器的，而包过滤防火墙只看IP、端口和协议不看包内容，CDN只接受导过来的请求并作出相应，拿到的不是原始请求。
可以，看HTTP包有没有Location重定向。
**反馈**：

**1 里三处要修一处半，2 基本对，3 错。**

**第 1 问**：防火墙 ✔。反代你写"应该是网络层"——去掉"应该"，**反代在应用层**，而且它做的正是你在沉淀里写对的那件事：**把 TCP 断开**。CDN 那一项没答"在哪一层"：**它在 DNS 层动手**，改的是解析结果，不是流量。

**第 2 问** ✔，理由对。但补一句边界：**谁能看见明文内容，取决于谁终结了 TLS/TCP**——反代终结了，所以它看得见。你说的"CDN 拿到的不是原始请求"不成立：CDN 边缘拿到的**就是原始请求**（它本质是反代加缓存），只是通常不负责拦；现在很多 CDN 自带 WAF，那就更能看见了。

**第 3 问错：CDN 不用 302 跳转。**它改的是 **DNS 解析结果**——你请求的域名一个字没变，只是解析出来的 IP 换成了就近节点，浏览器全程不知道。

而且证据就在你自己的输出第一行：

```text
www.taobao.com.danuoyi.tbcache.com.     ← CNAME，指向阿里 CDN
222.211.12.107
222.211.12.106
```

`danuoyi` 是阿里 CDN 的域名前缀，`tbcache` 是淘宝 cache。**这一行就是 CDN 的确证，你把它当噪音跳过去了。**这个问题比答错更值得记——M5 验证区批注里细说。

### Q2｜过程：有反代时，连接是谁建的

一个站点前面站着反向代理，源站是 `10.0.0.8:8080`。

1. 浏览器发起 TCP 连接时，对端是**谁的 IP 和端口**？这条连接的另一端在哪台机器上终结？
2. 源站处理这个请求时，它看到的**源 IP** 是谁？不是真实用户的话，源站还能靠什么拿到真实 IP？这个信息可信吗？
3. 同一台反代后面挂了 `a.com` 和 `b.com` 两个站，反代靠什么把请求分给不同的后端？

**我的回答**：
对端是反向代理的IP和请求，在经由反向代理转发的实际处理请求的Web服务器上终结。
源站看到的源IP是反向代理的IP，可以通过Forwarded字段看到真实IP，但这个字段可以被客户端伪造。
靠目录，如/a目录后的请求导向a.com，/b目录的请求给到b.com。
**反馈**：

**2 对，1 后半句错，3 错。**

**第 1 问**：前半句对（对端是反代的 IP:443）。后半句错——**这条连接在反向代理上终结，不在源站**。源站和浏览器之间根本没有连接，源站只跟反代之间有一条**新的、由反代发起**的连接。

这里有个值得你自己注意的现象：**你沉淀里写的是"反向代理断开 TCP"，那句是对的。**同一个知识点，题目里错、沉淀里对，说明你把这句话记住了，但没把它套到具体的两条连接上去。真懂不是能背出这句，是能指着一条连接说"到这儿就断了"。

**第 2 问** ✔。补术语：现代写法是 `Forwarded`，老的是 `X-Forwarded-For`。两者都是**代理自己加的**，客户端能伪造，所以源站只信**第一层可信代理**写下的那一段——再多层代理就往后面找，这也正是伪造能生效的地方。

**第 3 问错：`a.com` / `b.com` 是域名，靠 Host 头分，不是靠路径。**

你答的"按 /a /b 目录分"是另一种分流（location 分流），题目里两个站是**不同域名**，反代只能看 Host。

这条和 K02 是同一个判断，你骨架已经立过了——问题不在不知道，在**没往回连**。看到一个"一台机器上多个站"的场景，条件反射应该是"谁靠什么区分它"，而不是随手挑一个熟悉的字段。

### Q3｜判定：四个现象，各是什么设备

下面四个现象来自真实排查。逐个判断：**最可能是什么设备造成的**（防火墙 / 反向代理 / CDN / 都不是），并说出你依据的那一条。

1. `dig` 一个域名，回 6 个不同网段的 IP，换 `8.8.8.8` 再问又是另外 4 个。
2. `nc -zv ip 443` 显示端口开着，但 `curl` 报 `Connection reset by peer`。
3. 直接访问 `https://IP/` 报证书域名不匹配，加上 `Host` 头再访问就正常了。
4. 扫出 22、80、443、3306 全 open，但每个都连上就断，且没有任何应用层响应。

**我的回答**：
CDN，如果是同个Web服务器返回的内容应该不会是多个跨网段的IP，而且返回的IP也没在DNS服务器中有对应的域名记录。
防火墙，网络层过滤了请求。
反向代理，反向代理需要根据Host头转发请求。
不知道
**反馈**：

**1、3 对（1 的依据要改说法），2 错，4 不知道可以但要知道答案。**

**第 1 题**判对了，理由说得含糊（"IP 没在 DNS 中有域名记录"不通）。要的判据就一条：**多 IP + 换 DNS 结果还不同 + 落在 CDN 厂商段**——三个一起才是 CDN，单看"多个 IP"可能只是负载均衡。

**第 2 题是这一单元最容易错的一题，你踩的正是那个坑。**

`nc` 能连上，说明**TCP 三次握手成功了**——那就意味着网络层和传输层**已经放行**。所以不可能是"防火墙在网络层过滤"。

`Connection reset by peer` 的含义是：**有个东西接了你的连接，然后主动把它掐了。** 通常是应用层没有对应服务（反代转过去没人应答），或者策略设备做了重置。

记死这一对：

| 现象 | 含义 |
|---|---|
| 一直等到超时 | **没人理**——包被丢了（防火墙 drop、路由不通、目标不在） |
| 立刻 `reset` | **有人明确拒绝**——连接建起来了，被主动断开 |

这就是 N09 那条在防火墙场景里的样子。区分它，你就知道该去查策略还是查服务。

**第 3 题** ✔，判定和理由都对。

**第 4 题**：诚实写"不知道"比编一个强。答案是——**全端口 open 本身就是最可疑的信号**：正常主机不会 22、80、443、3306 一起开还都不给响应。常见成因是防火墙/IPS 的**欺骗式响应**（它替你应答了 SYN），或者把所有端口映射到一台不响应的机器（这叫端口欺骗/黑洞，红队里专门用来钓扫描器）。所以红队看到"全开"应当先怀疑陷阱，而不是高兴。

**① CNAME 就在第一行。**

```text
www.taobao.com.danuoyi.tbcache.com.
```

这是 `www.taobao.com` 的 CNAME，指向 `danuoyi.tbcache.com`——阿里 CDN 的域名（`danuoyi` = 阿里 CDN 产品，"挪移"；`tbcache` = 淘宝 cache）。**CNAME 指向 CDN 厂商，是判 CDN 最硬的一条**，比看 IP 归属还准。你贴了它，然后说"不知道是不是 CDN"。

**② 响应头里有边缘节点的签名。**

```text
server: Tengine

cache-control: max-age=0, s-maxage=106               ← s-maxage 是"共享缓存"有效期，只有 CDN/反代才用它
```

`s-maxage` 这个指令专门给"中间的共享缓存"看，浏览器不认它。**响应头里出现 `s-maxage`、`x-cache`、`via`、`x-air-*` 这一类，就说明有你和一个源站之外的第三方在参与应答。**

**③ 换 Host 那两条，你只贴了命令，没有输出。**

```bash
curl -sI https://222.211.12.107/ -H 'Host: www.taobao.com' | head -5
```

这两行下面没有任何结果——等于没跑。验证区的要求是**贴原始输出**，不是贴命令。这正是 N06 那条（做完了实验读不出证据）第 4 次出现。
但是这条命令就是没有输出

**最后一句反了**："并没有通过代理转发吧"——你看到的这个 200 响应**正是从边缘节点回来的**，`x-air-hostname` 就写着它在哪个机房。你已经在代理后面了，却以为自己在直连。

## 沉淀（本单元唯一入库物）

> **先确认「这个机制」指哪一条**：不是整章主题，是导读第 2 节里那条**判定/流程**。
> M5 的那条是：**一个请求被哪一层接走、靠哪个字段判定、判错的后果是什么。**

| 格 | 填什么 |
|---|---|
| ① 过程 | ______ 先 ______，然后 ______，最后 ______ |
| ② 为什么这样设计 | 不这么做会 ______；代价是 ______ |
| ③ 什么时候不成立 | 如果 ______，这套就不适用 |

**我的结论**（三格串成 2–3 句自己的话，不许分点照抄）：
防火墙只看五元组过滤，反向代理断开TCP作为中间设备转发客户端和服务端的请求，CDN作为导流的缓冲。防火墙只看五元组不看内容是因为本身在网络层，要看内容徒增功能和损耗；反向代理多了几跳才能到服务器增加了延迟；CDN是三方合作，无法控制缓存时间。

**反馈（沉淀 · 第一版，2026-11-04）**：

**判定：补一格。** ② 三句代价全对，是这轮写得最好的部分；① 的 CDN 那句太虚，③ 空着。

| 格         | 这次盯什么                                                                                                                                   |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| ① 过程      | 前两句 ✔ 保留（"反代断开 TCP"这句是全对的，比 Q2 第 1 问答得准）。**CDN 那句重写**："作为导流的缓冲"什么都没说清——要写成 **"CDN 不动流量，它改的是 DNS 解析结果：域名不变，解析出的 IP 换成就近边缘节点，请求压根没往源站去"** |
| ② 为什么这样设计 | ✔ 不用改。三条代价分别对应三个设备，一句一个，很清楚                                                                                                             |
| ③ 什么时候不成立 | 空。至少一条：**反代"看得见内容"这件事在 HTTPS 之后就不成立了**——它必须先终结 TLS 才看得见，你要是做了证书固定或端到端加密，这层就瞎了；或者：**CDN 只能加速"能被缓存/能被拆开"的东西**，纯长连接（WebSocket、数据库连接）导不过去   |

**这轮有个现象值得你自己看一眼**：

5 个错里，有 3 个不是"不知道"，是**知道但没套上去**——反代终结 TCP（你沉淀里写对了）、Host 分流（K02 你立过骨架）、CDN 靠解析（导读写了）。这类错比"不会"更值得警惕，因为它不疼：你答的时候是顺的，判下来才知道错了。**下次遇到这类题，先问自己一句「这个场景里，动手的是谁」，别急着挑一个熟悉的词填。**
防火墙只看五元组过滤，反向代理断开TCP作为中间设备转发客户端和服务端的请求，CDN修改DNS解析结果，将域名解析为就近到CDN节点，通过该节点响应请求。防火墙只看五元组不看内容是因为本身在网络层，要看内容徒增功能和损耗；反向代理多了几跳才能到服务器增加了延迟；CDN是三方合作，无法控制缓存时间。反向代理要看见明文内容需要流量包不加密或可解密，否则同样无法解析Host头，CDN只能缓存可被拆开的内容，若本身就需要持续连接的流量就无法导向最近节点解析。
补完交回，过了 K06 入库。剩下最后一个 K07（加密在哪一层），那一单元会正面撞上这里 ③ 埋的"反代在 HTTPS 之后还看不看得见"。

**反馈（沉淀 · 第二版，2026-11-04）**：

**判定：过。** → 已入 [[_结论]] K06

| 格 | 判 |
|---|---|
| ① 过程 | 三句全对。CDN 改成"修改 DNS 解析结果、解析为就近节点、由该节点响应"，这才是它的动手位置——和防火墙、反代完全不在同一层 |
| ② 为什么 | 三条代价原样保留，不用改 |
| ③ 不成立 | 两条都写出来了，方向都对。这是本单元最有价值的一格，见下 |

**③ 里有两处要各补半句，都是 K07 的入口。**

**第一处（你说对了一半）**：

> 反代要看见明文内容需流量不加密或可解密，否则无法解析 Host 头

对。但补一句：**HTTPS 里 Host 头确实加密了，可 SNI 是明文的。** 反代即使解不开内容，也能从 TLS 握手第一个包里读到你要访问的域名（除非上了 ECH）。所以"看不见 Host"和"看不见你在访问谁"是两件事——**前者被加密挡住了，后者还漏着**。这一条在监控和流量分析里天天用得上，K07 正面讲。

**第二处（措辞要收紧）**：

> CDN … 若本身就需要持续连接的流量就无法导向最近节点解析

准确说法分两件：

- **长连接（WebSocket）能过 CDN**，只是只能透传、不能缓存，所以享受不到加速。不是"导不过去"。
- **真正导不过去的是非 HTTP 协议**（数据库连接、任意 TCP），因为 CDN 只认 HTTP/HTTPS 那一套。

差别在于：前者的限制是"加速失效"，后者的限制是"根本进不来"。红队判断一个目标能不能走 CDN 打，看的就是这个区别。
