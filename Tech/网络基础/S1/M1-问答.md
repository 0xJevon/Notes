### Q1｜推演：交给下一层的到底是什么

`GET http://a.example.com:8080/x?y=1` 这个请求，浏览器最终要交给操作系统的，**不是 URL 这个字符串**。

请说清楚：它具体交出去的是哪几样东西？（提示：其中一样是字节流，另有两项是"目的地"的组成部分）

如果只能交出一个 IP 而不知道端口，会发生什么？

**我的回答**：HTTP协议，主机名a.example.com和端口8080，程序x和参数y=1。因为一个IP上可以搭建多个网站并通过端口映射网站服务，所以只有IP操作系统并不知道要将请求内容交给哪个网站服务器处理自然得不到任何响应。

**反馈**：

交出去的是三样：**按 HTTP 格式拼好的字节流** + **IP 地址** + **端口**。你写对了端口这个位置，另外两样都偏了。

**错 1（措辞）**：交出去的不是「HTTP 协议」。协议是**格式约定**，交出去的是**符合这个约定的那段字节**。区别相当于「中文」和「一句具体的中文」。

**错 2（要紧）**：**主机名不在交出去的东西里。** 交给操作系统时它已经是 IP 了。主机名没消失，是去了两个地方——

- DNS 用它换成 IP（M2 的事）
- 写进报文里的 `Host:` 头（给服务端看，不是给系统看）

所以「目的地」只有 IP + 端口两项，没有主机名。

**错 3（最要紧，也是本单元的病根）**：你写「一个 IP 上可以搭建多个网站**并通过端口映射**网站服务」——**这是把 Host 头的活派给了端口。**

三样各管一段，别混：

| 谁      | 管什么             | 例子            |
| ------ | --------------- | ------------- |
| IP     | 哪**台**机器        | 183.2.172.177 |
| 端口     | 这台机器上哪个**进程**   | 443           |
| Host 头 | 这个进程该服务哪个**站点** | www.baidu.com |

一个 IP + 一个 80 端口跑一千个网站，靠的全是 Host，**端口一次都没变过**。你在 Q3 又犯了同一个错，那里详说。

**最后那个假设（只给 IP 不给端口）**：你说「得不到任何响应」。结果说得通，但因果不是「交给了错的服务器」。真实情况更阴——**协议有默认端口**（http→80，https→443），所以只给 IP 不会报错，它会**静默地连到默认端口**。如果服务其实在 8080，你看到的是「连不上」或者「连上了但不是你要的东西」，而报错信息里不会提示「你少给了端口」。

**这种错最难查**：不报错，只是不对。

### Q2｜反例：这句话错在哪

> "HTTP 是无状态协议，服务端不会记得你，所以 HTTP 根本做不了登录功能。"

这句话哪一半是对的，哪一半是错的？错的那一半，靠什么补上的？补上之后，"HTTP 无状态"这句话还成立吗？

**我的回答**：HTTP是无状态协议，所以服务端记不到客户端是正确的，为了通过HTTP实现登录功能添加了Cookie、Session和Token等机制，客户端登录后为用户颁发这些识别标识从而实现认证用户身份的功能，所以通过HTTP可以做登录功能但是通过其他机制实现的所以HTTP还是无状态的。

**反馈**：

**方向对，最后一句是对的，而且是最重要的一句**——补了这么多机制，HTTP 依然无状态。这句判断很多人会答错，你没答错。

**一处要精确**：「服务端记不到客户端」——**服务端完全记得住**（Session 就存在它那儿）。无状态说的是**协议不要求、也不内建**「记住上一次」。

这两句差一个字，后果差很远：

- 「记不到」是**能力问题**，听着像服务端做不到
- 「协议不要求」是**规定问题**，服务端爱记不记，协议管不着

**另一处可以再分一层**：你并列的 Cookie / Session / Token 其实在回答三个不同的问题。

| 机制      | 状态存在哪    | 回答的问题                      |
| ------- | -------- | -------------------------- |
| Cookie  | 客户端      | 怎么**自动带上**上次的标识            |
| Session | 服务端      | 状态存哪、怎么不让客户端看见（客户端只拿一个 ID） |
| Token   | 客户端（带签名） | 服务端怎么**不存也能验**它是真的、没过期     |

一句话带走：**无状态不是缺陷，是把状态从服务端搬到客户端，换扩展性。** 代价就是「我是谁」每次都得自己带上——这正好是下一题 Host 头的同款逻辑。

### Q3｜预测：把 Host 头拿掉会怎样

假设时间回到 HTTP/1.0，没有 Host 头。某公司只有一个公网 IP，却想在这个 IP 上同时提供 `www.a.com` 和 `mail.a.com` 两个完全不同的网站。

在当时，这件事能做到吗？如果做不到，他们有哪些变通的笨办法？HTTP/1.1 加了 Host 之后，为什么这个限制就消失了？

**我的回答**：做不到，因为HTTP/1.0强制绑定一个IP对应一个网站，将公网IP绑定到a.com，然后通过目录访问以实现可访问不同的两个网站。HTTP/1.1加了Host后就可以通过端口区分要访问的网站了，所以可以在一个IP上提供不同的网站。

**反馈**：

**结论对（当时做不到），变通办法给了一个（同域名下用不同目录），但中间那句是反的。**

**错 1（关键）**：「HTTP/1.1 加了 Host 后就可以**通过端口**区分要访问的网站」——**恰恰相反：正是因为有了 Host，才不用换端口。**

Host 头里明写着 `Host: www.a.com`，服务端读这个字段选站点，**一个 80 端口就够**。如果靠端口区分，那每多一个网站就得多占一个端口——一千个网站要一千个端口，跟「一个 IP 多个站点」的初衷正相反。

正确表述：**Host 头让「地址」和「站点」解耦。** 同一个 IP:端口后面可以站无数个站点，用请求里的域名来挑。

**错 2**：不是「HTTP/1.0 **强制**绑定一个 IP 对应一个网站」。协议没写这条规定。真实原因是：**报文里没有任何字段能承载域名**，服务端收到请求后无从区分。这是**能力缺失造成的既成事实**，不是明文规定。

这个区别不是抠字眼：规定要改得改标准，能力缺失补个字段就行——HTTP/1.1 就是补了个字段。

**漏掉的变通办法**（当时真有人这么干）：

- 给一块网卡绑多个 IP，一个站点一个 IP
- 一个站点一个端口（:80 / :8080 / :8081）
- 前面架个反向代理，按域名分流——**这其实就是自己手搓了一个 Host 头**，只不过判断发生在代理上而不是源站上

最后这个值得多看一眼：它说明 Host 这个思路早就存在了，只是当时不在协议里。

**记住一句**：**端口区分进程，Host 区分站点。** 你在 Q1 栽的也是这一处，两题同一个病根。

### Q4｜归因：为什么"加载完成"了图还在转

浏览器状态栏已经显示"完成"，但页面里的图片还在一个个慢慢出来。

请用"请求-响应"模型解释这个现象的成因。并回答：**如果这个页面在 HTTP/1.1 下打开很慢，换到 HTTP/2 会明显变快，原因是什么？**（这题超纲一点，答不出没关系，说出你的猜测即可）

**我的回答**：状态栏显示完成是对网站页面的请求完成了，但每个请求对应一个响应所以页面中的图片也需要通过请求加载，图片的加载也会有大小和先后顺序的区别所以是一个个慢慢出来。我猜底层应该还是一样需要对资源分别请求但请求资源的格式可能换成更适应传输的格式，然后请求的方式也类似并发请求可以异步传输请求并返回响应。

**反馈**：

**方向对：一个页面是 N 次独立的请求-响应。** 但漏了最关键的那一环，所以「一个个慢慢出来」这个现象没被解释。

**漏的是并发上限。** HTTP/1.1 下浏览器对**同一个域名**只开 4–6 条 TCP 连接（各家不同，Chrome 是 6）。HTML 里引用的 20 张图，只有 6 张能同时在路上，剩下 14 张**在队列里等着**。

所以慢不是因为图大，是因为**它在排队**。你说「大小和先后顺序的区别」——大小影响单张的耗时，但让它们「一个一个」出来的，是那 6 个名额。

顺带分清两个常被混的词：

- **排队**：同域名连接数不够，后面的请求还没发出去
- **队头阻塞**：同一条连接上，前一个响应没传完，后面的只能等

**HTTP/2 你猜得不错**（并发、异步），精确一点：**一条 TCP 连接上并行跑多个流（多路复用）**，不再受那 6 条连接的限制；再加上头压缩（HPACK），把每次重复的 Cookie、User-Agent 压掉。

**一个可以自查的地方**：你自己的 curl 输出里写着 `ALPN: server accepted http/1.1`——刚才那次访问用的就是 1.1，不是 h2。你手上本来就有一份对照样本。

### Q5｜推演：换成二进制协议，这些概念还在吗

HTTP/1.1 是文本协议，有"请求行""消息头"这些说法。HTTP/2 改成了二进制帧。

那么"这是一个 GET 请求""我要访问 /x""我的 Host 是 a.com"这三条**信息**还在吗？如果还在，它们变成了什么形式？

由此追问一句：**协议"长什么样"和协议"表达什么"，是同一件事吗？**

**我的回答**：还在只是从原本的格式换成了二进制格式。协议长什么样只是对于人而言的，文本协议方便人阅读但底层都是二进制数据，因为完成操作的始终是计算机，如同汇编与二进制码一样，汇编只是方便人识别但计算机操作的始终是二进制码，所以长什么样对于计算机而言没区别，表达的是什么，要完成什么操作才重要。

**反馈**：

**这题答得最好。** 类比是你自己推出来的（汇编 vs 机器码），不是书上抄的，而且站得住。

**补一层更精确的**：信息不只是「换成二进制」，是**被拆进不同类型的帧里**了。

`GET /x HTTP/1.1` + `Host: a.com` 这三条信息，在 HTTP/2 里变成了 **HEADERS 帧**里的伪头字段：

```text
:method:    GET
:path:      /x
:authority: a.com
```

响应体走 **DATA 帧**。所以「信息还在」要加一句：**换的是承载结构，不只是编码方式**。文本协议里它们是三行字，二进制协议里它们是三个字段——解析器不再逐字符扫行，而是按帧长切。

**你的结论我同意一半**：「长什么样对计算机没区别」——对，但**对人、对效率有区别**。

- 文本：人肉可读、可手写、抓包直读 → 代价是头冗余、逐字符解析、数字得转成字符串
- 二进制：解析快、可压缩、可并行 → 代价是再也读不懂了，排障必须靠工具

所以答案不是「无所谓」，是**取舍**。导读第 4 节那句「没有哪个更好，取决于当时的主要矛盾」，就是这个意思。

### Q6｜前瞻：加密之后 Host 藏起来了

承 Q3：Host 头让一台机器能服务多个网站。但 HTTPS 把整个 HTTP 报文加密了，服务器在解密之前看不到 Host。

那它**怎么在解密之前就知道该用哪张证书**？如果这一步做不到，会发生什么后果？

（这题是本单元的伏笔，答不出完全正常——请写下你的猜测，答完 M15 我们回头对答案）

**我的回答**：可能有个第三方机构去辨别网站使用的证书，然后告知服务器该什么什么证书解密，如果服务器在解密前不知道要使用哪张证书自然不能完成HTTPS报文的解密，识别不出Host头自然就不知道请求该给哪个服务器也就无法返回响应消息。

**反馈**：

**你把 CA（证书颁发机构）和「每次连接时挑证书」混成了一件事。**

CA 只负责**签发和背书**——它盖章证明「这张证书确实是 baidu.com 的」，但它**不参与每一次连接**，也不知道此刻是谁在连你。所以「第三方机构告知服务器用哪张证书」这条路走不通。

**真实机制叫 SNI**（Server Name Indication）：TLS 握手的第一个包（ClientHello）里，客户端**明文**带上自己要访问的域名。服务器看到域名，在给出证书之前就知道该拿哪张。

**你的 curl 输出里就有铁证，三行：**

```text
* TLSv1.3 (OUT), TLS handshake, Client hello (1):     ← 第一个包，域名在这里
* TLSv1.2 (IN), TLS handshake, Certificate (11):      ← 证书是第二个包才来的
> GET / HTTP/1.1
> Host: www.baidu.com                                 ← Host 在握手全部结束之后
```

**服务器给证书时，Host 还没发出来，而且就算发了也是加密的。** 它唯一知道域名的途径就是 ClientHello 里的 SNI。

**后果你推到一半说对了**（不知道用哪张证书就打不开），但更准确的是：**握手在第一步就断了**，不是「解密失败」——证书选择发生在加密参数协商**之前**，那时候还没有「解密」这回事。

**多给你一条安全视角**：SNI 是明文。所以即便内容全加密，**路上任何人都能看见你在访问哪个域名**。这就是 ECH（Encrypted Client Hello）要解决的问题，M15 展开。

这题不用改，钩子种对了就行。M15 回来对答案。

**输出里至少四个证据你没读：**

**证据一：`ALPN: curl offers h2,http/1.1` → `server accepted http/1.1`**

协议是可以**协商**的。客户端说我支持 h2 和 1.1，服务端选了 1.1。所以刚才那次访问不是 h2——你 Q4 猜「HTTP/2 更快」，这里正好有一份现成的对照：同一台服务器，你的客户端带着 h2 的能力去，它给了你 1.1。

**证据二（这段输出里最值钱的一条）：**

```text
* TLSv1.3 (OUT), TLS handshake, Client hello (1):
* TLSv1.2 (IN), TLS handshake, Server hello (2):
* SSL connection using TLSv1.2
```

**客户端发的是 1.3，服务端回的是 1.2。** 最后实际用 1.2。

这是一次真实的**版本协商**，而且方向是**向下**——客户端只能「报出自己最高支持多少」，不能「要求用多少」，决定权在服务端。安全圈管这个叫**降级**，是 TLS 攻击面里最经典的一类（攻击者就靠掐掉高版本握手来逼你降到弱版本）。

你的输出里白纸黑字写着这件事，你把它当噪声划过去了。

**证据三：`subjectAltName: "www.baidu.com" matches cert's "*.baidu.com"`**

两件事：
- 证书匹配看的是 **SAN**（使用者可选名称），不是 CN（`CN=baidu.com` 只是显示用）
- 这是张**通配符证书**，`*.baidu.com` 覆盖所有子域

第二条正好解释了你 Q6 猜不出的东西：**对百度这种站点，就算没有 SNI 也能挑对证书**，因为它只有一张通配符证书。但一家公司如果同时挂 `a.com` 和 `b.com` 两张完全不同的证书，**没有 SNI 就物理上选不出来**——这才是 SNI 存在的理由。

**证据四：`> Host: www.baidu.com` 出现在证书之后**

`>` 是 curl 标记「我发出去的」。它在 `Certificate (11)` **之后**出现，而且是加密发的。

**服务器给证书的时候，Host 还没发出来。** 这就是 Q6 的答案——它一定有别的途径知道域名（SNI），否则不可能挑对证书。

## 本单元自评

合上书，用一句话说清：**Host 头解决的是什么问题，它的存在暴露了 HTTP 的哪个前提假设？**

**我的自评**：Host头解决了如何确定访问的网站，也就是提供服务的服务器的地址，暴露了HTTP协议是对服务器的请求，要获得网站服务器的响应。

**反馈**：

**前半对，后半没答到。**

**前半有一处不准**：「也就是提供服务的服务器的**地址**」——Host 里放的是**域名**，不是地址。而且「哪台服务器」是 IP 决定的，Host 决定的是**这台服务器上的哪个站点**。

地址 / 端口 / 站点，三个层级，Host 只管第三个。这跟 Q1、Q3 是同一个坑。

**后半答偏了**：「暴露了 HTTP 是对服务器的请求」——这不是假设，这是**定义**。题目问「前提假设」，是问：**HTTP 在设计时默认了什么，以至于需要加一个字段来补救？**

答案是：**它默认「一个地址 = 一个站点」**。

早期 URL 里的主机名和「那台机器上唯一的那个网站」是一回事，所以报文里根本不需要再写一遍——你连的是哪台机器，那台机器上就那一个站。

Host 头的存在，恰恰是在**承认这个默认不成立了**：一台机器上可以有很多站点，所以每次请求都得自己报一次「我要哪个」。

换个说法：**Host 头是协议给自己打的一个补丁**，补丁的内容是「地址和站点不是一一对应」。

这个视角在 M15 会翻出新问题：补丁本身是明文的，套上 TLS 就看不见了——那 HTTPS 靠什么补（答案你已经知道了，SNI）。
