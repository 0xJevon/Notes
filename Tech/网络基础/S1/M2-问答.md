### Q1｜归因：两个 ping 结果不一样

```
$ ping 8.8.8.8          → 通
$ ping www.baidu.com    → Unknown host（解析失败）
```

**第一个结果证明了什么？**（提示：能 ping 通一个 IP，说明从你到它之间哪些东西是好的？至少列出 3 样）

**第二个结果又排除了什么？**（既然 8.8.8.8 通，说明网络本身没问题，那么……）

故障最可能在哪一层？如果这时候你换成 `curl http://www.baidu.com` 会看到什么？

**我的回答**：
第一个结果证明和8.8.8.8也就是DNS服务器之间网络层是连通的，可以发出请求并收到请求，请求的传输层也没有问题。
第二个结果说明无法找到域名对应的IP，网络没问题也就是DNS服务器的解析有问题或是网站本身有问题，但baidu.com作为通用域名应该不会有问题所以就是解析有问题，可能是DNS本身也就是应用层出问题，没有绑定域名的IP，直接curl因为无法将域名解析为IP所以无法找提供服务的主机自然无法获得响应。

**反馈**：
**对在哪**

- 第一问抓到了核心：能 ping 通说明网络层通。而且你把它当**排除法**在用，方向对。
- 第二问的推理链成立：8.8.8.8 通 → 网络没问题 → 问题在解析。这是排障的正确起点。

**错在哪**

1. **最关键的一条你没说，而它是这道题的全部意义：你 ping 的 8.8.8.8 是个 IP，整条 DNS 链一次都没被碰过。**

   你给的是 IP，解析器从头到尾没被调用。所以 ping 通它，证明的是「**DNS 之外的一切都正常**」，不是「DNS 服务器网络层通」。

   这两件事要分清楚：**能 ping 通 8.8.8.8 ≠ 能查 8.8.8.8**。后者要往 UDP 53 发一个 DNS 报文。前者只证明包能到那台机器，不证明那台机器上的服务在听。

   这就是 M1 那个病的兄弟：**能到达一台机器，和能使用它的服务，是两件事。**

2. **「传输层也没有问题」这句不成立。** ping 用的是 **ICMP**，它不走 TCP 也不走 UDP——ICMP 封装在 IP 里，跟 TCP/UDP 是**并列**的，不是上下级。

   所以这条 ping 一次都没碰传输层，你无法从它推出任何关于传输层的结论。

   这是 N08 的第 3 次（ICMP 归错层）。

3. **「没有绑定域名的 IP」这个说法偏了。** 不是 DNS 没绑定域名，而是**这台机器配的那个 DNS 服务器无法完成这次解析**。可能原因是：DNS 地址配错、DNS 不可达、域名确实不存在、hosts 被改、53 端口被拦。

   你直接跳到「DNS 应用层出问题」，把过程全跳过了。

4. **curl 会看到什么——你没给准。** 实际输出是：

   ```text
   curl: (6) Could not resolve host: www.baidu.com
   ```

   **它根本不会发起 TCP 连接。** 请求在解析这一步就断了，后面三次握手、发 HTTP 全都没发生。

   为什么这条重要——这就是你诊断 Q2 栽过的那一刀：`could not resolve`（解析没成）和 `connection timed out`（解析成了但连不上）是两种病，查的地方完全不同。前者查 DNS，后者查端口、防火墙、服务。

**再深一层**

你 ping 8.8.8.8 通了，能据此判断「你系统里配的 DNS 服务器地址就是 8.8.8.8」吗？如果不能，还缺哪一步？
不能，可以ping通只能证明ICMP可达，还需要dig一个域名可以获得DNS服务器地址

### Q2｜预测：TTL 往两个方向调

某条 A 记录的 TTL 现在是 3600 秒。

**情形 A：调成 60 秒。**
- 对"换服务器后多久全网生效"有什么影响？
- 对权威 DNS 服务器的查询压力有什么影响？
- 什么业务场景下必须这么调？

**情形 B：调成 86400 秒（一天）。**
- 换服务器时会遇到什么麻烦？
- 那为什么还有大量域名用很长的 TTL？

最后一句：**如果用一句话概括 TTL 在权衡什么，你会怎么说？**

**我的回答**：
TTL短，DNS解析缓存时间短，所以换服务器后全网生效的速度快但对权威DNS服务器的查询压力大，害怕业务故障需要故障转移的主站或是需要频繁测试的初上线网站需要把TTL调低一点方便及时更新。
TTL长，DNS解析缓存时间长，所以换服务器后会导致IP不能及时更新导致一直使用旧IP，如果域名不用频繁变动如博客之类的就可以使用长的TTL。
在域名变动、降低权威服务器压力与维持域名、IP稳定之间权衡。

**反馈**：
**对在哪**

**这题是三题里答得最好的**，三个方向全对：短 TTL 生效快但压力大、长 TTL 换服务器麻烦、最后落在「权衡」。而且你举的场景（故障转移、初上线测试）是真在用的，不是背的。

**错在哪**（都是「漏」，没有一个「错」）

1. **你漏了 TTL 最反直觉的那一点：要提前调低，不是改的时候才调。**

   因为旧 TTL 已经写进各家缓存里了。你现在把 3600 改成 60，只影响**之后**发起的查询；已经缓存了 3600 的那些 DNS，还得把剩下的时间走完。

   标准做法是三步：**提前 24–48 小时把 TTL 降到 60** → 等全网缓存都换成短 TTL → **再改 IP**，改完调回长 TTL。

   你答的「调 TTL 能加快生效」是对的，但不完整——**它加快的是下一次生效，救不了这一次。**

2. **TTL 不是你说了算。** 实际生效时间取决于**每一个中间缓存愿不愿意遵守**。国内部分运营商 DNS 会无视 TTL 强制缓存更久（几小时到几天），这种事真实存在，而且你这边没有任何办法强制。

   所以「TTL 设 60」≠「60 秒全网生效」，只是「60 秒后大多数地方生效」。

   这条直接连到沉淀的失效条件，等下说。

3. 长 TTL 为什么普遍——你答「不常变」。对，但还有一层：**TTL 长意味着抗故障**。权威服务器挂了，缓存还能撑一段；TTL 短的话服务器一挂，全网立刻解析失败。所以长 TTL 不只是省事，是多一层缓冲。

**再深一层**

一个域名的 TTL 是 86400，你现在**必须立刻**切 IP（比如源站被打挂要切高防）。你能做什么，做不了什么？
---
可以把TTL调小但是已经缓存了的域名DNS解析无法短时间修改
### Q3｜反例：这句话错在哪

> "DNS 用 UDP 而不是 TCP，是因为 UDP 比 TCP 快。"

这句话哪里不准确？准确的表述应该是什么？

再追问两个：
1. 什么情况下 DNS **会**用 TCP？
2. 如果 UDP 报文装不下答案，协议里是怎么处理的？（这个机制叫什么）

**我的回答**：
并不是UDP比TCP快而是UDP本身携带的数据少且连接机制简单，不用频繁的建立三次握手方便大量的DNS查询，降低服务器的压力。当返回包长度超过UDP长度上限就会用TCP，UDP装不下的答案会用TCP装，具体机制不知道叫什么。

**反馈**：
**对在哪**

「不是 UDP 比 TCP 快，而是 UDP 轻」——**核心抓对了**，而且给了理由（数据少、不用握手、降低压力），不是复述结论。

**错在哪**

1. **「轻」的本质你只说了一半。** 少一次握手只省几百毫秒，那不是关键。关键是：

   > **服务端不用为每个客户端保留状态。**

   一个公共 DNS 一天几十亿次查询。如果每次都要记「这个客户端建了连接、序号是什么、窗口多大」，内存直接爆。UDP 一问一答，答完就忘，服务端零负担。

   所以准确说法不是「UDP 快」，是 **UDP 无状态**。

2. **「什么情况下用 TCP」——你只答了一个，漏了最重要的那个。**

   | 场景 | 说明 |
   |---|---|
   | 响应被截断 | 你答的这个 ✓ |
   | **区域传送（AXFR/IXFR）** | **主从 DNS 同步整个 zone 文件，必须用 TCP。** 这是最常见的「必须 TCP」场景，跟答案太长无关 |
   | DNSSEC 大响应 | 签名数据让报文变大 |
   | 显式要求 | `dig +tcp` |

   区域传送那条值得记：它说明「DNS 用 UDP」从来不是绝对的，**协议早就为「必须可靠传输」留了 TCP 这条路**。

3. **那个机制叫 TC 标志位。** 过程是：

   ```text
   UDP 响应超过上限
     → 服务器在 DNS 头的 flags 里置 TC=1（Truncated）
       → 客户端看到 TC=1
         → 改用 TCP 重问一次
   ```

   这就是导读那句「平时不用，必要时用」的具体实现。

4. **上限不是死的 512。** 你的验证输出里就写着：

   ```text
   ; EDNS: version: 0, flags:; udp: 4096
   ```

   **EDNS0** 让双方协商 UDP 报文上限，从 512 提到 4096。所以现在绝大多数查询根本碰不到截断。

   这行是你自己贴上来的，没读。

**再深一层**

既然 EDNS0 已经把上限提到 4096，为什么 TC 这套机制还留着不废掉？
---
有需要使用TCP可靠传输的场景
### Q4｜推演：根服务器全挂了

假设全世界的根域名服务器同时宕机，并且短时间内不会恢复。

**你今天还能上网吗？** 分两种情况说：
1. 你要访问的网站，你今天已经访问过（缓存还没过期）
2. 你要访问一个从没访问过的域名

再往深一层：这个思想实验说明了 DNS 这套设计的什么特性？它是有意为之，还是运气好？

**我的回答**：
缓存过的网站不用根域名服务器，最近的DNS服务器应该就保存有记录，可以直接解析为IP访问。从未访问过的域名因为需要根域名做协调转接所以应该看不到。分层查看，保留缓存，有意为之的设计，让DNS服务器分层告诉找哪级服务器获得ip方便管理大量的域名和IP，同时通过缓存降低DNS服务器压力的同时可以提高网站的访问效率。

**反馈**：
**对在哪**

两问都对，「有意为之而非运气」这个判断也对。你答出了分层 + 缓存两个设计要素。

**错在哪**（都是可以再深一层）

1. **「能上网吗」这个问法，你答成了能/不能，但真实答案是分档的。**

   - 浏览器缓存或本地 DNS 缓存未过期 → **能上**，一次查询都不发
   - 缓存过期了，但缓存里**还留着 `.com` 的 NS 记录** → **也能上**，直接去问 `.com` 的服务器，跳过根
   - 连 `.com` 的 NS 也过期了 → 才真的失败

   第二档是关键：**根挂掉不等于全瘫，因为「下一跳是谁」这条记录本身也被缓存着，而且 TTL 通常更长**（NS 记录常见 2 天，A 记录常见几分钟到几小时）。

   这就是分层的真正价值——**不是「多几台服务器」，是「每一层都可以被单独缓存」**。

2. **比「上不上得了网」更准确的描述：新增能力全部失效。**

   老业务（缓存里有的）照跑；新域名、新证书、新服务、刚扩容的节点——全部解析不了。

   所以影响面不是「断网」，是「**长不出新东西**」。这个区分在应急时决定你先救什么：优先恢复的不是「上网」，是「新增解析」。

3. **「根全挂」这个假设，物理上几乎不可能——这是设计的一部分，不是巧合。**

   根服务器是 **13 个 IP 地址**，不是 13 台机器。每个 IP 背后是上百台实例，靠 **anycast**（同一个 IP 在全球多地同时宣告，就近应答）分散部署。任何一台挂了，其他接管。

   所以要「13 个全挂」，得同时打掉分布在几十个国家的上千台机器。

   这就是「抗毁」那条理由的具体实现——**它没有准备一个备用方案，它直接把单点从设计里删掉了**。

**再深一层**

如果攻击者不打根服务器，改打「某个域名的权威服务器」，会发生什么？影响面和根挂掉有什么不同？
---
该域名所管的区域会因没有DNS缓存而无法访问网站，根服务器挂掉还可以靠权威服务器分层查询，但权威挂掉既访问不到权威也访问不到根直接就没法访问新域名
### Q5｜辨析：哪一段是递归，哪一段是迭代

场景：你在公司电脑上打开浏览器，公司 DNS 是 `192.168.1.1`，它转发去问运营商 `114.114.114.114`，后者再去问根服务器。

请标出这条链上**每一段**是递归还是迭代，并说明判据（你怎么一眼看出来）。

再追问一个实际的：如果公司把 DNS 配成一个**根本不存在响应**的地址（比如 10.255.255.1），你打开网页会看到什么现象？多久才报错？为什么是这个表现？

**我的回答**：
浏览器输入网址从本地解析到公司DNS是递归，从公司DNS到运营商再到根服务器这种逐级查询是迭代，会加载一段时间后报错，时间要根据缓存时间来定，缓存时间过了向更上级DNS服务器查询时就会因不存在响应而报错。

**反馈**：
**对在哪**

第一段（应用 → 公司 DNS）判成递归，对。而且你抓住了「逐级查询」这个动作。

**错在哪**

**1. 「公司 DNS → 运营商」这一段，你判错了。它是递归，不是迭代。**

你把「公司 DNS → 运营商 → 根」当成一整段说成迭代。这是两段，语义不同：

| 段 | 谁问谁 | 期望返回什么 | 类型 |
|---|---|---|---|
| ① | 浏览器 → 本机解析器 → 公司 DNS | 最终答案 | 递归 |
| ② | **公司 DNS → 运营商 DNS** | **最终答案** | **递归** |
| ③ | 运营商 → 根 → .com → 权威 | 「下一步问谁」 | 迭代 |

公司 DNS 把请求转发给运营商，它要的是**答案**，不是「你去问谁」。所以 ② 仍是递归——叫**转发式递归**。

**判据只有一条，请背下来：**

> **看回来的东西是什么。给最终答案 = 递归；给「下一步问谁」 = 迭代。**

不是看谁问谁，不是看跳了几次，是**看返回的内容**。

这个错跟 M0 那个是同一个形状：**你把「动作相似」当成了「性质相同」**。两段都在往外问，但一段要答案、一段要指路。

**2. 第二问错了，而且错在根子上。**

你说「会加载一段时间后报错，时间要根据缓存时间来定」。**跟缓存无关。**

配一个不存在的 DNS 地址（`10.255.255.1`），意味着你发出去的请求**没有任何人应答**。

- 缓存里要是有这个域名 → 压根走不到这一步，直接命中
- 缓存里没有 → 才去问 → 然后**石沉大海**

时间由**超时和重试**决定：

```text
每个 DNS 服务器：超时 5 秒 × 重试 2 次
配了多个 DNS 地址 → 依次试
总时长 ≈ 5 × 2 × 服务器数
```

浏览器上大约转 **10–30 秒**，然后报 `DNS_PROBE_FINISHED_TIMEOUT`。

**3. 这里藏着一个你已经踩第三次的坑，必须单独说。**

> **「服务器明确说没有」和「没人应答」是两种完全不同的失败。**

| 现象                | 谁在说话            | 多快          | 含义        |
| ----------------- | --------------- | ----------- | --------- |
| `NXDOMAIN`（域名不存在） | DNS 服务器**明确回答** | **秒回**      | 有人在，说没有   |
| 超时（timeout）       | **没有任何人回答**     | **等满超时才放弃** | 没人在，或者被拦了 |

你现在把超时说成「缓存决定时间」，就是把这两种混了。

这个坑你已经踩了三次：

| 时间 | 表现 |
|---|---|
| 诊断 Q2 | `cannot resolve` 和 `Request timeout` 混为一谈 |
| M0 验证区 | `Time to live exceeded`（有回应但失败）当成失败划掉 |
| M2-Q5（这次） | 超时当成缓存问题 |

我建了一条新问题 **N09** 专门盯它。

这不是抠字眼——**在你的老本行里，DNS 被劫持/被拦截的表现就是「超时」，而域名拼错是「NXDOMAIN」，两者处置完全不同**：一个查链路和策略，一个查拼写。

**再深一层**

公司 DNS 把请求**转发**给运营商（递归），和公司 DNS **自己迭代**去问根——这两种配置，对「公司内部能不能看到员工访问了哪些域名」这件事，有什么不同？
---
公司DNS请求运营商，DNS分层查询就是运营商DNS服务器处理的所有公司内部看不到员工访问了哪些域名，而公司DNS自己迭代解析域名就可以看到查询的步骤也就知道员工访问了哪些域名

**另外六个证据你没读：**

**① TTL 三个不同的值：483 / 456 / 344**

同一份 A 记录，三次查询剩余 TTL 完全不同。**这是「每层缓存各自计时」的铁证**——不是一份记录被复制，是每个缓存从自己拿到那一刻开始倒计时。

M2 全部机制最直接的现场证据，你一个字没提。

**② `flags: qr rd ra`**

- `rd` = Recursion Desired（我要递归，给我最终答案）
- `ra` = Recursion Available（我支持递归）

**这两个 flag 就是 Q5 那道题在报文层的答案。** 你答错了 Q5，正确答案一直贴在你自己的输出里。

**③ `; EDNS: version: 0, flags:; udp: 4096`**

Q3 追问「UDP 装不下怎么办」的一半答案（另一半是 TC 位）。EDNS0 把上限从 512 协商到 4096。

**④ `SERVER: 223.5.5.5`**

你以为是本地 DNS，实际问的是**阿里公共 DNS**。所以 `dig baidu.com` 和 `dig @8.8.8.8` 结果一样——两个都是公共 DNS，都没走「公司 → 运营商」那条链。

**⑤ 4 个 A 记录，而且顺序会变**

`+short` 给 103/247/164/102，`dig` 给 247/103/102/164。**顺序不同。**

这就是 DNS 层的负载均衡：一次给多个 IP，客户端轮询或随机选。也是 CDN 的入口——不同地区解析出不同 IP，靠的就是这个。

## 本单元自评

不看资料，用两句话回答：**为什么域名和 IP 不能只留一个？**

**我的自评**：
IP必须保留是因为这个才是网络中找到主机及服务器的地址，域名是为了方便人记住从而访问，或当网站服务器迁移变更后可以直接重新绑定IP，但同样可以用相同的域名访问。

**骨架对，但只答了「方便」，没答「必须」。**

你写的三条（IP 是找主机的地址、域名方便人记、迁移后可重绑）都对。但题目问的是「**不能只留一个**」——要论证的是两边各自的**不可替代性**。你证了「域名有用」，没证「域名不可省」，也没证「IP 不可省」。

**为什么不能只留域名：**

网络设备（路由器、交换机、防火墙）**不做 DNS 查询**。每一跳转发都是拿目的 IP 去路由表做最长前缀匹配，从来不看域名。

如果只有域名：

- 每台路由器都得会解析域名 → 不可能，也不该（性能、安全、自治全是灾难）
- 更根本的：**DNS 自己跑在 IP 之上**。只有域名没有 IP，DNS 查询本身就无处可发——**循环依赖，系统起不来**

**为什么不能只留 IP：**

不是因为难记。是因为 **IP 是位置，不是身份**。

- 一台服务器换机房，IP 就变了，但业务身份不该变
- 一个 IP 上可以站无数个站点（M1 刚学的 Host 头）

所以 IP 表达不了「我是谁」，只能表达「我现在在哪」。**域名承担身份，IP 承担位置，两者变化频率不同，才必须分开。**

这一层正好接上你 M1 入库的那句「IP 定位服务端，Host 区分站点」——现在再往上加一层：**域名是更上面那层的身份。**
