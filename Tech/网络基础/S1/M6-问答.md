### Q1｜概念：加密之后还剩下什么明文

1. TLS 夹在哪两层之间？为什么防火墙看不见 HTTP 内容？
2. 一个 HTTPS 请求在路上，下面四样东西哪些**仍然明文**、哪些被加密了：**目标 IP、你要访问的域名、URL 里的路径、Cookie**？
3. 用一句话概括：HTTPS 藏住了什么、没藏住什么？

**我的回答**：
TLS在HTTP层和TCP层之间，防火墙在网络层，看到的已经是加密后的HTTP了。
目标IP和要访问的域名SNI没加密，URL里的路径和Cookie加密了。
HTTPS藏住了通信的内容和细节但没藏住要访问的目标。
**反馈**：**✔ 三问全对。** 位置对（夹在应用与传输之间，不是网络层加密），四样东西分得也对（IP、SNI 明文；路径、Cookie 密文）。第三问那句话本身就是本单元的结论。
只补一样漏掉的：**流量大小、时间、连接数也漏着**。加密不改变包的长度和节奏，所以"你几点上线、传了多大的文件、多久一次"全在外面。SNI 被 ECH 解决之后，这一层仍然是可用的。

### Q2｜过程：证书凭什么让浏览器相信

1. 一张证书里主要包含什么？它证明的是**哪一句话**？
2. 浏览器验证一张证书时，是拿什么去验的？"受信"这件事的源头在哪？
3. 下面三种情况，浏览器会不会告警：① 网站自己签的证书 ② 证书域名和访问的域名不一致 ③ 证书由一条你系统里已有的根签出。**第 ③ 种为什么危险？**

**我的回答**：
公钥、域名、CA和CA的签名，证明公钥属于域名；
验证CA的签名是否正确，信任的是第三方认证机构CA；
前两个会告警，第三个不会，因为信任主要是要本机信任，第三种攻击者可通过根签使本机信任恶意网站。
**反馈**：**△ 第 3 问最好，第 2 问答偏了一层。**

| 问   | 判                                                          |
| --- | ---------------------------------------------------------- |
| 1   | ✔ 公钥、域名、签发者、签名四样都在。漏了**有效期**——过期也会告警，而且是最常见的"什么都没改却打不开"的原因 |
| 2   | △ 见下                                                       |
| 3   | ✔ 结论对，理由也对："信任"落在**本机**，不落在 CA 声誉上                         |

第 2 问错在哪：你答"信任的是第三方认证机构 CA"。**这句话在概念上没错，但它答的是"谁签的"，不是"拿什么验的"。**

验的动作是**用上一级 CA 的公钥去解这张证书的签名**，解出来对得上，就往上走一级，直到走到一张**你机器里本来就存着的根证书**。链条尽头不是"某家机构"，是**你本机那个根证书库里的某一个文件**。

所以问题的后半句"受信的源头在哪"，答案就在你自己跑出来的那行：

```text
security find-certificate ... | grep -c 'BEGIN CERTIFICATE'
158
```

**158 —— 这 158 个文件就是"受信"的全部源头。** 你跑出来了，但没读它（N06 第 5 次，见下）。任何一张证书，只要能一路验到这 158 个里的任意一个，浏览器就不再问第二句。第三方机构之所以"可信"，只是因为**它的根恰好在你这 158 个里面**。

### Q3｜判定：三个现场

1. 你在公司网络抓包，看到 TLS 握手里 `server_name` 是 `mail.example.com`，但连接的目的 IP 是一个内网地址。**说明了什么？**
2. 用户访问 HTTPS 站点，浏览器**没有**任何告警，但你抓包能看到完整的 URL 和请求体。**最可能发生了什么？**
3. 一个域名，用 `ping` 解析出一个陌生 IP，`dig` 显示 CNAME 指向某云厂商，访问时浏览器证书显示是**你自己的域名**。这三条信息合起来，你判断是什么？

**我的回答**：
访问的网站是内网系统，或者是在内网访问的网站；
并没有用TLS加密HTTP，而是用本机根签签名的证书访问的HTTPS站点；
通过CDN搭建的仿冒网站，可能用于钓鱼。
**反馈**：**1 △ ／ 2 △ ／ 3 ✘（判反了）。** 三题都差在"从证据走向结论"那一步。

**第 1 问**方向对，但没落到"所以"。SNI 是 `mail.example.com`、目的 IP 是内网段，这条同时说明两件事：
- 这个域名**被解析到了内网**（内网 DNS 或 hosts 在起作用）；
- 更重要的一句你没说：**域名和 IP 在这一刻解耦了——判断你访问的是什么，只能看 SNI，看 IP 会判错。** 这才是这条观察的用途。

**第 2 问**说乱了。你写"并没有用 TLS 加密 HTTP"——**流量仍然是 TLS，加密一直在**。变了的是**对面是谁**：

> 中间有人（企业上网管理、杀毒软件的 SSL 扫描、恶意代理）把自己的根装进了这台机器，于是它和浏览器建一条 TLS、和源站再建一条 TLS，中间那段它是明文。你的抓包点恰好落在**它解密之后**的位置。

判据很好认：**看证书的 issuer**。正常站点是 GlobalSign／DigiCert／Let's Encrypt，被拦截时 issuer 会变成公司名或防火墙厂商名。这也是为什么"浏览器不告警"——它验的那条链确实通到了本机 158 个根里的一个。

**第 3 问判反了，这条最重要。** 三条信息摆在一起，指向的是**完全正常的 CDN 接入**，不是仿冒：

| 现象 | 正常 CDN 就该这样 |
|---|---|
| `dig` 显示 CNAME 指向某云厂商 | CDN 的标准接入方式就是 CNAME 到厂商域名 |
| `ping` 出陌生 IP | 那是**边缘节点**，本来就不该是你的源站 IP |
| 证书显示的是你自己的域名 | CDN 支持自定义域名 + 托管证书，所以证书必须匹配你的域名 |

三条**互相吻合、没有一条矛盾**。你判"仿冒"用的依据是"IP 陌生"——可"IP 陌生"就是 CDN 的定义。真正的仿冒会长什么样：**证书域名和你访问的域名不一致**，或者 CNAME 指向一个和该站点毫无关系的域名，或者证书 issuer 是不该出现的自签／企业根。判 CDN 与判仿冒，看的都不是 IP，是**这三条能不能自洽**。

## 动手验证（3 分钟，不做不影响判定）

```bash
# 看证书链：谁签的、签给谁
echo | openssl s_client -connect www.baidu.com:443 -servername www.baidu.com 2>/dev/null | openssl x509 -noout -subject -issuer -dates
subject=C=CN, ST=Beijing, L=Beijing, O=Beijing Baidu Netcom Science Technology Co., Ltd., CN=baidu.com
issuer=C=BE, O=GlobalSign nv-sa, CN=GlobalSign RSA OV SSL CA 2018
notBefore=Jul  9 02:32:55 2026 GMT
notAfter=Jan 24 02:32:55 2027 GMT
# 看本机信任了多少个根证书
security find-certificate -a -p /System/Library/Keychains/SystemRootCertificates.keychain | grep -c 'BEGIN CERTIFICATE'
158
```

**我看到了什么**（跑了才写，逐行说明每一行说明什么）：第一行是公司的名称和地理位置，第二行是签发机构GlobalSign，CA名称GlobalSign RSA OV SSL CA 2018

**我的批注**（三处）：

1. **第一行不是"公司名称和地理位置"，是证书主体（subject）。** `C=CN, ST=Beijing, L=Beijing` 是国家/省/市，`O=Beijing Baidu Netcom Science Technology Co., Ltd.` 是**这张证书的持有者**——百度，不是你所在的公司。这个字段的含义是"这张证书签给谁"，也是全链最该看的一行：**它和你要访问的域名是否一致，就是防钓鱼的全部依据**。
2. **`issuer` 是中间 CA，不是根。** `GlobalSign RSA OV SSL CA 2018` 之上还有一张 `GlobalSign Root CA`，那一张才是躺在 158 个文件里的。你说"验证 CA 的签名"，链上就有这一跳，只是你没指认出来——而这一跳正是"一路验到根"的实物。
3. **158 那行你没写。** 第二个命令的输出明明在，一字未提。N06 第 5 次：这已经是第 5 个单元出现"跑了、输出来了、没读成结论"。

## 沉淀（本单元唯一入库物）

> **先确认「这个机制」指哪一条**：不是整章主题，是导读第 2 节里那条**判定/流程**。
> M6 的那条是：**加密挡住了哪一段、哪一段仍然漏着、谁有机会站在中间。**

| 格 | 填什么 |
|---|---|
| ① 过程 | ______ 先 ______，然后 ______，最后 ______ |
| ② 为什么这样设计 | 不这么做会 ______；代价是 ______ |
| ③ 什么时候不成立 | 如果 ______，这套就不适用 |

**我的结论**（三格串成 2–3 句自己的话，不许分点照抄）：
TLS在HTTP和TCP之间加密，加密后还能看到目的IP和要访问的域名SNI等。如果在IP层加密就需要每台转发设备都能解密包否则连目的地址都不知道，现在这样加密使IP是明文可以知道目的地址，但内容是加密的所以若目的服务器不知道用什么证书解密同样看不到Host头也就找不到对应的网站服务。如果证书被伪造比如用根签签名就不会有TLS加密。
> 写完 → 我判「过 / 补哪一格」→ 过了写进 [[_结论]] K07。这是第一轮最后一个节点。

**判定（11-05）：补三格，不重写全篇。**

| 格 | 判 | 要动什么 |
|---|---|---|
| ① 过程 | 只给了位置 | 缺过程。补成"先…然后…最后" |
| ② 为什么 | 理由对，代价缺，末句机制反了 | 删掉末句，补代价 |
| ③ 不成立 | **错** | 这条整句重写 |

**① 要补的过程**：先发 ClientHello（**SNI 明文**在里面）→ 服务端回证书 → 客户端把签名一路验到本机受信根、确认"这公钥属于这域名" → 双方协商出会话密钥 → **之后所有 HTTP 都走这把密钥**。

**② 删掉这一句**："若目的服务器不知道用什么证书解密同样看不到 Host 头"。服务器**有私钥，解得开**。HTTPS 里服务端靠 SNI（明文）选站点和证书，不靠 Host——Host 加密了它反而看不见，这正是 M5 ③ 你写对的那半句。
② 的代价补一句即可：**每台中间设备都成了睁眼瞎，包括你希望它看见内容的那台**（所以企业只能靠装根重新看见）。

**③ 这句错了**：「证书被伪造比如用根签签名就**不会有 TLS 加密**」。

**加密一直在，变的是对面是谁。** 装了根之后，浏览器照样跟中间人握手、照样走 AES，握手时"锁"还亮着——只是对面不是源站，是一条能被解开的链路。**你把"加密"和"身份"当成了一件事。**

③ 换成这三条之一或全写（都是"机制没坏、结论错"）：

| 失效 | 机制哪里没坏 |
|---|---|
| 有人把根装进了这台机器 | 加密、验链全程正常，只是对面换了人 |
| DNS 被劫持 + 签一张 DV 证书 | 证书是真的、域名也是真的，只有 IP 是假的（K03） |
| 根本没上 TLS（`http://`） | 不存在"破解"，本来就没锁 |
TLS在HTTP和TCP之间加密，先发ClientHello（存有SNI），服务端回证书，客户端验签到本机的受信根确认公钥属于要访问的域名，然后双方协商会话密钥，通过该密钥加密通信。如果在IP层加密就需要每台转发设备都能解密包否则连目的地址都不知道，现在这样加密使IP是明文可以知道目的地址，代价是HTTPS对流量包具体内容做了加密只知道要发往对目的地址。没有使用https而是http，或是攻击者装了其他信任根到机器中。
**另有一件事要说**：Q2 第 3 问你已经答对了"装根→无感"，沉淀 ③ 却写成"不会有 TLS 加密"。**同一件事，题里对、沉淀里错**——这是 M5 那个病的第二次：不是不知道，是写的时候没把知道的调出来。
