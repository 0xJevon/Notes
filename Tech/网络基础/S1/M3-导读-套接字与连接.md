# M3 套接字与连接

> 归属：[[00-学习地图]] ｜ 答题：[[M3-问答]] ｜ 上一单元：[[M2-导读-域名如何变成IP]]

## 1. 这个单元要回答什么

两个问题，都是被日常用语耽误得最厉害的：

1. **"套接字"到底是什么东西？**（是一个程序？一个文件？一个连接？）
2. **发数据之前为什么要先"连接"？** 这一步到底做了什么？

第二个问题最容易被理解成"双方打个招呼确认在线"。**它远不止打招呼——它其实是双方协商出一整套收发规则，并各自建好账本。**

## 2. 核心机制

### 2.1 套接字不是程序，是一块记账信息

书里专门写了一个专栏（PDF p157，插进 Socket 里的是灯泡还是程序）来澄清这件事，说明这个误解很普遍。

准确的描述是：**套接字是操作系统内核里的一条记录**，存着这通通信的全部状态——对端 IP、对端端口、本端 IP、本端端口、当前序号、接收窗口大小、连接状态。应用程序手里拿到的只是一个编号（文件描述符），它所有"发送/接收"的调用，最终都是在改这块记录。

由此可以推出一条很重要的推论：**连接的状态在内核里，不在你的进程里。** 进程崩了，连接不一定立刻消失——M4 会用到这条。

### 2.2 "连接"这一步交换了什么

```text
客户端                                        服务端
   │  ① SYN  seq=x                                │
   │ ───────────────────────────────────────────> │
   │      "我想连你，我的起始序号是 x，            │
   │       我的接收窗口是 W1"                      │
   │                                              │
   │  ② SYN+ACK  seq=y, ack=x+1                   │
   │ <─────────────────────────────────────────── │
   │      "收到，我的起始序号是 y，                │
   │       我的接收窗口是 W2，                     │
   │       我确认收到了你的 x"                     │
   │                                              │
   │  ③ ACK  ack=y+1                              │
   │ ───────────────────────────────────────────> │
   │      "确认收到你的 y，开始吧"                  │
```

**这里面真正被同步的，是三样东西**，而不是一句"你好"：

| 交换的内容 | 为什么必须有 |
|---|---|
| 各方的**起始序号**（ISN） | 后面每个字节都要编号，双方必须知道从哪开始数，否则无法判断"有没有收到、缺没缺" |
| 各方的**接收窗口** | 告诉对方"我一次最多能接多少"，这是流量控制的前提 |
| **双向可达**的确认 | 我发的你能收到、你发的我也能收到，两个方向都要验证 |

### 2.3 连接的唯一标识：四元组

一条 TCP 连接由**四个值**唯一确定：

```text
（源 IP，源端口，目的 IP，目的端口）
```

理解这一条，很多现象就自洽了：

- 一台服务器的 80 端口为什么能同时服务几万个客户端？因为"目的端口相同"，但"源 IP/源端口"各不相同，四元组互不相同，所以是几万条不同的连接，而不是一条。
- 服务端为什么不会"端口不够用"？端口只有 65535 个，但**服务端用的是同一个本地端口（80），靠对端四元组区分**——所以限制不在端口数量，而在内存和文件描述符。

### 2.4 端口解决的是"同一台机器上的哪个程序"

一句话分工：**IP 定位机器，端口定位进程。**

0–1023 是知名端口，绑定需要特权；1024–49151 是注册端口；49152 以上是临时端口（客户端发起连接时由内核分配）。

这个分工解释了一个常见现象：为什么客户端连接数一多，会出现"端口耗尽"——因为**每个出去的连接都要占一个本地临时端口**，而临时端口是有范围的（Linux 默认约 2.8 万个，可用 `net.ipv4.ip_local_port_range` 调整）。

## 4. 为什么这样设计

**为什么必须有"连接"这一步，不能直接发数据？**

因为要发"可靠的字节流"，双方必须先对齐四件事：从哪个序号开始、我一次能收多少、你一次能发多少、两个方向是否都通。**这四件事没有对齐之前，收到的任何数据都无法判断是新的、重复的、还是乱序的。**

换句话说：连接不是礼貌，是**建立记账规则**。这也是为什么"三次握手保证可靠性"这句话是错的——握手只把账本立起来，真正的可靠性（确认、重传、排序、流控）发生在 M4。

**为什么是三次，不是两次？**

只握手两次会留下两个具体问题：

1. **被动方无法确认"对方收到了我的 SYN+ACK"。** 如果这个 ACK 丢了，被动方会以为连接已建立并开始分配资源，而主动方还在等——双方状态不一致。
2. **网络里滞留的历史 SYN 会造成假连接。** 一个很早以前发出的 SYN 如果延迟到达，被动方会误以为是一次新连接，单方面建立并占用资源，而主动方根本没有要连。第三次 ACK 让被动方得以确认"这一次是对方真的要连"。

两个问题都在第三次 ACK 里被解决——这就是为什么不能少这一次。

**为什么断开要四次？**

因为 TCP 是**全双工**的，两个方向的"我说完了"是独立事件。A 说"我没数据了"（FIN），只代表 A→B 方向结束；B 还可以继续发数据给 A。所以 B 要先回一个 ACK 表示收到，等自己也没数据了，再发自己的 FIN。两个方向各自关闭，所以是四次。

## 5. 动手验证（10 分钟）

```bash
# 终端 1：抓包
sudo tcpdump -nn -i en0 'tcp port 80'

# 终端 2：发起一次请求
curl -sv http://example.com/ -o /dev/null

# 终端 3：看连接状态
netstat -an -p tcp | grep -E 'ESTABLISHED|TIME_WAIT' | head
```

在抓包里按顺序找到 `[S]`（SYN）、`[S.]`（SYN+ACK）、`[.]`（ACK）、`[F.]`（FIN）。**亲眼确认序号和 ack 号的递增关系**，比记住"三次握手"这四个字有用得多。

macOS 的网卡名通常是 `en0`，用 `ifconfig` 确认一下。
