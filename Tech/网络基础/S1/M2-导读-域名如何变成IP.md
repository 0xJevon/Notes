# M2 域名如何变成 IP

> 归属：[[00-学习地图]] ｜ 答题：[[M2-问答]] ｜ 上一单元：[[M1-导读-从URL到HTTP请求]]

## 1. 这个单元要回答什么

浏览器手里只有一个主机名 `a.example.com`，它怎么变成一个 IP？**这个过程中谁在替我干活，代价是什么？**

这一节的真正难点不是"DNS 是什么"，是理解**为什么必须存在这么一套分布式系统**——为什么不能维护一份"全世界域名总表"。

## 2. 核心机制

### 2.1 IP 地址不是"一个数"，是一组三层含义

`192.168.1.10/24` 要拆成三部分理解：

| 组成 | 值 | 作用 |
|---|---|---|
| 地址 | 192.168.1.10 | 标识这台机器 |
| 掩码 /24 | 前 24 位是网络号 | 决定"哪些地址算自己人" |
| 网关 | 192.168.1.1 | 同网段之外的所有去处 |

**关键机制：一台上网机器在发包前，先做一次判断**——
目的地址和自己同网段吗？同网段 → 直接在局域网里喊（ARP，见 M5）；不同网段 → 一律交给网关，不管对方在天涯海角。

这就是为什么网关地址**必须和自己的地址在同一网段**：否则你连网关都喊不到，还谈什么交给它。这条是理解路由的第一块砖。

### 2.2 为什么域名和 IP 必须并存

| | 域名 | IP |
|---|---|---|
| 对谁友好 | 人 | 机器 |
| 稳定吗 | 稳定（可换后端） | 会变（换机房、换云） |
| 能定位吗 | 不能，必须先翻译 | 能 |

两者并存不是历史包袱，而是**解耦**：网址描述"我要找谁"，IP 描述"它此刻在哪台机器上"。有了这层解耦，换服务器、加 CDN、做灰度，用户都不用改任何东西。

### 2.3 一次域名解析，实际有四段

| 步骤 | 谁问谁 | 方式 | 拿到什么 |
|---|---|---|---|
| ① | 应用程序 → 解析器（`getaddrinfo`） | 函数调用 | 阻塞等待结果 |
| ② | 解析器 → 本地 DNS 服务器 | **递归**（UDP 53） | 要么给答案，要么报错 |
| ③ | 本地 DNS → 根 / 顶级域 / 权威 | **迭代** | 每一级只说"下一步该问谁" |
| ④ | 各层缓存 | 受 TTL 控制 | 命中就跳过 ③ |

**②和③的区别是最常被混淆的地方，务必分清：**

- **递归** = 我不管过程，你给我最终结果。（客户端对本地 DNS）
- **迭代** = 告诉我下一步问谁，我自己去问。（本地 DNS 对根、对顶级域）

### 2.4 缓存在四五个地方同时存在

浏览器缓存 → 操作系统缓存 → 本地 DNS 缓存 → 各级 DNS 服务器缓存。每一层都有自己的过期时间。

所以"我明明改了 DNS 记录，为什么还是访问到旧服务器"——不是一个地方没生效，是**四五个地方各自持有过期副本**。

## 4. 为什么这样设计

**为什么是分布式，而不是一份全世界总表？**
三个理由，按重要性排：规模（十亿级域名，没有任何单点能扛住查询量）、**自治**（某个公司改了记录，不该需要去某个中心机构报备）、抗毁（没有单点故障）。代价是：查询可能要多跳几次，而且**结果最终一致而非实时一致**——这就是 TTL 存在的根本原因。

**为什么用 UDP 而不是 TCP？**
常见的错误答案是"因为 UDP 快"。准确的说法是**因为 UDP 轻**：一问一答、没有握手、服务端不用为每个客户端保留状态。一个 DNS 服务器一天要处理几十亿次查询，如果每次都要三次握手 + 四次挥手，成本不可接受。
代价很具体：UDP 报文有长度上限（传统 512 字节），答案太长会被截断，此时返回一个"截断"标志，客户端改用 TCP 重问一次。**所以 DNS 不是"不用 TCP"，是"平时不用，必要时用"。**

**TTL 的本质是什么？**
它是**一致性 与 查询量**之间的一个旋钮：
- TTL 长 → 缓存命中率高、权威服务器压力小，但改了记录要等很久才全网生效
- TTL 短 → 改记录生效快，但查询量暴涨

这是全书反复出现的主旋律：**几乎所有网络设计，都是在几个互相矛盾的目标之间取平衡，没有"更好"，只有"更适合当下"。** 你以后遇到任何"为什么要这么设计"，先找它在平衡哪两件事。

## 5. 动手验证（10 分钟）

```bash
dig example.com +short                  # 最快的一次查询
dig example.com                          # 看 ANSWER SECTION 和 TTL 字段
dig +trace example.com | head -40        # 亲眼看到"迭代"：根 → .com → 权威
dig @8.8.8.8 example.com                 # 换一个 DNS 服务器问，比较结果和 TTL
```

`+trace` 那一条是本单元的核心验证：**你会亲眼看到本地解析器一级一级问下去，每级只回一句"去问它"。** 这比读十遍"迭代查询"的定义有用。

## 6. 伏笔

DNS 查询默认是**明文**的。中间人既能看到你在查什么域名，也能直接改掉返回的 IP。

由这一点可以推出两个后续问题（M15 回收）：
1. 怎么让别人看不到你在查什么？
2. 看到也改不了，靠什么保证？
